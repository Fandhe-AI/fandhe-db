# SELECT DISTINCT ON の構文解析と ORDER BY 先頭一致の検証

- ステータス: 実装記録（Issue #3260。親 #3259。後続 #3261・#3262）
- 対応ビヘイビア: SQL-25 のポインタ（`docs/spec/04-behavior/sql-surface.md`）。spec 本文は転記しない
- 依存・unsafe の変更なし

## 1. 範囲

本 Issue は構文解析・個数上限・`ORDER BY` 先頭一致の検証までを担う。行を返す実行段は #3261、`ORDER BY` なしの決定性・結果行数の上限・RLS 越境の試験は #3262 の範囲。

整合した文（検証を通過した文）は通常の広域取得として黙って実行せず、`0A000`（"SELECT DISTINCT ON is not supported yet"）で fail-closed に拒否する。誤った行を返さないための暫定で、#3261 が置き換える。

## 2. 判定順序

| 順 | SQLSTATE | 内容 |
| -- | -------- | ---- |
| 1 | `42601` | 構文（空リスト・閉じ括弧欠落・末尾カンマ・SELECT リスト欠落） |
| 2 | `54000` | `ON` リストの式数が `MAX_SCALAR_ORDER_KEYS`（8）超。確保前に検査 |
| 3 | `42P01` | FROM の関係が未知（`view::resolve_from`） |
| 4 | `42P10` | `ORDER BY` 先頭との不一致 |
| 5 | `0A000` | 整合しているが実行段が未実装 |

- 集計・`GROUP BY`・`HAVING`・ウィンドウ・距離順位付け・`USING PLAN`・投影のスカラーサブクエリとの併用は `0A000`
- 検出位置は共有の検証経路 `validate_select_statement`。Parse／Describe・ビュー本文・カーソル等の入口は同じ分類になる
- CTE 本文・WITH 主クエリは `parse_distinct_shape` 冒頭で `0A000`。JOIN・集合演算・派生表・FROM なしは従来どおり拒否のまま（#3259）
- 列名 `on` は `DISTINCT` 直後でも、3 番目のトークンが `(` でなければ従来の経路で解釈する

## 3. 先頭一致の規則

PostgreSQL と同じ。`ORDER BY` キーを先頭から見て、`ON` 集合に含まれるキーは結果列へ加え、含まれないキーを読み飛ばした後に `ON` 集合のキーが現れたら `42P10`。さらに `ON` のキーで結果列に無いものがあり読み飛ばしが起きていれば `42P10`。`ASC`／`DESC`・`NULLS` は影響しない。`ORDER BY` なしは整合（決定性は #3262）。

- 比較は式の構造的等価（識別子は書かれたとおりに比較）
- 出力別名・序数は、一意に解決できるときだけ式へ置き換えて比較する。曖昧・位置が確定しない（`*` 含む）・範囲外は推測せず `0A000`
- ビューの別名書き換えより前の、利用者が書いた名前どうしで比較する

## 4. 既知の差と引き継ぎ

- 未知列（`42703` 等）は束縛段の判定で、PostgreSQL は未知列を `42P10` より先に判定する。本実装では先頭一致を先に判定する。順序の確定は #3261 で束縛段を通すときに行う
- `0A000` の暫定・NULL キーの同一グループ化・行を返す受理: #3261
- `ORDER BY` なしの決定性・上限・越境の試験: #3262
- JOIN・集合演算・派生表・CTE 文脈の DISTINCT ON: #3259
