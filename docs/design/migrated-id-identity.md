## 1. 背景・目的

移行 Issue #2200 で既存表の `id` は通常の `BIGINT` PRIMARY KEY 列になる。ただし INSERT・COPY・NoSQL は
現状 `id` の明示を必須にしている。親 #1696 の目的は、移行後の既存表の `id` を PostgreSQL 17 の
`GENERATED BY DEFAULT AS IDENTITY` 相当にし、`id` を省略した書き込みでサーバーが採番することである。

本 ADR は後続 #1698〜#1700 の判断がぶれないよう、次を実装設計として記録する。

1. 割り当てる SEQUENCE（名前・所属・`OWNED BY`・初期値・上限・欠番・並行採番）
2. 明示 `id` との共存（BY DEFAULT）
3. `USING OPERATION_ID` と台帳の関係
4. 影響する表層の一覧

本書の決定は、公開 Issue（#1696〜#1700）に既に書かれた内容・PostgreSQL 17 の公開挙動・本 ADR
独自の実装上の決定だけで構成する。独自の決定は「#169x で確定」または「自動運転下の判断で、
人間の確認が要る」と明記し、spec が確定した事項と区別する。

### 1.1 Issue 文言の統一（台帳に採番値を保存しない）

Issue #1697 の起票時の文言には「台帳へ採番値を保存する形式」とある。しかし
[sequence-namespace-and-ledger.md](sequence-namespace-and-ledger.md) の D1（台帳値のレイアウトを
変えず、新しい台帳版も作らない）と §11.1（再送は `23505` で再実行せず、同じ値を再現しない）、
および兄弟 #1700 は、いずれも「台帳に採番値を保存しない」で確定している。本 ADR もこの立場に
統一し、**保存形式の設計はしない**。

## 3. 決定

### D1. 適用範囲

- #2200 で移行した既存表の `id` 列だけに適用する。新規作成の表・一時表・matview には適用しない
- 新規表は #1693 の範囲で、主キー列を省略して DEFAULT が無ければ従来どおり `23502`
  （TABLE-23 (6) ポインタ）
- 移行済みかどうかは、#2200 がカタログに残す移行済みの印で判定する。印の実体は
  `RowIdentity::MigratedId`（カタログ v15 の `rowmode:migrated`。[rowid-primary-key-separation.md](rowid-primary-key-separation.md) の §12）

### D2. SEQUENCE の割り当て（#1698 で確定）

- 名前は PostgreSQL と同じく `<table>_id_seq`。relation 名前空間で衝突したら、PostgreSQL の
  `ChooseRelationName` と同様に数字の接尾辞を付けて衝突しない名前を選ぶ。63 バイトを超える
  場合は表名側を切り詰め、選んだ名前は `validate_identifier` を通す
- 所属は `public` の共有定義で、採番状態はテナントごと。#1711／#1717 の後に表が SCHEMA を移る
  場合は表の SCHEMA に追随させる（[schema-tenant-namespace.md](schema-tenant-namespace.md)
  D7・D12、sequence ADR §7.5 の残課題）
- パラメータは `AS bigint` 相当・INCREMENT 1・MINVALUE 1・MAXVALUE は `i64::MAX`・START 1・
  CACHE 1・NO CYCLE。上限を超えたら `2200H` で fail-closed
- 内部生成の経路は SQL の `CREATE SEQUENCE` を経由しない。そのため `AS`・`OWNED BY` が SQL 上
  `0A000` のままでも作れる

### D3. テナントごとの初期値（#1698 で確定）

- 初期状態の作り方・移行の原子性・再実行条件は、private spec のポインタ表記に留める
  （`docs/spec/04-behavior/data-model.md` TABLE-24 (1)〜(4)・`docs/spec/04-behavior/recovery.md`
  RECOVER-1・RECOVER-10〜12）。公開境界の拡張にはオーナー承認が要るため、承認記録が得られるまで
  具体の契約は本書へ転記しない
- 実装の所在: `catalog/sequence/migrated_identity.rs`。具体の方式・値域の扱いは上記ポインタ先と
  #2200 の判断に従い、本書には転記しない

### D4. IDENTITY 相当の表現（#1698 で確定。自動運転下の判断で、人間の確認が要る）

- 採用案: `id` 列に `ColumnDefault::Sequence` を付け、SEQUENCE 側の `owned_by` を有効にする
  （定義 blob v3。未知の値は `CorruptSchema`）。BY DEFAULT の INSERT の挙動は `DEFAULT nextval`
  と観測上同じで、#1690 の省略列の採番経路をそのまま使える
- 列と SEQUENCE の結び付きは、RENAME に耐えるよう内部 ID で持つ方式を推奨する。現状の
  `ColumnDefault::Sequence` は名前で保持するため、sequence ADR §9.2 の「依存する DEFAULT が
  あれば RENAME は `0A000`」が掛かる。名前か内部 ID かは #1698 で確定する
- #1695（`GENERATED … AS IDENTITY`）と表現を共有する。#1695 は `ColumnDefault::Identity` を採用して着地した
  （[sequence-namespace-and-ledger.md](sequence-namespace-and-ledger.md) §13）。#1698 はこの表現へ合わせ、
  本案の独自表現は採らない
- 確定（#1698）: `ColumnDefault::Identity { sequence, kind: ByDefault }` を採用する。列と SEQUENCE は名前で
  結び付き、`ALTER SEQUENCE … RENAME` は sequence ADR §9.2 のとおり `0A000` のまま受け入れる。
  部品は `assign_migrated_id_identity_in_txn`。
- 結線（#1699。自動運転下の判断で、人間の確認が要る）: #2200 の移行と #1698 の部品は、それぞれの PR が
  「結線は相手の担当」としたまま着地したため、本番経路の移行済み表に SEQUENCE が無かった。#1699 で
  `legacy_id_migration` に 2 段目を足して埋めた。1 段目（印の書き換え）は不変で、2 段目は「移行済みなのに
  `id` を所有する SEQUENCE が無い表」を読み取り txn で検出し、表ごとに 1 つの write txn で部品を呼ぶ
  （世代 bump・commit まで同じ txn）。#2589 以降にすでに移行済みの DB も次の open で補完され、1・2 段目の
  間のクラッシュも次の open で収束する。前提不一致などは、その表を見送る（SEQUENCE の無い移行済み表のまま。
  下記 D6 の `23502`）。Backend の I/O エラーは open を失敗させる。副作用: 既存の全表に `<table>_id_seq` が
  見えるようになる（PostgreSQL の IDENTITY 列と同じ。名前の衝突時は `seq1`… の接尾辞）
- 保留案: 新しい列属性 `identity`（BY DEFAULT／ALWAYS と sequence_id）。ALWAYS や `OVERRIDING` を
  扱う #1695 の判断に委ねる

### D5. OWNED BY に連動する DDL

- PostgreSQL の挙動に合わせ、DROP TABLE と `DROP COLUMN id` で、所有されている SEQUENCE を
  同じ txn で削除する
- SEQUENCE だけを DROP すると依存の `2BP01`
- `ALTER TABLE … RENAME TO` では SEQUENCE の名前を変えない
- `TRUNCATE … RESTART IDENTITY`（SQL-48 ポインタ）は #1645 で受理済みで、所有者が付いた SEQUENCE が対象になる
  （そのテナントの全行が消えた後に START へ戻るため衝突しない）。`ALTER COLUMN … DROP IDENTITY` は、
  受理する Issue が決まるまで `0A000`
- ALTER SEQUENCE の RESTART は全テナントへ作用する（sequence ADR §9.2）。所有された SEQUENCE への
  RESTART は既存の `id` と衝突して `23505` を招く。DDL 権限ゲートの下にあり、データ破壊ではなく
  一意性違反で止まる

### D6. BY DEFAULT と明示 `id` の共存（#1699 で確定）

- `id` を省略すると採番する。明示した値はそのまま受理し、SEQUENCE を進めない
- 後で採番した値が明示値と衝突したら PRIMARY KEY 違反の `23505`（行制約由来。台帳由来の
  `23505` とは `error_class`／variant で区別する）。自動で飛ばして次の値を採ることはしない
- 既存 SQL の互換を維持する: `INSERT … (id, …)`・`WHERE id = n`・`ON CONFLICT (id)`
- `VALUES (DEFAULT, …)` による明示の省略は既存の DEFAULT 経路に従う
- 確定（#1699）: 移行済み表の単一行 `INSERT` に限り、列リストの疑似列 `id` の省略を受理する
  （束縛段はスキーマだけで判定し、SEQUENCE の有無は見ない）。採番は書き込み txn 内で、台帳照合と
  NOT NULL 検査の後に所有 SEQUENCE（既定名 `<table>_id_seq` を優先し、所有者で検証。だめなら所有者で走査）
  から払い出す。session の `currval` にも記録されるので `currval('<table>_id_seq')` が使える。
  `RETURNING id` は払い出し値で投影し直す。SEQUENCE の無い移行済み表への省略は、DEFAULT の無い
  NOT NULL 列を省略した場合と同じ `23502`（列名 `id`、値は消費しない）で、判定はカタログだけで決まり
  他テナントの状態を引かない。従来方式のままの表（実行時に作った表は次の open まで）と、NoSQL の
  公開 `bind_insert` は従来どおり `22000`

### D7. 欠番・並行採番

- `SequenceAllocator`（`(tenant_id, sequence_id)` ごとの Mutex）と単一ライタの redb の組み合わせで
  二重採番は起きない
- ROLLBACK・失敗した文・制約違反・接続断で消費した値は欠番になる（TABLE-24 (1) ポインタ）
- ROLLBACK 後のクラッシュでの再払い出しは、sequence ADR §11.2 の不採用判断を引き継ぐ

### D8. 台帳との関係（#1700 で確定）

- 台帳には採番値を保存しない（§1.1）。内容照合ハッシュは送られた値（採番前）で計算し、
  省略した `id` は「省略列に適用した DEFAULT」として材料から除外する
- 明示 `id` の文のハッシュはバイト単位で不変にする（golden を不変）。`id` を省略した文は、どの
  明示 `id` の文ともハッシュが一致しないこと（省略を 0 として `push_u64` しない）。#2196 とは
  どちらが先に着地しても golden を保つ
- 確定（#1699。単一行分。自動運転下の判断で、人間の確認が要る）: `OpTag::InsertIdentity = 21`
  （通常形）と `OpTag::InsertIdentityExpr = 22`（`VALUES` に単独の時刻関数・`nextval` を含む形）を追加した。
  材料は明示 `id` の文（`Insert`・`InsertExpr`）から `id` を除いたもの（visibility → embedding → 列）。
  明示 `id` の文のバイト列は不変（golden）。複数行・COPY・NoSQL は #1700 が同じ系列で拡張した
  （下の「確定（#1700）」）。UPSERT は `id` 省略を受理しない
- operation_id を指定した再送は `23505` で再実行せず、SEQUENCE を進めない（同じ `id` を再現しない）
- operation_id を省略した書き込みは台帳に記録せず、再送すれば別の値を採番する
- `--require-operation-id` の構成で省略すると、値を消費せずに `23502`
- 複数行 INSERT は [multi-row-dml-operation-id.md](multi-row-dml-operation-id.md) の方式
  （1 文 = 1 台帳エントリ）で、行ごとに採番する
- 確定（#1700。自動運転下の判断で、人間の確認が要る）: `OpTag::InsertIdentityBatch = 23`・
  `InsertIdentityBatchExpr = 24` を追加した。材料は明示 `id` のバッチ（`InsertBatch`・
  `InsertBatchExpr`）から行ごとの `id` を除いたもの（件数プレフィクスと行ごとの列数
  プレフィクスは維持）。SQL 複数行・COPY・NoSQL が同じ関数を共有し、全行が明示 `id` のバッチは
  従来のタグ・バイト列のまま（golden 不変）。省略行と明示行の混在バッチは `0A000`（SQL・COPY は
  列リストを共有するため表現できず、NoSQL の行ごとの有無だけが該当。ハッシュに行ごとの有無を
  持ち込まない）

### D9. 影響する表層（各 sub-issue が着地するまで fail-closed）

| 表層 | 現状 | 担当 |
| ---- | ---- | ---- |
| SQL 単一行 INSERT | `id` 省略を受理（#1699 で着地。従来方式の表は `22000`） | #1699 |
| SQL 複数行 INSERT | `id` 省略を受理（#1700 で着地。全行一様。混在は `0A000`） | #1700 |
| `RETURNING id` | 採番値で投影し直す（#1699 で着地。sequence ADR §8.4） | #1699 |
| UPSERT（`ON CONFLICT`） | `id` 省略・`DEFAULT nextval` とも `0A000`（#1700 の結論: 受理しない。衝突時の欠番と `DO UPDATE` の意味が未設計） | #1700 |
| COPY FROM | 移行済み表は `id` 列を省略可（#1700 で着地。`\N` の `id` は `22000`）。`DEFAULT nextval` は `0A000` | #1700 |
| NoSQL HTTP insert | 移行済み表は `id` キーを省略可（#1700 で着地。`"id": null` は `22000`）。`returning` は NOSQL-22 で対象外 | #1700 |
| ファイル形 INSERT（path/body） | `0A000` | 対象外のまま |
| 更新可能ビュー経由の INSERT | [create-view.md](create-view.md) | #1699 の結論: 基表の `id` を省略する形は `0A000` のまま（`WITH CHECK OPTION` の検査時点と採番値の関係を検証し切れていないため）。受理は後続 Issue |
| 分割実行 DML・一時表・matview | INSERT を伴わない／適用外 | 対象外 |

### D10. テナント境界とエラー契約

- 状態行のキー先頭は `tenant_id` で、初期値はテナントごと
- 他テナントの最大 `id`・採番量を、エラー文言・`2200H` の有無・応答時間から推測できないようにする
- 利用者が `nextval('<table>_id_seq')` を直接呼んでも、作用は呼び出し元テナントに閉じる
- 未対応の形は `42601`／`0A000` で拒否する（RLS-9・RLS-10 ポインタ）

## 7. セキュリティ上の不変条件

- 採番状態はテナントごとに分ける（D10）
- 名前は `validate_identifier` を通したものだけを使い、SQL／プラン文字列へ連結しない
- 未知の blob 版・タグは `CorruptSchema`
- 移行の走査は既存データの量に比例する一度きりの処理で、外部入力では起動しない
- 依存は追加しない

## 8. Issue #1700 実装記録（複数行・COPY・NoSQL への拡張）

ポインタ: TABLE-23・TABLE-24・RECOVER-1・RECOVER-10〜12・RLS-9・RLS-10・NOSQL-6。
自動運転下の判断を含むため、人間の確認が要る（下の D-b・D-c・D-d）。

- 受入: operation_id 付きの再送は文全体が `23505` で再実行せず、SEQUENCE も進まない。operation_id
  省略の書き込みは台帳に残らず、再送すれば新しい値を採番する。クラッシュしても二重採番は無い
- Issue 題名にある「台帳に保存し再送で同じ値を返す」は採用しない（§1.1。#1699・#1692 と同じ解釈）
- D-a ハッシュ: D8 の確定（#1700）のとおり、タグ 23・24 と、全行明示のバッチの不変
- D-b 混在バッチ: `0A000`。SQL・COPY は列リストを共有するため表現できず、NoSQL だけが該当する
- D-c 採番順: 台帳照合 → NOT NULL 検査 → 列の SEQUENCE（`nextval`・`DEFAULT nextval`）→ `id`（行順）→
  行書き込み → 制約検査。PostgreSQL との差は、`VALUES` で `nextval('<table>_id_seq')` を併用した
  場合に限り観測できる。所有 SEQUENCE が無い表は値を消費せずに `23502`
- D-d UPSERT: `0A000` のまま（D9）
- COPY: `schema.is_migrated_id()` の表に限り `id` 列の省略を受理する。session 付きの完了処理
