# 運用: バックアップ・整合検査・復元と変更ログ

- ステータス: 運用手順（Issue #2158）
- 対応: Issue #2158（親 #2154）。ドキュメントのみの変更で、コード・依存・CI は変えない
- 関連ビヘイビア: RECOVER-13（取得・検査・復元）・RECOVER-14（変更ログ）。ポインタ: `docs/spec/04-behavior/recovery.md`。本文は転記しない（[spec-confidentiality](../../.claude/rules/spec-confidentiality.md)）
- 関連 doc: [backup-snapshot.md](backup-snapshot.md)（取得方式の判断）・[change-log-pitr.md](change-log-pitr.md)（変更ログの設計）・[README](../../README.md)（フラグの詳細と出力形式）

## 1. 対象と前提

- 対象は redb の単一ファイル（DB）である。運用者は `wire-server` の `backup`・`verify`・`restore`・`change-log-verify` の各サブコマンドと、サーバー起動時の `--backup-socket`・`--change-log*` 系のフラグを使う
- DB ファイルには全テナントのデータが入る。取得物・一時ファイル・復元先は、いずれも運用者だけが読める場所に置く（ファイルは 0600 で作られるが、ディレクトリの権限も絞る）
- バックアップに含まれないもの: `--users` ファイル（ロールと検証子の初期ブートストラップ用）と、redb の外にある状態（セッション専用の一時表など）。`--users` ファイルは別途保管する

## 2. 取得（`wire-server backup`）

### 2.1 停止中と稼働中の違い

| 項目 | 停止中（`--db`） | 稼働中（`--backup-socket` 経由） |
| ---- | ---------------- | -------------------------------- |
| 経路 | CLI が DB を直接開いて書き出す | 稼働中のサーバーに依頼し、サーバー内で書き出す |
| 書き込みへの影響 | 停止している前提のため、影響する書き込みはない | 書き込みを止めない（読み取りトランザクション内で書き出す） |
| 事前条件 | サーバーが同じ DB を開いていないこと | サーバーを `--backup-socket <path>` 付きで起動すること（opt-in。既定ではソケットを作らず、unix 限定） |
| 使用中の扱い | サーバーが開いていると `in use` で終了コード 1。何も変えない | 同時に実行できる書き出しは 1 本。実行中の依頼は終了コード 1 で返る |
| 取得中のファイル | 影響なし | 長い読み取りトランザクションはページ回収を止めるため、取得中は DB ファイルが伸びうる |

- 稼働中の取得でも、DB ファイルを OS の `cp` などでコピーしてはいけない。稼働中のファイルの素朴なコピーは一貫性が保証されず、実測でも開けない・古い状態になる失敗が出ている（[backup-snapshot.md](backup-snapshot.md) の第 3 節）
- 停止中の `--db` 取得は、DB を通常の書き込み可能な open で開く。そのため、旧形式の `id` の一方向移行が必要な DB では、移行が元ファイルに書かれる。移行前のバックアップは README「既存データディレクトリの `id` 移行とバックアップ」の節のとおり、サーバーを停止してファイルをコピーして保管する

### 2.2 一貫性の取得点

- 取得点は、書き出しの読み取りトランザクションを開いた時点で commit 済みのデータである。書き出し中に commit されたデータは含まれない
- 出力は単一の時点の一貫したスナップショットになる（redb の読み取りトランザクションの保証に基づく）
- フルバックアップは、変更ログのメタ情報（DB 識別子・timeline）と commit 番号の表を含むため、増分の連鎖の起点にできる（4.4 節）。チェックサムは記録しない（3.4 節）

### 2.3 手順

停止中の DB を取得する場合:

```bash
wire-server backup --db <DB のパス> --out <新しい出力先のパス>
```

稼働中のサーバーから取得する場合は、サーバーを起動するときに `--backup-socket` を付ける。

```bash
wire-server --users <users ファイル> --db <DB のパス> --backup-socket <ソケットのパス>
wire-server backup --socket <ソケットのパス> --out <新しい出力先のパス>
```

稼働中の経路の制約:

- ソケットの親ディレクトリは起動ユーザーの所有で、group・other に権限がないこと（0700 相当）。満たさなければ起動を拒否する
- ソケットは 0600 で作られ、テナント向けの TCP リスナーとは分離されている。認可はファイルシステムの権限だけである
- 既存のパスは、接続を拒否される古いソケットの場合だけ置き換える。通常ファイル・ディレクトリ・シンボリックリンク・稼働中のソケットは起動を拒否する。停止時にソケットを削除するが、残っていても次回起動で置き換える
- CLI は、ソケットが自分の所有で 0600 相当でなければ接続せず、終了コード 2 で拒否する
- 要求は出力先の絶対パスの 1 行（4096 バイト以内。全体で 5 秒の期限）。応答の待ち時間には上限がないため、大きな DB では完了まで長くかかる

出力先の制約:

- `--out` は**まだ存在しない**パスに限る。空・`..` 成分・ファイル名なし・親ディレクトリの不在・既存のファイル／ディレクトリ／シンボリックリンク（壊れたリンクを含む）は、DB を開く前に拒否する。既存のバックアップや DB を上書きしない
- 出力は同じディレクトリに 0600 の一時名で作り、完成後に最終名へ公開する。最終名に不完全なファイルは現れない
- hard link 非対応のファイルシステムでは使えない
- 出力は全データの複製になるため、出力先には DB のサイズ以上の空き容量を見込む
- 出力先ディレクトリは運用者だけが読めるようにする

### 2.4 一時名の残骸

- 取得中の一時名は `.fandhe-snapshot-<pid>-<seq>.tmp`（`--out` と同じディレクトリ、0600）である
- 強制終了や電源断で残りうる。最終名には現れない
- 残骸が見つかったら、該当の CLI・サーバーが動いていないことを確かめてから手動で削除する。中身は全テナントのデータのコピーである
- 最終名が存在しなければ、残骸を残したまま同じ `--out` で取り直せる

### 2.5 終了コード（`backup`）

| 終了コード | 意味 |
| ---------- | ---- |
| 0 | 成功。標準出力に `backup written: ...` を出す |
| 1 | 実行時の失敗（DB を開けない・稼働中のサーバーが使用中・書き出し中の失敗・socket 経路で別の書き出しが実行中） |
| 2 | 引数または出力先パスの拒否（DB は開いていない）。socket 経路では、ソケットの所有者・権限の拒否も含む |
| 3 | 出力は最終名へ公開済みで中身は完全だが、一時名の削除や親ディレクトリの fsync を確かめられなかった |

終了コード 3 のときは、`--out` に完成したファイルがある。出力を `verify` で確かめてから使うか、消してから取り直す。同じ `--out` で再実行すると、既存の出力先として拒否される。

### 2.6 取得後の確認

- 取得後は必ず `wire-server verify --db <出力>` で整合を確かめる（3 節）。`verify` は元ファイルを変更しない

## 3. 整合検査（`wire-server verify`）

```bash
wire-server verify --db <DB のパス> [--memory-budget-bytes <n>]
```

- 停止中の DB を、元ファイルへ書き込まずに検査する。取得物・復元物・停止中の DB のいずれにも使う
- 検査の中身（項目と重大度）は `Storage::verify_integrity`（Issue #2155）による。Warning は正しさに影響しない衛生指標や遅延再構築待ちで、終了コードは 0 のまま件数だけ報告される
- `--memory-budget-bytes` は重複検査の集合に使うメモリの目安の上限（既定 64 MiB）。小さくすると走査を分割し、分割の上限を超えた項目は「検査できなかった項目」として報告する

### 3.1 検査経路

| `verify_mode` | 条件と動作 |
| ------------- | ---------- |
| `read_only` | 通常の経路。書き込み権限なしで開き、共有ロックを取って直接検査する。コピーも一時ファイルも作らないため空き容量は要らず、検査の前後でファイルのバイト列は同一である |
| `copy` | 読み取り専用では開けない状態（異常終了後の修復が要る・redb のファイル形式の更新が要る）のときだけ使う。元ファイルを排他ロックで保持したまま、同じディレクトリの 0600 の一時コピーを検査して消す。修復はコピーにだけ入る。この経路だけ DB と同程度の空き容量と、同じディレクトリへの書き込み権限が要る |

- `copy` 経路で強制終了や電源断が起きると `.fandhe-verify-<pid>-<seq>.tmp` が残りうる。全テナントのデータを含むため、見つけたら手動で削除する
- 稼働中のサーバーが開いている DB は、どちらの経路でも排他ロックが取れず、`in use` で終了コード 1 になる（フォールバックしない）。稼働中のプロセスとデータには影響しない
- `verify` 同士は並行できる。`verify` の実行中に別のサーバーを起動すると、そのサーバーの起動は拒否される
- `--db` は既存の空でない通常ファイルに限る。存在しないパスや長さ 0 のファイルは、空の DB として初期化されないよう拒否する

### 3.2 出力

標準出力に `key=value` 形式の行を出す。

- 先頭行は `status=consistent|inconsistent|incomplete`
- 続いて `storage_tables_scanned`・`catalog_tables_checked`・`rows_scanned`・`error_total`・`warning_total`・`incomplete_total`・`findings_truncated`
- (種類, 表) ごとに `finding code=<識別子> severity=<error|warning|incomplete> table=<表の識別または -> count=<件数>`
- 最後の行は `verify_mode=read_only|copy`

行の値・キー・テナント名・パスは出さない。機械可読の JSON 形式は設けず、この行形式を安定した契約とする。

### 3.3 終了コード（`verify`）

| 終了コード | 意味 |
| ---------- | ---- |
| 0 | 整合（Warning だけを含む場合も 0） |
| 1 | 実行時の失敗（DB を開けない・稼働中のサーバーが使用中・`copy` 経路のコピー中の失敗・検査を始められなかった） |
| 2 | 引数の不備、または `--db` が既存の空でない通常ファイルではない |
| 3 | 検査は完了したが、`copy` 経路の一時コピーを消せなかった。結果の行は標準出力に出ている。残ったパスは標準エラーに出る |
| 4 | 矛盾あり（Error が 1 件以上。検査できなかった項目が同時にあっても 4） |
| 5 | 検査できなかった項目（未対応の表・読み取り失敗・予算超過）だけがある。整合とは報告しない |

### 3.4 検査の限界

- redb のページチェックサムは、通常の読み取りでは検証されない。ページ単位の破損は検出できない（[implementation-status.md](implementation-status.md) の Issue #2156 の記録）
- フルバックアップ自体のチェックサムは記録されないため、`verify` の対象外。増分の連鎖は `restore --incremental` が検証する（4.4 節）

## 4. 復元（`wire-server restore`）

```bash
wire-server restore --from <バックアップのパス> --db <新しい DB のパス>
```

### 4.1 手順（fail-closed）

1. `--from` を読み取りで開き、共有ロックを試みる。他のプロセスが開いていれば拒否する（稼働中の DB を復元元にしない）。`--from` は変更しない
2. `--db` と同じディレクトリの 0600 の一時名 `.fandhe-restore-<pid>-<seq>.tmp` へコピーし、サイズを確かめて fsync する
3. 一時コピーを開いて整合検査を実行する。Error も検査できなかった項目も無いときだけ公開へ進む
4. `hard_link` で `--db` へ公開する。既存の宛先があれば `EEXIST` で拒否する。公開後に、公開先が検査したファイルそのものかを確かめ、一時名を消して親ディレクトリを fsync する

- 検査に通らなければ、何も公開せず一時コピーを消す（終了コード 4 または 5）
- `--db` は**まだ存在しない**パスに限る。既存のファイル・ディレクトリ・シンボリックリンクは書かずに拒否する
- **既存の DB を上書きするフラグは設けていない。** 置き換える場合は、運用者が旧ファイルを明示的に退避してから実行する
- 公開直後に差し替えが検出され、かつ取り消しの削除にも失敗した場合は、終了コード 1 で終了し、検査していない内容が残っている旨の WARNING を標準エラーに出す。手動で削除する
- 公開しなかった経路で一時コピーを消せなかった場合は、終了コードは失敗の種類のまま残ったパスを通知する。`.fandhe-restore-<pid>-<seq>.tmp` は全テナントのデータのコピーであるため、見つけたら手動で削除する
- 失敗時の標準エラーには表の識別（DDL 上のテーブル名。テナント名ではない）が出うる。ログの送り先は運用者に限る

### 4.2 終了コード（`restore`）

| 終了コード | 意味 |
| ---------- | ---- |
| 0 | 成功。標準出力に `restore written: rows_scanned=<N> warnings=<M>` を出す |
| 1 | 実行時の失敗（復元元が使用中・コピー中に変化・コピーを開けない・I/O の失敗・未検査の内容が公開先に残った） |
| 2 | 引数または拒否（`--db` が既存、`--from` が空または通常ファイルでない、この環境が対応しない〔hard link 非対応など〕）。DB は開いていない |
| 3 | 最終名へ公開済みで中身は完全だが、一時名の削除や fsync を確かめられなかった。検査は通っている |
| 4 | 検査で矛盾あり（公開していない）。標準エラーに `verify` と同じ形式の報告を出す |
| 5 | 検査できなかった項目だけがある（公開していない） |

### 4.3 復元後の確認

1. `wire-server verify --db <復元先>` を実行し、終了コード 0 と `status=consistent` を確かめる
2. 復元先の DB でサーバーを起動する（`--users` ファイルは別途保管していたものを指定する）。変更ログを有効にしていた DB の取得物では、`--change-log` を付けて起動する（5.1 節）
3. 業務上の確認（件数や代表的なクエリの結果など）は、運用者が対象ごとに定める
4. 旧 DB から復元先への切り替えは運用者が行う。旧ファイルは削除せず退避する

### 4.4 増分バックアップ（`backup-incremental`・`restore --incremental`）

変更ログ（5 節）を有効にした DB に限る（Issue #2168。RECOVER-13・RECOVER-14 ポインタ。形式と判断は [change-log-pitr.md](change-log-pitr.md) の D7）。フルバックアップ（`backup`）を連鎖の起点にし、その後の変更だけを増分として取る。

```bash
# 1. フルバックアップ（連鎖の起点）
wire-server backup --db <DB> --out base.redb
# 2. 書き込みの後、停止中の DB から増分を取る（直前のベースの次から最新まで）
wire-server backup-incremental --db <DB> --base base.redb --out inc1.seg
# 3. さらに書き込みの後、前回の増分をベースにして次の増分を取る
wire-server backup-incremental --db <DB> --base inc1.seg --out inc2.seg
# 4. ベース + 増分（古い順）を新しい DB へ復元する
wire-server restore --from base.redb --db <新規パス> --incremental inc1.seg --incremental inc2.seg
```

- `backup-incremental` は DB を読み取り専用で開き、書き込まない。稼働中のサーバーが開いている DB、書き込みを要する状態（異常終了後の修復が要る DB）は終了コード 1 で拒否する。`--base` はフルバックアップの DB ファイルか前回の増分で、読むだけである
- 出力は 1 ファイル（変更ログのアーカイブと同じセグメント形式）。既存の `--out` は上書きせず（終了コード 2）、他者が書き込めるディレクトリ（グループ・その他に書き込み権限）の中には書かない（終了コード 2。`chmod 755` が要る）
- 連鎖が切れている場合は、何も出力せず終了コード 1 で拒否する。拒否するのは、別の DB のベース、別の timeline、ベースが DB より先に進んでいる、ベースの後に新しい commit が無い、DB の変更ログがベースの次から欠けている（刈り込み済み）、変更ログを有効にしていない DB またはベース、のとき
- `restore --incremental` は、ベースをコピーした一時ファイルへ増分を古い順に適用してから、通常の復元と同じ整合検査・公開を行う。連鎖の切断（欠落・順序違反・重複）、別の DB・timeline の増分、破損・不整合（チェックサム不一致・途中切れ・形式不正）は、何も公開せず終了コード 1 で終わる（一時ファイルも残さない）。ベースと増分のファイルは変更しない
- **信頼境界**: チェックサムは鍵なしの SHA-256 で、破損・不整合の検出であり認証ではない。細工してチェックサムを計算し直した増分は検証を通る（適用時にレコードの形式・表の有無・型は検査するが、内容の正しさは保証しない。適用後の整合検査は通常の復元と同じく行う）。増分とベースは、ベースの DB ファイルと同じ信頼境界の経路で受け渡す
- **注意（分岐の未検出）**: 復元した DB は元と同じ DB 識別子・timeline を持つ。復元した DB と元の DB が別々に書き込まれた後、別系統の増分を同じベースへ適用しても、LSN が連続していれば検出できない。系統ごとにベースと増分を分けて保管する（timeline の分岐は #2446 待ち）
- 適用は 1 レコードを丸ごとメモリに載せる。レコードの上限は 256 MiB で、復号後の表現を含め数倍のメモリを使いうる
- 復元した DB は変更ログを含むため、起動には `--change-log` が要る（5.1 節）。継続して増分を取れる
- 稼働中のサーバーからの増分の取得、刈り込み済みの区間をアーカイブから補う取得は未対応（6 節）。指定 LSN／時刻までの復元は 4.5 節

### 4.5 指定 LSN／時刻までの復元（PITR。`restore --until-lsn|--until-time`）

変更ログ（5 節）を有効にした DB のフルバックアップと、変更ログのアーカイブ（5.2 節）から、指定した点のコミット境界までの状態を新しい DB へ復元する（Issue #2169。RECOVER-14 ポインタ。設計は [change-log-pitr.md](change-log-pitr.md) の D12）。

```bash
# LSN で指定する（その LSN のコミットを適用した直後の状態）
wire-server restore --from base.redb --db <新規パス> \
  --change-log-archive-dir <アーカイブのディレクトリ> --until-lsn 1234
# 時刻で指定する（RFC 3339・ゾーン必須。この時刻を超える最初のコミットの直前の状態）
wire-server restore --from base.redb --db <新規パス> \
  --change-log-archive-dir <アーカイブのディレクトリ> --until-time 2030-01-02T03:04:05Z
# 増分バックアップと併用する（増分の末尾より後ろをアーカイブから補う）
wire-server restore --from base.redb --db <新規パス> --incremental inc1.seg \
  --change-log-archive-dir <アーカイブのディレクトリ> --until-lsn 1234
```

- **停止はコミット境界だけ**: 1 つのコミット（明示トランザクションを含む）は、丸ごと適用されるか、丸ごと適用されない。時刻指定は、コミット時刻が指定を超える最初のコミットの直前で止まる（壁時計が巻き戻っていても、コミット順の接頭辞になる）
- **指定点の LSN を調べる**: アーカイブの範囲は `change-log-verify --archive-dir <dir>` の出力から分かる。LSN 指定は、ベース DB の終点より後、入力したログ全体（増分とアーカイブ）の最大 LSN 以下に限る(増分の途中でも、アーカイブなしの増分だけでも指定できる。例: ベースが 10、増分が 11〜20 なら 15 を指定できる)
- **範囲外は拒否する**: 指定点がベース DB の終点以前、または入力したログの最大 LSN より後なら、何も公開せず終了コード 1 で拒否する（末尾まで黙って適用しない）。時刻指定でその時刻を超えるコミットがログに無い場合も同じ。最新まで戻したいときは、最後の LSN を `--until-lsn` に指定する
- **アーカイブの検証**: ベースと同じ DB・timeline であること、ベースの次から欠けなく続くこと、LSN の飛び・重複・チェックサム不一致・途中切れが無いことを、DB に触れる前に確かめる。**停止点より後ろのセグメントの欠落・破損も拒否する**。他者が書き込めるディレクトリ（グループ・その他に書き込み権限）のアーカイブは拒否する
- **引数の不正は終了コード 2**（DB を開く前）: `--until-lsn` と `--until-time` の併用、`--change-log-archive-dir` だけの指定、`--until-*` だけでログの入力（アーカイブも `--incremental`）が無い、0 や数字以外の LSN、ゾーンの無い・IANA 名・空白区切りの時刻、存在しないディレクトリ、同じフラグの重複。範囲外・欠落・改ざん・別の DB／timeline・連鎖の切断は終了コード 1
- 公開の手順（一時名へコピー → 適用 → 整合検査 → `hard_link`）と、失敗時に何も公開しない性質は 4.1 節のとおり。ベース・増分・アーカイブのファイルは変更しない
- **注意（分岐の未検出）**: 復元した DB は元と同じ DB 識別子・timeline のまま、LSN が巻き戻った状態になる。元の DB のアーカイブ先へ続きを書かず、復元した DB は別のアーカイブ先で運用する。timeline の分岐は #2446 待ち
- 信頼境界は 4.4 節と同じ（チェックサムは破損の検出であり認証ではない。アーカイブはベースと同じ信頼境界で受け渡す）

### 4.6 論理ダンプ（`dump`・`dump-restore`）

物理バックアップ（上記）と別に、SQL スクリプト形式の論理ダンプを取れる（Issue #2162・RECOVER-16 ポインタ。形式・上限・判断は [logical-dump.md](logical-dump.md) §12）。

```sh
# 1. 停止中の DB から 1 テナント分（共有の定義を含む）を書き出す。--shared-only なら共有の定義だけ
wire-server dump --db /var/lib/fandhe/db.redb --out /backup/tenant-a.sql --tenant tenant-a
#    --schema-only／--data-only で片方だけ、--format insert で INSERT 形式（既定は COPY）

# 2. 新規パスへ復元する（既存のパスは拒否。途中で失敗したら何も公開しない）
wire-server dump-restore --from /backup/tenant-a.sql --db /var/lib/fandhe/restored.redb \
  --expect-tenant tenant-a   # 任意。ヘッダのテナントと一致しなければ拒否する
```

- `--tenant` か `--shared-only` のどちらかが必須。全テナントを 1 回で書き出す指定は無い（テナントごとに取る）
- 出力は 0600 の一時名に書いて成功したときだけ公開する。ロールの SCRAM 検証子と全行の値を含むので、保管先の権限を管理する
- **復元先の親ディレクトリは、グループ・その他が書き込めないこと**（0755・0700 など。sticky bit つきの共有ディレクトリ〔`/tmp` 直下など〕も拒否し、何も作らず終了コード 2 になる）。所有者が自分と異なる親も拒否する
- `dump-restore` は復元先の親の中の 0700 の作業ディレクトリで流し込み、整合検査を行い、通ったときだけ公開する（作業ディレクトリは成功・失敗とも消える。消せなかったときは標準エラーにパスを出す）。終了コード: 0=成功、1=実行時の失敗（文の適用の失敗を含む。通し番号と SQLSTATE を標準エラーへ出す）、2=引数／パスの拒否（復元先が既存を含む）、3=公開済みだが後始末を確かめられなかった、4=ダンプファイルの拒否（改ざん・破損・許可外の文・データのみのダンプ）、5=整合検査の失敗。`dump` は 0〜3
- `--data-only` のダンプは新規 DB へ復元できない（表が無いため）。復元に使うのは全部（既定）または `--schema-only` のダンプ
- ダンプファイルは書き込み SQL を運ぶ。信頼できる出典のものだけを復元する。ヘッダのテナントは信用されるため、取り違えを防ぐには `--expect-tenant` を使う。枠の順序（作成 → データ → 後段）とヘッダとの整合は復元時に検査される
- **制約**: `--users` ファイルから起動したサーバーが作った DB は、そのテナントの利用者のブートストラップ権限が記録されているため、現状は `dump` が書き出せないオブジェクトとして拒否する（終了コード 1）。権限の書き出しが実装されるまでの制約
- 稼働中のサーバーからの取得は未対応（`dump` は停止中の DB を開く）

## 5. 変更ログ

変更ログ（Issue #3067・#3069・#2167。RECOVER-14 ポインタ）は、増分バックアップと PITR の土台として opt-in で提供する。ログを使った復元は、増分バックアップ（4.4 節）と指定点までの復元（PITR。4.5 節）ができる。

### 5.1 有効化

- `--change-log` は値を取らないスイッチで、既定は無効。有効にすると、各 commit の変更（評価済みの値の after-image）が、データと同じ redb トランザクションで DB 内の `change_log` 表へ追記される
- 有効化より前の変更はログに無い。有効にしたことのない既存の DB に後からフラグを付けることはできるが、それ以前の変更はログに無いため、有効化前のベースからの PITR はできない
- **一度有効にした DB は、フラグなしでは起動できない。** 無効のまま書くとログに欠落（LSN の欠落）が生じるため、起動を固定文言で拒否する
- `backup` で取った複製も変更ログを含むため有効扱いになり、起動には `--change-log` が要る
- 有効化を戻す（無効化）手段は用意していない
- `--change-log` の重複指定・値付きは起動エラーになる
- アーカイブしない場合、`change_log` 表は DB ファイルの中で増え続ける。書き込み量の多い DB では、ファイルが無効時の約 3 倍、一括 ingest のスループットが約 0.6 倍になった（実測は [change-log-pitr.md](change-log-pitr.md) の D11）
- 有効時は 1 回の commit に載せる変更に上限があり、超えた書き込みは `54000` で拒否される（書き込みは何も反映されない）。原因は stderr の固定文言 `engine: change log: commit refused: ...` で区別する。上限の目安は README の `--change-log` の節を参照する

### 5.2 アーカイブと保持

| フラグ | 意味と前提 |
| ------ | ---------- |
| `--change-log-archive-dir <dir>` | 既存のディレクトリを指定する。常駐スレッドが `change_log` 表のレコードを、チェックサム付きのセグメントファイル（`fandhe-cl-*.seg`、0600）へ周期的に書き出す。前提は `--change-log` |
| `--change-log-archive-interval-secs <1-86400>` | 書き出しの周期（既定 10 秒）。前提は `--change-log-archive-dir` |
| `--change-log-retain-records <n>` | アーカイブ済みのレコードのうち新しい `n` 件を DB に残し、より古いものを DB から刈り込む（`0` はアーカイブ済みのすべて）。指定しなければ刈り込まない（既定）。前提は `--change-log-archive-dir`。アーカイブされていないレコードは刈り込まれない |

- 既存のセグメントファイルは上書きも削除もしない。同名で内容が違うファイルがあれば書き出しを止め、stderr に固定文言を出す。水位は進まず、DB のログは消えない
- アーカイブ先は DB と別の媒体に置くことを推奨する
- グループ・その他が書き込めるディレクトリは、スティッキービットの有無に関係なく起動時に拒否される。umask 002 で作ったディレクトリは `chmod 755` で所有者だけが書ける状態にする
- 刈り込みは世代を進めず、再起動後の連続性検査にも影響しない
- セグメントファイル自体の保持（古いファイルの削除）は、まだ自動化していない。削除するのは、運用者が復元に不要と確認したものだけにする。削除の前に 5.3 節の検証で連鎖の欠落がないことを確かめる

### 5.3 検証（`change-log-verify`）

```bash
wire-server change-log-verify --archive-dir <アーカイブ先> [--db <DB のパス>]
```

- チェックサムの不一致、LSN の飛び、別 DB・別 timeline のセグメント、途中切れを検出し、終了コード 1 で報告する
- `--db` を付けると、停止中の DB のメタ情報と突き合わせ、先頭・末尾のセグメントの紛失も検出する。DB は読み取り専用で開き、書き込まない。書き込みを要する状態の DB は拒否するため、その場合は DB のコピーを検査する。稼働中の DB は `in use` で終了コード 1
- 成功時は `change log archive ok: segments=<N> records=<M> lsn=<先頭>..<末尾>` を出す（レコードが無い場合は `lsn=none`）

| 終了コード | 意味 |
| ---------- | ---- |
| 0 | 検証に通った |
| 1 | 検証の失敗、または DB を開けない（使用中・書き込みを要する状態） |
| 2 | 引数の不備（`--archive-dir` は必須） |

## 6. 未対応の範囲

- **レプリケーション**: 対象外
- **PITR（ログの適用による任意時点への復元）**: 実装済み（4.5 節）。timeline の分岐と復元後の世代番号の進行は未実装（#2446）
- **稼働中のサーバーからの増分の取得**: 未対応。`backup-incremental` は停止中の DB を読み取り専用で開く
- **刈り込み済みの区間を含む増分**: 未対応。DB の変更ログがベースの次から欠けていれば拒否する（アーカイブから補う経路は持たない）
- **変更ログの無効化**: 手段がない。一度有効にした DB は、フラグなしでは起動できない
- **アーカイブファイルの保持と削除**: 自動では行わない。削除は運用者が手動で、復元に不要と確認したものだけに対して行う
- **復元後の世代番号の進行**: 未実装（#2446・RECOVER-17）。現行の `restore` は世代番号を進めない
- **論理ダンプ**: 手順は 4.6 節（`dump`・`dump-restore`。Issue #2162）。全テナントのダンプ、権限の書き出し、既存 DB へのデータのみの流し込みは未対応（設計は [logical-dump.md](logical-dump.md) §12）
- **フルバックアップ自体のチェックサム**: 現行の形式に記録がなく、`verify` の対象外（3.4 節）。増分バックアップはチェックサム付きで、連鎖を検証する（4.4 節）
- **`--users` ファイルとセッション状態**: バックアップに含まれない（1 節）

## 7. crash-test による確認範囲

`scripts/crash_test_backup_restore.sh`（Issue #2157・RECOVER-13 ポインタ）は、取得・復元の crash 耐性を確かめる回帰テストである。`make crash-test-backup-restore` で実行し、`crash-test`（CI の crash-test ジョブ）の前提になっている。wire-server のリリースバイナリを使い、運用者が使う CLI の経路そのものを対象にする。

- 書き込み中のサーバーを SIGKILL して、DB が異常終了した状態を作る
- `backup --db`・`restore` の実行中に CLI を SIGKILL する反復と、`--backup-socket` 経由の取得中にサーバーを SIGKILL する段を行い、次の点を確かめる
  - 最終名に不完全なファイルが現れないこと
  - 残骸が一時名（`.fandhe-snapshot-*.tmp`・`.fandhe-restore-*.tmp`）だけであること
  - 完成したバックアップと復元先が `verify` で終了コード 0 になり、サーバーで同じ件数を読めること
- 公開前の段階で実際に kill できた回数を段ごとに数え、0 回なら失敗にする（空虚な成功を避けるため）

限界: SIGKILL はプロセスの強制終了であり、電源断や OS のクラッシュは再現しない。fsync による持続性を検証するものではない。kill のタイミングは乱数で、網羅的ではない。
