## 1. 背景・目的

述語形 `UPDATE ... WHERE`／`DELETE ... WHERE`（SQL-19）は、1 文の全対象行を 1 つの write
トランザクションで適用し、台帳へ 1 文 1 エントリを記録する（`predicate-dml-exec.md` §3・
`multi-row-dml-operation-id.md` §6）。影響行数上限は Issue #997 で既定無効になった
（`predicate-dml-exec.md` §6）が、大量行の更新・削除には次の制約が残る。

- **走査上限**: 1 文あたりの総走査行数上限 `tenant::MAX_SCANNED_ROWS`（1,000,000）は常に
  適用される。対象テナントの所有行が 100 万行を超えるテーブルでは、述語にほとんど一致しなく
  ても 1 文で処理できず `54000` になる。
- **writer の占有**: redb の writer はプロセス内で 1 つで、全テナントが共有する（`explicit-transaction.md` §1・
  `storage/writer_gate.rs`）。
  1 文の DML が writer を握る時間に上限はなく、全走査と適用が終わるまで他テナントの書き込みは
  writer gate で待つ（待機上限 30 秒を超えると `55P03`。`explicit-transaction.md` §2・§5）。
- **メモリ**: 現行の実行器は候補 id をすべて `Vec<u64>` に集めてから適用する。

単一トランザクションの肥大化と writer の長時間占有を避けるため、原子性を持たない分割実行
（チャンク単位コミット）の経路を**別経路として**追加する方式を検討する。既存の 1 文 1
トランザクション経路（`delete_rows_where_unchecked`／`update_rows_where_unchecked`）とその
原子性・台帳契約は変えない。

他 DB の同種機能として、Cloud Spanner の Partitioned DML（パーティションごとに独立に
コミットし、文全体は原子的でない）、TiDB の非トランザクション DML（`BATCH ON <列> LIMIT n`
で分割する）、CockroachDB で推奨される分割削除（クライアント側のループ）がある。本 ADR は
それぞれの意味論を参考にするが、互換構文は目標にしない。

## 3. 論点 1: 対象文と構文

### 3.1 対象文

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| T1 | 述語形 `UPDATE`／`DELETE`（SQL-19）のみ | 走査上限・writer 占有の問題があるのはこの 2 文。対象集合が述語で決まり、チャンク分割の意味が明確 | 大量 INSERT は対象外 |
| T2 | T1 ＋大量 `INSERT`（複数行 `VALUES`・ファイル形） | 取り込みも分割できる | INSERT は既に `batch_limits`（`max_files_per_batch`・`max_batch_chunks`）とファイル単位の取り込み経路で分割でき、クライアントが文を分ければ足りる。INSERT の対象集合は入力そのもので、走査上限の問題もない |
| T3 | T1 ＋ `TRUNCATE`・UPSERT | 網羅的 | `TRUNCATE` は全行削除専用の別経路。UPSERT は衝突判定と台帳の関係が複雑で、分割すると意味論が変わる |

**採用**: T1。単一行形（`WHERE id = n`）・`RETURNING` 付き・UPSERT・`TRUNCATE` との
組合せは受理しない（返却行がチャンクを跨ぐと原子性のない結果セットになるため、`RETURNING`
も対象外とする）。

### 3.2 構文

| 候補 | 内容（例示） | 利点 | 欠点 |
| ---- | ------------ | ---- | ---- |
| S1 文の修飾 | `UPDATE t SET ... WHERE ... USING OPERATION_ID '<id>' PARTITIONED [CHUNK <n>]` | 既存の述語形 DML の許可リスト・束縛・内容照合ハッシュをそのまま再利用できる。同期実行なので応答（完了／部分完了）が文の結果として返る | 長時間の同期実行になり、クライアント側のタイムアウトに当たりうる（再送で再開できるので致命的ではない。5.3 節） |
| S2 専用文 | `PARTITIONED UPDATE ...`／`BATCH DELETE ...` のような別の先頭キーワード | 先頭トークンで経路が分かれ、既存の文と取り違えない | 先頭トークン分岐と許可リストを二重に持つことになり、述語・`SET` の検証を共有する設計（`delete-predicate-form.md`）から外れやすい |
| S3 非同期ジョブ形 | 起動文がジョブ識別子を即座に返し、サーバー側のワーカーが実行する。照会・取り消しは別の文 | 接続を保持しなくてよい | サーバー内にバックグラウンド実行器・スケジューラが必要。セッションを持たない実行主体が RLS の文脈（`PolicyContext`）を保持・永続化する必要があり、テナント境界の検査面が増える。再起動後の自動再開も実装しなければならない |

**採用**: S1（同期実行の文修飾）。S3 は S1 の実績を見てから必要性を判断する。

**確定（Issue #1129）**: キーワードは文脈キーワード（字句解析のキーワードは増やさない）で、
文の末尾の `USING OPERATION_ID '<id>'` の直後に `PARTITIONED [CHUNK <n>]` を置く。進捗照会は
`SHOW PARTITIONED DML '<id>' ON <table>`、取り消しは `CANCEL PARTITIONED DML '<id>' ON <table>`、
実行せずに確認するには `EXPLAIN UPDATE|DELETE ... PARTITIONED` を使う。`INSERT`（UPSERT を含む）・
`TRUNCATE`・単一行形・`RETURNING` との併用は `42601`。

### 3.3 トランザクション内での扱い

分割実行は「チャンクごとに commit する」ことが本質であり、明示トランザクション・暗黙
トランザクションの 1 回 commit（F8）と両立しない。

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| X1 | トランザクション内では拒否する | PostgreSQL がトランザクションブロック内で実行できない文（`VACUUM` 等）に返す `25001` と同じ扱い |
| X2 | トランザクション内では通常の原子的実行へ黙って縮退する | 利用者が指定した意味論と違う実行になる（fail-open 側の挙動）ため不可 |

**採用**: X1。コードは既存の `ActiveSqlTransaction`（`25001`。これまでは `Active` 中の再
`BEGIN` に使っている）を流用する（2026-10-01 オーナー判断。PostgreSQL と同じコードで、
`ErrorClass` の追加は要らない。再 `BEGIN` とは固定メッセージで区別する）。

## 4. 論点 2: 対象集合の確定と冪等性

### 4.1 対象集合の確定

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| P1 開始時スナップショット固定 | 開始時に述語を一度評価して対象 id 集合を確定・永続化し、チャンクはその集合を順に適用する | 対象集合が開始時点で決まる | 開始時の全走査そのものが `MAX_SCANNED_ROWS` と writer 占有の問題を抱える（分割の目的と矛盾する）。id 集合の永続化が O(対象行数) になる。開始後に他クライアントが述語列を変えた行も適用してしまう（チャンク時点で再判定しない場合） |
| P2 チャンクごと再評価（キー順カーソル） | 物理キー `(tenant, id)` の昇順に 1 回だけ進むカーソルを持つ。各チャンクは下端を排他にした範囲（未開始なら `(tenant, 0)` から、開始後は `(tenant, cursor)` を含まない次のキーから `(tenant, u64::MAX)` まで。`cursor + 1` のような加算はしない）を走査し、そのチャンクのトランザクション時点の行内容で述語を評価し、一致行を適用し、最後に走査したキーを新しいカーソルとして**同じトランザクションで**保存する。範囲を走査し尽くしたチャンク（最後に走査した `id` が `u64::MAX` の場合を含む）が最後のチャンクになる | 開始時の全走査が不要。メモリはチャンク幅に比例。カーソルが単調に進むので、1 ジョブ内で同じ行を 2 回訪れない | 対象集合はジョブ全体で一意に定まらない（カーソルより後ろに挿入された一致行は適用され、前に挿入された行は適用されない） |
| P3 P2 ＋収束まで再走査 | P2 を一巡した後、一致行がなくなるまで先頭から繰り返す | 終了時点で一致行が残らない | 他クライアントが一致行を作り続けると終わらない。`SET` 後も述語に一致し続ける文では同じ行へ再適用する |

**採用**: P2。各行は「チャンクのトランザクション時点で述語に一致していれば、その
トランザクションで 1 回だけ適用される」意味論になる。`UPDATE` は `id` を変えないため、更新後の
行をカーソルが再訪することはない（ハロウィン問題が起きない）。カーソルより前に後から入った
行は対象外になることを利用者向けの文書に明記する。

### 4.2 冪等性（同じ行へ 2 回適用されうるか）

- P2 では「チャンクの行変更」と「カーソル・処理済み件数の更新」を同じ write トランザクションで
  commit する。クラッシュ・中断の後もカーソルより前の行は適用済み、後ろの行は未適用であり、
  再開しても同じ行を 2 回適用しない。この性質は `SET` の右辺の形に依存しない。
- 現状 `SET` の右辺はリテラルのみ（F12）なので、仮に同じ行へ 2 回適用されても結果は変わらない。
  ただしこれは偶然の性質であり、採用案はカーソルの原子的保存で「ちょうど 1 回」を保証する。
  将来 `SET col = col + 1` のような非冪等な式を許す場合も、この保証がそのまま効く。
- ジョブ完了後の同一文の再送は台帳で `23505` になる（6 節）。

### 4.3 既存の上限との関係

| 上限 | 候補 | 採用 |
| ---- | ---- | ------------ |
| `MAX_SCANNED_ROWS`（1 文の総走査行数） | (a) ジョブ全体に適用 ／ (b) チャンクごとに適用（チャンクの走査予算 ≤ `MAX_SCANNED_ROWS`） | (b)。(a) では 100 万行を超えるテーブルを処理できず、分割の目的を果たせない。一致行が少ない述語でもチャンクの走査予算で writer の占有が区切られる |
| `--max-dml-affected-rows`（影響行数上限・既定無効） | (a) 分割実行には適用しない ／ (b) 明示指定時はジョブ全体の累計に適用し、累計が上限を超えるチャンクは適用せずに部分完了として止める ／ (c) チャンクごとに適用 ／ (d) 明示指定時は分割実行そのものを拒否する | 既定（未指定）ではどの候補でも差が出ない。運用者が明示指定した場合は (b)（2026-10-01 オーナー判断）。(a) は運用者が安全策として設けた上限を分割実行の修飾だけで迂回できる（制限を緩める側の変更）ため採らない。(b) は上限を超える行へ一度も適用しない一方、既存の「超過時は副作用ゼロで `54000`」（`predicate-dml-exec.md` §6）は P2 では守れない（総件数が事前に分からない）ため、`54000` ではなく部分完了のコード（5.1 節）で止める。最初のチャンクで超える場合は 1 件も commit していないので、5.1 節の R1 どおり `54000`（副作用ゼロ）になる。より保守的な (d) は採らない。(c) は 1 チャンク内の件数しか見ず、上限の意味を失う |
| チャンク幅 | (a) 適用行数 ／ (b) バイト数 ／ (c) 時間 | (a) 適用行数を主とし、(b)・(c) の代わりにチャンクあたりの走査予算と writer 保持時間の上限を併用する。既定値・指定可能範囲は 15 節の確定値（2026-10-01 オーナー確認） |

## 5. 論点 3: 部分完了の応答・エラーコード・進捗照会・再開・取り消し

### 5.1 部分完了の応答と `wire_code`

中断の原因は、チャンク内の行エラー（式評価エラー・制約違反）、チャンク開始時の writer 待機
上限（`55P03`）、取り消し、接続断、プロセス停止のいずれかである。

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| R1 部分完了専用の新コード | 行を変更したチャンクを 1 つ以上 commit 済みで中断したら、部分完了を表す新しい `ErrorClass`（ラベル例 `PARTIAL_COMPLETION`、SQLSTATE は実装定義の値）で返す。原因のコードと commit 済み件数・`operation_id` は固定書式のメッセージに入れる。行を変更したチャンクがまだなければ（変更 0 件のチャンクしか通っていなければ）原因のコードをそのまま返す（従来の原子的失敗と区別がない） | 「一部 commit 済み・同じ文の再送で再開できる」ことをコードだけで判別できる。既存コードの意味（`54000`＝副作用ゼロ等）を変えない | `ErrorClass` の追加（件数定数・HTTP 射影表の更新）が必要。SQLSTATE 値の選定が要る |
| R2 原因コードをそのまま返す | 中断原因のコード（`22012`・`23505`・`55P03` 等）を返し、部分完了であることはメッセージだけで示す | クラス追加が不要 | クライアントはコードだけでは原子的失敗と区別できず、「何も起きていない」と誤認しうる（fail-open 側） |
| R3 `57014`／`40001` を流用 | キャンセル・ロールバック系の既存 SQLSTATE を使う | PostgreSQL クライアントが知っているコード | `40001` は「ロールバックされた」意味で事実と逆。`57014` は本リポに未実装で、PostgreSQL では副作用なしの中断を意味する |
| R4 成功応答＋警告 | `UPDATE n` を返し、`NoticeResponse` で部分完了を知らせる | 応答が単純 | 警告を読まないクライアントは成功と誤認する（fail-open）。不可 |

**採用**: R1。SQLSTATE の具体値は、PostgreSQL の既存クラスと衝突しない実装定義の値とし、
15 節の確定値（2026-10-01 オーナー確認）の `VD001` とする。全チャンク完了時の応答は従来どおり `UPDATE n`／`DELETE n`
（`n` はジョブ全体の累計。再開をまたいだ場合も累計）とする。

### 5.2 HTTP 射影（ERR-4）

| 候補 | HTTP | 評価 |
| ---- | ---- | ---- |
| H1 | `409 Conflict`＋`code` ラベル＋本文に `committed`・`operation_id` | 「ジョブが中間状態にあり、同じ要求の再送で解消する」状態の衝突として表せる。`23505`（409）と同じ帯 |
| H2 | `503 Service Unavailable` | `55P03`（503）と同じ再試行可能の帯だが、行エラーで止まった場合（再送しても同じ行で再び止まる）には合わない |
| H3 | `200 OK`＋`"complete": false` | R4 と同じく fail-open。不可 |

**採用**: H1。完了時の本文は既存 D4（`nosql-update-delete-mapping.md`）と同型
（`{"updated":<n>,...}`／`{"deleted":<n>,...}`）とする。

### 5.3 進捗照会・再開・取り消し

| 項目 | 候補 | 採用 |
| ---- | ---- | ------------ |
| ジョブの識別子 | (a) クライアントが指定した `(table, operation_id)` ／ (b) サーバーが採番するジョブ id | (a)。`operation_id` は既に必須で一意。採番 id を推測・列挙される面を作らない。テナントは認証主体から導出し、キーに含める |
| 進捗照会 | (a) 読み取り専用の専用文（例: `SHOW PARTITIONED DML '<operation_id>' ON <table>`）／ (b) システムビューへの `SELECT` ／ (c) 照会手段なし | (a)。writer を使わずに状態（実行中／中断／取り消し済み／完了）・処理済み件数を返す。ジョブ表の行がまだない間（行を変更したチャンクをまだ commit していない間）は、自テナントの実行中ジョブ登録簿から「実行中・0 件」を返す。登録簿にもジョブ表にもない場合は「ジョブがない」と同じ応答にする。(b) は仮想テーブルの基盤が要る |
| 再開 | (a) 同じ文を同じ `operation_id` で再送すると、内容照合ハッシュが一致すればカーソルから再開 ／ (b) 専用の再開文 | (a)。「再送して commit 済みか確かめる」既存の回復手順（`multi-row-dml-operation-id.md` §3 の候補 C の説明）と同じ操作で再開できる。ハッシュ不一致は `22023`、完了済みは `23505`（6 節） |
| 取り消し | (a) 専用文（例: `CANCEL PARTITIONED DML '<operation_id>' ON <table>`）で、実行中なら次のチャンク境界で止め、状態を取り消し済みにする ／ (b) CancelRequest（pg wire）で止める | (a)。CancelRequest は未実装（F9）。(b) は別 Issue で検討する。行を変更したチャンクを commit する前に届いた取り消しは、実行中ジョブ登録簿へ伝えて実行中のチャンクを commit せずに破棄し、記録を残さない（変更 0 件の「取り消し済み」記録は作らない。`operation_id` は失敗した通常の DML と同じく再利用できる）。取り消しで止まった文には、commit 済み件数をメッセージに含めて `VD002`（15.1 節）を返す |
| 取り消し後のロールバック | (a) 行わない（commit 済みチャンクは残る）／ (b) 変更前の行内容を保存して戻す | (a)。(b) は変更前イメージの保存が O(対象行) になり、分割の目的に反する |
| 実行中ジョブへの再送 | (a) `55P03` で拒否 ／ (b) 実行中ジョブの終了を待つ | (a)。プロセス内の実行中ジョブ登録簿で `(tenant, table, operation_id)` の二重実行を防ぐ。クライアントがタイムアウト後に再送した場合も安全 |

取り消し済みジョブへの同一内容の再送は再開しない（取り消しを優先する）。この場合のコードは、
再送しても状態が変わらないことをコードだけで判別できるよう、部分完了とは別のコード（15 節の確定値（2026-10-01 オーナー確認）の `VD002`）
にする。

## 6. 論点 4: 台帳と再送検出

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| L1 ジョブ単位（完了時に台帳記録） | 進行状態は台帳と別のジョブ表（キー `(tenant, table, operation_id)`、値は内容照合ハッシュ・状態・カーソル・処理済み件数）に持つ。最後のチャンクと同じトランザクションで台帳エントリを記録し、ジョブ表の行を「完了」状態（内容照合ハッシュと累計件数だけを持つ固定長の記録）へ縮める | 「台帳エントリの存在 ⇔ 対象とした全行の変更が commit 済み」（F2）を分割実行でも保てる。完了後の再送は既存どおり `23505`／`22023`。完了応答を受け取れなかったクライアントも、進捗照会で完了と累計件数を確かめられる。台帳の値の形式は変えない | 通常の DML が実行中・取り消し済みジョブと同じ `operation_id` を使う場合を検出するため、台帳照合の際にジョブ表も 1 回引く必要がある。完了ジョブ 1 件につき台帳エントリと完了記録の 2 件が残る |
| L2 チャンク単位 | チャンクごとに `(operation_id, チャンク番号)` の台帳エントリを記録する | 各チャンクの commit が台帳で確定する | P2 ではチャンク境界がデータに依存し、再送時にチャンク番号を再現できない。エントリ数がチャンク数に比例して増え、掃除がない（F3）。`multi-row-dml-operation-id.md` が候補 B を退けた理由（部分状態・どこまで commit 済みか判定できない）と同じ問題を持つ |
| L3 開始時に台帳記録 | 開始トランザクションで台帳エントリを記録する | 二重起動を台帳だけで防げる | F2 の同値性が崩れる（エントリがあっても全行は未適用）。既存の再送判定・回復手順の意味が変わる |
| L4 台帳値に「進行中」版を追加 | 台帳値の版バイトに進行中を表す版を足し、完了時に通常の版へ書き換える | ジョブ表を別に持たない | keep-first（上書きしない）の契約を変える。未知の版を `Corrupted` とみなす既存の読み手（F3）と互換がない |

**採用**: L1。あわせて次を採る。

- **ハッシュのドメイン**: 分割実行は原子的実行と意味論が違うため、内容照合ハッシュの操作種別
  タグを分ける（例: `OpTag::UpdateWherePartitioned`／`DeleteWherePartitioned`。既存タグの値は
  変えない）。同じ `operation_id` を原子的実行と分割実行で使い回すと `22023` になる。
  チャンク幅はハッシュに**含めない**（結果に影響しないため、幅を変えて再開できる）。
- **通常 DML との衝突**: 実行中・中断・取り消し済みジョブの `operation_id` を通常の DML が
  使った場合は、ドメインが違うので `22023` で拒否する。逆向きに、ジョブの実行中（とくにジョブ表の
  行がまだない、行を変更するチャンクの前）に通常の DML が同じ `operation_id` で先に commit する場合に
  備え、**各チャンクのトランザクションは走査の前に台帳の `(tenant, table, operation_id)` を引く**
  （F1 の「台帳照合を候補列挙より先」と同じ順序）。エントリがあれば `22023` で止める（完了した
  分割実行ジョブは完了記録で先に判定するので、ここで見つかるのは別ドメインのエントリだけ）。
  行を変更したチャンクをまだ commit していなければ、原因のコードのまま返り、記録も残らない。
- **保持期間**: 完了時はジョブ表の行を「完了」の記録（内容照合ハッシュ・累計件数）へ縮めて残す。
  進捗照会（5.3 節）はこの記録から完了と累計件数を返す（累計件数を台帳の値へ入れる案は、台帳の
  値の形式と既存の読み手〔F3〕を変えるため採らない）。取り消し済み・中断のまま放置された
  ジョブは、`operation_id` の再利用を防ぐため状態を残す。掃除は台帳と同じく
  `DROP TABLE` 時とし、期限掃除は設けない（15 節の確定値（2026-10-01 オーナー確認））。
- **明示トランザクション内の台帳**: 3.3 節の X1 により分割実行はトランザクション内に入らない
  ため、明示トランザクションの台帳の扱い（`explicit-transaction.md` §1）とは交わらない。

## 7. 論点 5: テーブル世代・キャッシュ失効・索引更新と途中状態の可視性

### 7.1 索引更新

UNIQUE 索引・FK 検査（F6）は、各チャンクで行の書き込みと同じトランザクション内で行う（候補を
置かない。チャンクの commit ごとに行と索引が一致していなければならない）。FK はチャンクごとに
即時検査する。スカラー二次索引・HNSW・疎索引は派生キャッシュで、世代で失効する。

### 7.2 世代の進め方

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| G1 チャンクごと | 影響 1 行以上のチャンクで `bump_table_generation_in_txn` を呼ぶ | 各キャッシュは世代照合だけで失効する（F5）ので、commit 済みの行と読み取り結果が常に一致する | テーブル世代は全テナント共通なので、チャンクごとに全テナントのキャッシュが失効し、`USING PLAN` の世代照合も失敗しうる |
| G2 ジョブ完了時に 1 回 | 途中のチャンクでは世代を進めない | キャッシュの失効が 1 回で済む | 途中のチャンクで commit 済みの行（削除済みの行など）を、古い世代のキャッシュが返し続ける。読み取りの正しさが崩れるため不可 |
| G3 G1 ＋間引き | G1 を保ったまま、チャンク幅の下限やチャンク間の間隔で世代を進める頻度を抑える | 正しさを保ったまま負荷を調整できる | 分割の細かさ（writer を手放す頻度）との兼ね合いになる |

**採用**: G1（必要なら G3 の間引きをチャンク幅・間隔の既定値で調整する）。G2 は
キャッシュの正しさを壊すので採らない。

### 7.3 途中状態の可視性

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| V1 見えることを許容し文書化する | チャンク commit ごとに他クライアントから途中状態が見える。行単位（行は旧値か新値のどちらか）とチャンク単位の原子性は保つ | Spanner の Partitioned DML と同じ扱い。追加の仕組みが要らない |
| V2 途中状態を隠す | ジョブ完了まで変更を見せない | 影の版管理（MVCC 相当）が必要で、本リポのストレージ（単一 writer・スナップショット読み取り）にはない。不可 |

**採用**: V1。`EXPLAIN` の出力と利用者向けの文書で、分割実行であり途中状態が見える
ことを示す（#1129）。

## 8. 論点 6: RLS とテナント間の資源上限

### 8.1 テナント境界

- 各チャンクは既存の述語形 DML と同じ範囲（テナント所有かつ可視。閉区間
  `(tenant, 0)..=(tenant, u64::MAX)`。`predicate-dml-exec.md` §4）だけを走査する。カーソルは
  この閉区間の中だけを進み、他テナントの領域のキー・値を読まない。
- 再開時の認可は、再開したセッションの認証主体から改めて導出する（ジョブ表に RLS の文脈を
  永続化しない）。ジョブ表のキーにテナントを含めるので、別テナントからは同じ
  `(table, operation_id)` のジョブに到達しない。
- 進捗照会・取り消しは自テナントのジョブだけを対象にする。「ジョブが存在しない」「別テナントの
  ジョブ」「`ON <table>` のテーブルが存在しない」「テーブルはあるが要求元から見えない」は、
  すべて同じ応答（同じコード・同じ文言）にする（RLS-9 の応答同一性と同じ考え方）。
- 応答に含める件数は自テナントで commit した件数だけとする。

### 8.2 資源上限

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| Q1 プロセス全体の上限だけ | 同時実行ジョブ数の上限をプロセス全体で持つ | 単純 | 1 テナントが枠を使い切ると他テナントが起動できない。拒否されたこと自体から他テナントの負荷が分かる |
| Q2 テナント単位＋プロセス全体 | テナントごとの同時実行ジョブ数上限を主にし、プロセス全体の上限は余裕のある値にする | テナント間の公平性を保てる | 設定項目が増える |
| Q3 上限なし | — | — | writer をチャンク単位で手放しても、多数のジョブが交互に writer を取れば通常の書き込みが待たされる |

**採用**: Q2。加えて次を採る。

- **writer の手放し方**: チャンクごとに writer gate を取り直す（取得には既存の待機上限が
  効き、超えたら `55P03` で部分完了または 0 件失敗になる）。1 チャンクの writer 保持時間には
  上限を設け、走査予算と合わせて占有時間を区切る。
- **通常の書き込みの優先**（PR #1309 で具体化。2026-10-01 オーナー確認）: writer gate は
  `Mutex`＋`Condvar` で到着順を保証しないため、「待機者がいれば譲る」だけでは、分割実行の
  チャンクが通常の書き込みを繰り返し追い越しうる。そこで writer gate に「待機中の通常の書き込みの
  数」を持たせ、分割実行のチャンクは、その数が 0 で、かつ gate が空いているときにだけ取得する。
  これにより、通常の書き込みが分割実行に待たされるのは、待ち始めた時点で実行中だったチャンクと、
  待機数の加算と分割実行側の判定が行き違った場合のもう 1 チャンクの、高々 2 チャンク（保持時間の
  上限 × 2 以内）になる。分割実行の側は通常の書き込みが続くと待たされるが、待機上限で
  `55P03`（部分完了または 0 件失敗）になり、再送で再開できる。
- **起動時の上限超過**: 1 チャンクも commit していない時点での拒否なので副作用ゼロである
  （コードは 15.4 節の確定値（2026-10-01 オーナー確認））。プロセス全体の上限による拒否も同じコード・同じ文言にし、他テナントの
  ジョブの数や識別子を応答に含めない。ただし、自テナントのジョブが上限未満なのに拒否された
  ことから、プロセス全体が混んでいることは分かる。これは writer 待機の `55P03` と同じ程度の
  残余リスクであり、許容する（15 節の確定値（2026-10-01 オーナー確認））。
- 既定値（チャンク幅・走査予算・保持時間・同時実行数）と設定方法は 15 節の確定値（2026-10-01 オーナー確認）とする。

## 9. 論点 7: クラッシュ時の挙動と crash-test の「部分コミット 0 件」基準との区別

### 9.1 既存の crash-test が確認していること

`make crash-test`・`crash-test-cross-table`・`crash-test-unique-index` は、それぞれ
`crates/engine/examples/crash_tool*.rs` の書き込み処理を `kill -9` で止め、再起動後に次を
確認する（`crash-test-interrupt` はスクリプト自体の中断処理のセルフテスト）。

| ターゲット | 書き込み | 再起動後の確認 |
| ---------- | -------- | -------------- |
| `crash-test`（PERSIST-1） | 1 行ずつ commit | 行 id が欠番なく連続し、内容が一致し、ack 済みの件数以上が残る |
| `crash-test-cross-table`（TABLE-10） | 10 行＋バッチ台帳を 1 トランザクション | 行と台帳が連続し、台帳の件数合計と行の総数が一致し、行数がバッチ幅の倍数（1 トランザクションの部分 commit が 0 件） |
| `crash-test-unique-index`（TABLE-16） | UNIQUE 列への 10 行を 1 文で INSERT | 行数がバッチ幅の倍数で、既存値の再 INSERT が必ず `23505`（索引の欠落がない） |

いずれも「1 トランザクション（1 文）の変更は全部残るか全く残らないか」を確認しており、
UPDATE／DELETE を kill するシナリオはない（F14）。

### 9.2 分割実行のクラッシュ時の挙動

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| C1 クライアントの再送で再開 | 再起動後は何も自動実行しない。永続化された「実行中」状態は、プロセス内の実行中ジョブ登録簿にないことから「中断」とみなす。同じ文の再送でカーソルから再開する | セッションのない実行主体を持たない。S1・L1 と整合する |
| C2 起動時に自動再開 | 再起動時にサーバーが中断ジョブを自動で再開する | RLS の文脈の永続化と、セッションのない実行主体が必要（S3 と同じ欠点）。利用者が知らないうちに書き込みが再開する |

**採用**: C1。チャンクの commit に失敗した場合は既存どおり `process::abort()` で止まる
（F7）。各チャンクは「行変更・索引・カーソル・処理済み件数・（最後のチャンクでは）台帳記録と
ジョブ表の完了記録への書き換え」を 1 トランザクションで commit するので、再起動後の状態はチャンク境界の
どこかにそろう。

### 9.3 検証基準の区別（#1131 の範囲）

- 既存の crash-test 系ターゲットと、その「部分コミット 0 件」基準（1 トランザクション・1 文の
  単位）は**変更しない**。分割実行を既存ターゲットの対象に加えない。
- 分割実行には別の基準を設ける。2〜3 は、P2 ではチャンク時点の行内容で述語を評価し直す（4.1 節）
  ため、ジョブ実行中に並行する書き込み（カーソルより前への挿入・述語列の変更）があると正しい実行でも
  成り立たない。crash シナリオでは並行書き込みを止めた fixture（ジョブ開始時の一致行集合が完了まで
  変わらない）で判定する。並行書き込みとの整合は、別のシナリオで「各チャンクがそのトランザクション
  時点の一致行にだけ適用したこと」を、テスト側で記録したチャンクごとの対象集合と照合して確認する。
  1. **チャンク原子性**: 1 チャンクの変更は全部残るか全く残らない（チャンク単位での「部分
     コミット 0 件」）。
  2. **前方一致**（並行書き込みなしの fixture）: 適用済みの行は、永続化されたカーソル以下の一致行と
     正確に一致する（カーソルより後ろの行は未適用）。処理済み件数とも一致する。
  3. **ちょうど 1 回**（並行書き込みなしの fixture）: 再開後に全一致行へ 1 回だけ適用される。
     `SET` がリテラルだけの現状では値から二重適用を観測できないため、`DELETE` のシナリオと処理済み
     件数の照合で確認する。
  4. **台帳**: 完了前は台帳エントリがなく、完了後はちょうど 1 エントリある。
- 新しい `crash_tool` と `scripts/crash_test_*.sh`・Makefile ターゲットを追加する形が候補だが、
  `make ci` に入れるかは実行時間を見て #1131 で決める。
- **#1131 の結論**: `crash_tool_partitioned_dml`・`scripts/crash_test_partitioned_dml.sh`・Makefile ターゲット
  `crash-test-partitioned-dml` を追加した。全体で 1 秒前後（既定 2 セット）と短いため `make ci` と ci.yml の
  独立ジョブに入れた。既存の crash-test 系は変更していない。

## 10. 論点 8: NoSQL 表層とのパリティ

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| N1 既存 op の修飾 | `update`／`delete` op に `"mode": "partitioned"`（例示）を足す。`filter` 指定時だけ受理し、`where`（単一行）との組合せは `42601` | SQL の S1（文の修飾）と対称。同じ実行器・同じ内容照合ハッシュのドメインを使える | op ごとの判定順序（`nosql-update-delete-mapping.md` D5）に分岐が増える |
| N2 専用 op | `partitioned_update`／`partitioned_delete` op を新設 | op の許可リストで経路が分かれる | `filter` の検証・写像を二重に持ちやすい |
| N3 NoSQL では提供しない | SQL 表層だけ | 実装量が少ない | NOSQL-12 のパリティから外れる |

**採用**: N1。進捗照会・取り消しは NoSQL にも用意する（op の追加。名前は #1130 で
確定）。次の点を SQL 表層とそろえる。

- 実行器・上限・部分完了の意味論・内容照合ハッシュのドメインは SQL 表層と同じ（同じ
  `operation_id` で SQL と NoSQL を跨いで再送すると、内容が同じなら再開・`23505`、違えば
  `22023`）。
- 述語は既存の述語形 DML の `filter` と同じ語彙にする（起草時点の F13 は `eq`／`prefix` のみだったが、その後 #1197 で述語形 DML の `filter` が広がったため、それに追従する。下記「確定（Issue #1130）」）。
- HTTP 射影は 5.2 節の H1。長時間の HTTP 要求はクライアント・中継のタイムアウトに当たりうるが、
  再送で再開できる（5.3 節）ことを利用者向けの文書に書く。
- NoSQL 表層にはトランザクションがない（`explicit-transaction.md`）ため、3.3 節の拒否は該当しない。

**確定（Issue #1130）**:

- `update`／`delete` の任意キー `"mode"`（`"partitioned"` のみ受理。それ以外の値は `42601`）と
  `"chunk"`（`mode` 指定時のみ有効。値は SQL の `CHUNK n` と同じ規則: `0`・小数・`usize` 超過は
  `22000`、負数は `42601`、サーバー幅超過は `22000`）。`where`（単一行形）との組合せは `42601`。
  `explain` は引き続き未知キーとして `42601`。
- 進捗照会・取り消しの op 名は `show_partitioned_dml`／`cancel_partitioned_dml`。要求は `table`・
  `operation_id` だけを持ち、応答は SQL 表層と同じ結果セット形（`status`・`rows` の 2 列）。
- 述語の語彙は、既存の述語形 DML の `filter` の語彙をそのまま再利用する（`bind_filter_where_predicates`
  を変更しない）。分割実行専用の追加制限は設けない。**オーナーが覆せる判断**として PR 本文に明記する。
- 共有の仕組み: SQL 経路と NoSQL 経路が、束縛以降の同じ private 関数（`run_partitioned_update`／
  `run_partitioned_delete`）を呼ぶ。内容照合ハッシュ・実行器・上限・失敗写像が構造的に同一になる。
- 部分完了（`VD001`）・取り消し（`VD002`）は HTTP 409。本文は通常のキー集合に `data` を追加し、
  `data` は `committed`（自テナントで commit 済みの件数）と `operation_id`（クライアントが指定した値）
  だけを持つ。

## 11. 採用案のまとめ

| 論点 | 採用 |
| ---- | ------------ |
| 対象文 | 述語形 `UPDATE`／`DELETE` のみ（`RETURNING`・単一行形・UPSERT・`TRUNCATE` は対象外） |
| 構文 | 同期実行の文修飾（S1）。明示・暗黙トランザクション内では拒否（`25001` の流用） |

| 世代・可視性 | 影響のあるチャンクごとに世代を進める（G1）。途中状態は見える（V1） |

| NoSQL | 既存 op の修飾（N1）。照会・取り消しの op を追加 |

| 取り消しの SQLSTATE（取り消しで止まった文と、取り消し済みジョブへの再送） | `VD002` | 部分完了と同じ実装定義クラス `VD` の続番。再送しても再開しないことをコードだけで判別できるよう、`VD001` と分ける（5.3 節） |
| 取り消しの `code` ラベル | `PARTITIONED_DML_CANCELLED` | 何が取り消されたかをラベルだけで判別できる |
| HTTP 射影（両コード） | `409` | 5.2 節の H1（採用済み）。`23505`（`409`）と同じ帯 |

クラス名 `VD` は本リポ（vector-db）固有のクラスとして、今後の実装定義コードの置き場にもする。
`ErrorClass` は 2 件増えて 44 件になる（件数定数と HTTP 射影表の更新は #1129）。

### 15.2 既定値と設定方法

| 項目 | 確定値（既定） | 指定可能範囲 | 根拠 |
| ---- | -------------- | ------------ | ---- |
| チャンク幅（1 チャンクの適用行数。サーバー設定値） | 1,000 行 | `1..=1,000,000` | 1 文の影響行数上限の旧既定値 1,000（Issue #997 で既定無効へ変更する前の値）と同じで、1 トランザクションで扱う行数として運用実績がある。範囲は `--max-dml-affected-rows` と同じ（`MAX_DML_ROW_LIMIT`＝`MAX_SCANNED_ROWS`） |
| チャンクごとの走査予算 | 100,000 行 | `1..=1,000,000` | 読み取り経路の可視行上限 `MAX_VISIBLE_ROWS`（100,000）と同じ。上限は 1 文の総走査行数上限 `MAX_SCANNED_ROWS`（1,000,000）を超えない |
| 1 チャンクの writer 保持時間の上限 | 1 秒 | `100..=5,000` ミリ秒 | 8.2 節の優先により、通常の書き込みが分割実行に待たされるのは高々 2 チャンク分になる。保持時間の上限は走査・適用の行境界での打ち切り判定であり、最後に判定を通過した 1 行の適用（UNIQUE・FK 検査を含む）と世代 bump・ジョブ記録の保存・commit は時計で中断できないため、待ちの見積もりは「この上限 × 2 ＋ その非中断段の所要」とする。他の書き込みの writer 待機上限 30 秒（`DEFAULT_WRITE_LOCK_WAIT`）・明示トランザクションの `max_duration` 20 秒より 1 桁以上短くする。範囲の上限 5 秒（× 2 で 10 秒）でも 30 秒に収まる |
| 同時実行数（テナント単位） | 1 | `1..=64`（かつ全体の値以下） | writer は 1 つなので、同じテナントのジョブを並べても速くならない。上限は接続数上限 `MAX_CONNECTIONS`（64） |
| 同時実行数（プロセス全体） | 4 | `1..=64` | 通常の書き込みの待ち時間は 8.2 節の優先で同時実行数に依存しないため、この値は分割実行どうしで writer を分け合う数として小さく保つ（ジョブ数が多いほど各ジョブの完了が遅れ、待機上限での部分完了が増える）。上限は `MAX_CONNECTIONS`（64） |
| 中断ジョブの記録数（テナント・テーブル単位。取り消し済み記録は数えない） | 1,000 件 | `1..=1,000,000` | 15.3 節。単位は台帳・ジョブ表のキーと同じ `(tenant, table)`。値は明示トランザクションの `max_statements`（1,000）・チャンク幅と同じ桁にそろえる。範囲は `MAX_DML_ROW_LIMIT` と同じ |

組合せの制約（起動時に検証し、満たさなければ fail-closed で起動を拒否する）:

- テナント単位の同時実行数が全体の同時実行数以下であること

通常の書き込みの待ち時間の上限は、同時実行数と保持時間の積ではなく、8.2 節の優先（待機中の
通常の書き込みがある間は分割実行のチャンクを取得しない）で保証する。

設定方法:

- いずれも `wire-server` 起動時の CLI フラグだけで設定する（フラグ名は #1129 で確定:
  `--partitioned-dml-chunk-rows`・`--partitioned-dml-scan-budget`・`--partitioned-dml-max-hold-ms`・
  `--partitioned-dml-max-jobs-per-tenant`・`--partitioned-dml-max-jobs`・
  `--partitioned-dml-max-interrupted-records`）。範囲外・非数値・多重指定は起動時に fail-closed で拒否する。
  根拠: `--max-dml-affected-rows`・`--max-insert-rows`（`predicate-dml-exec.md` §6）と同じ流儀で、
  セッション・テナント単位の設定は持たない。環境変数は設けない（`batch_limits` の
  `VECTOR_DB_BATCH_MAX_FILES` は既存互換のためのもので、新しい上限には広げない）。
- 文の `CHUNK <n>` で指定できるのはチャンク幅だけとし、範囲は `1..=サーバー設定のチャンク幅`
  （小さくする方向だけ）にする。走査予算・writer 保持時間・同時実行数・記録数は文から変えられない。
  根拠: 資源上限をテナントが文で緩められないようにする（8.2 節）。
- 1 チャンクは「適用行数がチャンク幅に達した」「走査行数が走査予算に達した」「writer 保持時間が
  上限に達した」のいずれかで締め、そこまでの変更とカーソルを commit する（エラーではない）。
  変更が 0 件のチャンクは、ジョブ表の行がまだなければ何も書き込まず、カーソルはメモリ上だけで
  進める（15.3 節）。ジョブ表の行があれば、その行のカーソルを更新する（記録は増えない）。

### 15.3 取り消し済み・中断ジョブの保持期間

| 項目 | 確定値 | 根拠 |
| ---- | ------ | ---- |
| 期限掃除 | 設けない（`DROP TABLE` 時にだけ、台帳と同じトランザクションで削除する） | 台帳（`OP_LEDGER_TABLE`）にも期限掃除がない（F3）。中断・取り消し済みの記録を期限で消すと、同じ `operation_id` を別内容で再利用できてしまい、keep-first と同じ「使用済み `operation_id` は再利用できない」性質が崩れる |
| 記録の大きさ | 1 ジョブあたり固定長（キーの `operation_id` は既存の `MAX_OPERATION_ID_LEN`〔256 バイト〕で検証済み。値はハッシュ・状態・カーソル・件数） | 1 件の大きさが有界になる |
| 変更 0 件での正常完了 | 述語に一致する行がないまま範囲を走査し尽くした場合は、最後のチャンクのトランザクションで台帳エントリと完了記録（累計件数 0）を作り、同じトランザクションで commit する（ジョブ表の行がない状態から、完了記録を直接作る） | 原子的な述語形 DML が 0 行一致でも台帳エントリを commit する契約（`multi-row-dml-operation-id.md` §6）と同じ扱いにし、完了後の再送を `23505`／`22023` で、進捗照会を「完了・0 件」で判定できるようにする。完了記録は台帳エントリと 1 対 1 なので、増え方は既存の 0 行一致の DML と同じ |
| 完了記録の件数 | 上限を設けない | 完了記録は台帳エントリと 1 対 1 で、完了した DML 1 件につき 1 件増える台帳と同じ増え方になる |
| 記録を作る時点 | 行を 1 件以上変更した最初のチャンクの commit と同じトランザクションでジョブ表の行を作る。それまでの走査位置（カーソル）はメモリ上だけに持つ。行を変える前に失敗・取り消し・接続断・プロセス停止になったジョブは記録を残さず、再送すると最初からやり直す | 行を変える前のジョブは何も適用していないので、最初からやり直しても 1 行 1 回は崩れない。その `operation_id` は、失敗した通常の DML（台帳に記録されず再利用できる。`predicate-dml-exec.md` §8 の失敗注入テスト）と同じく再利用できる。記録が増えるのは行を 1 件以上変更したジョブに限られる（2026-10-01 のオーナー追加確認 2 で、作成時点を「最初のチャンクの commit」から改めた） |
| 取り消し済み記録 | 取り消しの時点で、カーソルを持たない固定長の記録（内容照合ハッシュ・状態・commit 済み件数）へ縮めて残す。削除する手段は設けず、記録数の上限にも数えない | 台帳は完了時にしか記録しないため、行を変更済みのジョブの記録を消すと、同じ `operation_id`・同じ文を新しいジョブとして再実行でき、適用済みの行へ再び適用しうる（1 行 1 回と `operation_id` の再利用禁止が崩れる）。上限に数えないので、取り消しを繰り返しても新しいジョブの開始が妨げられない |
| 取り消し済み記録の増え方 | 上限を設けない（完了記録と同じ扱い） | 記録は行を 1 件以上変更したジョブにだけ作る（上の「記録を作る時点」）。述語に一致する行が 0 件のまま走査予算や保持時間でチャンクを締めても記録はできないので、取り消し済み記録を 1 件増やすには、毎回 1 行以上の実際の変更（writer の取得・行の変更・commit）が要る。そのため増え方は実際の書き込み量に比例し、完了した DML 1 件につき 1 件増える既存の台帳と同じ性質になる。1 件の大きさも固定長で有界 |
| 中断記録の件数 | 中断記録（再開用のカーソルを持つ記録）だけを `(tenant, table)` 単位で数え、上限を設ける（15.2 節の確定値（2026-10-01 オーナー確認） 1,000 件）。上限に達したら、そのテーブルでの新しいジョブの開始を副作用ゼロで拒否する（コードは 15.4 節）。開始時の判定に加え、ジョブ表の行を作るトランザクション（行を変更する最初のチャンク）の中で、カーソルを持つ記録（実行中＋中断）の件数を数え直し、上限に達していればそのチャンクを commit せずに同じコードで拒否する（行の変更・記録とも残らない） | 再開用のカーソルを持つ記録が際限なく増えるのを防ぐ。実行中の記録は中断すればそのまま中断記録になるので、作成時に実行中も含めて数える。writer は 1 つなので、記録を作るトランザクション内の判定は並行するジョブに対しても原子的になり、同じテナントの複数ジョブが同時に最初の変更を commit しても上限を超えない。中断ジョブを再送して完了させるか、取り消せば枠が空く（どちらも中断記録から外れる）ので、通常の運用で枠を回復できる。拒否の応答に他テナントの情報を含めない（2026-10-01 のオーナー追加確認で、対象を中断＋取り消し済みから中断だけに変更） |

### 15.4 8.2 節の残余リスク

| 項目 | 確定値 | 根拠 |
| ---- | ------ | ---- |
| プロセス全体の同時実行数上限による拒否から全体の混み具合が分かること | 許容する | 分かるのは「全体が混んでいる」ことだけで、他テナントの識別子・ジョブ数・行数は応答に含めない。単一 writer の待機上限（`55P03`）・接続数上限（`53300`）も同じ程度の全体負荷を既に示している。テナント単位の上限を先に判定し、全体上限の拒否もテナント単位の拒否と同じコード・同じ文言にする |
| 同時実行数の上限超過のコード | `55P03`（`LOCK_NOT_AVAILABLE`） | 時間をおけば解消する一時的な拒否で、writer 待機上限と同じ「再試行できる」扱いがふさわしい。`54000`（`PAYLOAD_TOO_LARGE`）は要求自体の大きさの超過に使っており意味が合わない。全体上限による拒否が示す情報も、writer 待機の `55P03` と同じ程度にとどまる |
| 中断記録数の上限超過のコード | `54000`（`PAYLOAD_TOO_LARGE`） | 時間をおいても解消しない上限超過で、副作用ゼロで拒否する既存の `54000` の扱いと同じ。自テナント・自テーブルの判定だけで、他テナントの状態は応答に影響しない |

## スコープ外・申し送り

- `crates/` 配下のコード変更・実装（#1127〜#1131 の担当）
- 非同期ジョブ形（S3）と起動時の自動再開（C2）。S1 の運用実績を見て必要なら別 Issue で検討する
- pg wire の CancelRequest・`statement_timeout`（F9）。分割実行の取り消しは専用文で扱い、
  CancelRequest 対応は別 Issue で検討する
- 大量 `INSERT`・UPSERT・`TRUNCATE` の分割実行（3.1 節）
- `SET` の右辺に式を許す拡張（F12）。4.2 節の保証はそのまま効くが、拡張自体は対象外
- スカラー二次索引による候補削減（`predicate-dml-exec.md` §10 の申し送りと同じ）
