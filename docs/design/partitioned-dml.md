## 1. 背景・目的

述語形 `UPDATE ... WHERE`／`DELETE ... WHERE`（SQL-19）は、1 文の全対象行を 1 つの write
トランザクションで適用し、台帳へ 1 文 1 エントリを記録する（`predicate-dml-exec.md` §3・
`multi-row-dml-operation-id.md` §6）。影響行数上限は Issue #997 で既定無効になった
（`predicate-dml-exec.md` §6）が、大量行の更新・削除には次の制約が残る。

- **走査上限**: 1 文あたりの総走査行数上限 `tenant::MAX_SCANNED_ROWS`（1,000,000）は常に
  適用される。対象テナントの所有行が 100 万行を超えるテーブルでは、述語にほとんど一致しなく
  ても 1 文で処理できず `54000` になる。
- **writer の占有**: redb の writer はプロセス内で 1 つで、全テナントが共有する（`explicit-transaction.md` §1・
  `storage/writer_gate.rs`）。
  1 文の DML が writer を握る時間に上限はなく、全走査と適用が終わるまで他テナントの書き込みは
  writer gate で待つ（待機上限 30 秒を超えると `55P03`。`explicit-transaction.md` §2・§5）。
- **メモリ**: 現行の実行器は候補 id をすべて `Vec<u64>` に集めてから適用する。

単一トランザクションの肥大化と writer の長時間占有を避けるため、原子性を持たない分割実行
（チャンク単位コミット）の経路を**別経路として**追加する方式を検討する。既存の 1 文 1
トランザクション経路（`delete_rows_where_unchecked`／`update_rows_where_unchecked`）とその
原子性・台帳契約は変えない。

他 DB の同種機能として、Cloud Spanner の Partitioned DML（パーティションごとに独立に
コミットし、文全体は原子的でない）、TiDB の非トランザクション DML（`BATCH ON <列> LIMIT n`
で分割する）、CockroachDB で推奨される分割削除（クライアント側のループ）がある。本 ADR は
それぞれの意味論を参考にするが、互換構文は目標にしない。

## 2. 現状整理（決定の前提）

## 3. 論点 1: 対象文と構文

### 3.1 対象文

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| T1 | 述語形 `UPDATE`／`DELETE`（SQL-19）のみ | 走査上限・writer 占有の問題があるのはこの 2 文。対象集合が述語で決まり、チャンク分割の意味が明確 | 大量 INSERT は対象外 |
| T2 | T1 ＋大量 `INSERT`（複数行 `VALUES`・ファイル形） | 取り込みも分割できる | INSERT は既に `batch_limits`（`max_files_per_batch`・`max_batch_chunks`）とファイル単位の取り込み経路で分割でき、クライアントが文を分ければ足りる。INSERT の対象集合は入力そのもので、走査上限の問題もない |
| T3 | T1 ＋ `TRUNCATE`・UPSERT | 網羅的 | `TRUNCATE` は全行削除専用の別経路。UPSERT は衝突判定と台帳の関係が複雑で、分割すると意味論が変わる |

**推奨（候補）**: T1。単一行形（`WHERE id = n`）・`RETURNING` 付き・UPSERT・`TRUNCATE` との
組合せは受理しない（返却行がチャンクを跨ぐと原子性のない結果セットになるため、`RETURNING`
も対象外とする）。

### 3.2 構文

| 候補 | 内容（例示） | 利点 | 欠点 |
| ---- | ------------ | ---- | ---- |
| S1 文の修飾 | `UPDATE t SET ... WHERE ... USING OPERATION_ID '<id>' PARTITIONED [CHUNK <n>]` | 既存の述語形 DML の許可リスト・束縛・内容照合ハッシュをそのまま再利用できる。同期実行なので応答（完了／部分完了）が文の結果として返る | 長時間の同期実行になり、クライアント側のタイムアウトに当たりうる（再送で再開できるので致命的ではない。5.3 節） |
| S2 専用文 | `PARTITIONED UPDATE ...`／`BATCH DELETE ...` のような別の先頭キーワード | 先頭トークンで経路が分かれ、既存の文と取り違えない | 先頭トークン分岐と許可リストを二重に持つことになり、述語・`SET` の検証を共有する設計（`delete-predicate-form.md`）から外れやすい |
| S3 非同期ジョブ形 | 起動文がジョブ識別子を即座に返し、サーバー側のワーカーが実行する。照会・取り消しは別の文 | 接続を保持しなくてよい | サーバー内にバックグラウンド実行器・スケジューラが必要。セッションを持たない実行主体が RLS の文脈（`PolicyContext`）を保持・永続化する必要があり、テナント境界の検査面が増える。再起動後の自動再開も実装しなければならない |

**推奨（候補）**: S1（同期実行の文修飾）。キーワード名・チャンク幅指定の形は #1129 で確定する
（例示の `PARTITIONED`・`CHUNK` は仮）。S3 は S1 の実績を見てから必要性を判断する。

### 3.3 トランザクション内での扱い

分割実行は「チャンクごとに commit する」ことが本質であり、明示トランザクション・暗黙
トランザクションの 1 回 commit（F8）と両立しない。

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| X1 | トランザクション内では拒否する | PostgreSQL がトランザクションブロック内で実行できない文（`VACUUM` 等）に返す `25001` と同じ扱い |
| X2 | トランザクション内では通常の原子的実行へ黙って縮退する | 利用者が指定した意味論と違う実行になる（fail-open 側の挙動）ため不可 |

**推奨（候補）**: X1。コードは既存の `ActiveSqlTransaction`（`25001`。現在は `Active` 中の
再 `BEGIN` に使っている）の流用と、既存 `InvalidTransactionState`（`25000`）の流用のどちらかで、
オーナー判断とする（推奨は PostgreSQL と同じ `25001`。どちらも `ErrorClass` の追加は要らない）。

## 4. 論点 2: 対象集合の確定と冪等性

### 4.1 対象集合の確定

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| P1 開始時スナップショット固定 | 開始時に述語を一度評価して対象 id 集合を確定・永続化し、チャンクはその集合を順に適用する | 対象集合が開始時点で決まる | 開始時の全走査そのものが `MAX_SCANNED_ROWS` と writer 占有の問題を抱える（分割の目的と矛盾する）。id 集合の永続化が O(対象行数) になる。開始後に他クライアントが述語列を変えた行も適用してしまう（チャンク時点で再判定しない場合） |
| P2 チャンクごと再評価（キー順カーソル） | 物理キー `(tenant, id)` の昇順に 1 回だけ進むカーソルを持つ。各チャンクは `(tenant, cursor + 1)..=(tenant, u64::MAX)` を走査し、そのチャンクのトランザクション時点の行内容で述語を評価し、一致行を適用し、最後に走査したキーを新しいカーソルとして**同じトランザクションで**保存する | 開始時の全走査が不要。メモリはチャンク幅に比例。カーソルが単調に進むので、1 ジョブ内で同じ行を 2 回訪れない | 対象集合はジョブ全体で一意に定まらない（カーソルより後ろに挿入された一致行は適用され、前に挿入された行は適用されない） |
| P3 P2 ＋収束まで再走査 | P2 を一巡した後、一致行がなくなるまで先頭から繰り返す | 終了時点で一致行が残らない | 他クライアントが一致行を作り続けると終わらない。`SET` 後も述語に一致し続ける文では同じ行へ再適用する |

**推奨（候補）**: P2。各行は「チャンクのトランザクション時点で述語に一致していれば、その
トランザクションで 1 回だけ適用される」意味論になる。`UPDATE` は `id` を変えないため、更新後の
行をカーソルが再訪することはない（ハロウィン問題が起きない）。カーソルより前に後から入った
行は対象外になることを利用者向けの文書に明記する。

### 4.2 冪等性（同じ行へ 2 回適用されうるか）

- P2 では「チャンクの行変更」と「カーソル・処理済み件数の更新」を同じ write トランザクションで
  commit する。クラッシュ・中断の後もカーソルより前の行は適用済み、後ろの行は未適用であり、
  再開しても同じ行を 2 回適用しない。この性質は `SET` の右辺の形に依存しない。
- 現状 `SET` の右辺はリテラルのみ（F12）なので、仮に同じ行へ 2 回適用されても結果は変わらない。
  ただしこれは偶然の性質であり、推奨案はカーソルの原子的保存で「ちょうど 1 回」を保証する。
  将来 `SET col = col + 1` のような非冪等な式を許す場合も、この保証がそのまま効く。
- ジョブ完了後の同一文の再送は台帳で `23505` になる（6 節）。

### 4.3 既存の上限との関係

| 上限 | 候補 | 推奨（候補） |
| ---- | ---- | ------------ |
| `MAX_SCANNED_ROWS`（1 文の総走査行数） | (a) ジョブ全体に適用 ／ (b) チャンクごとに適用（チャンクの走査予算 ≤ `MAX_SCANNED_ROWS`） | (b)。(a) では 100 万行を超えるテーブルを処理できず、分割の目的を果たせない。一致行が少ない述語でもチャンクの走査予算で writer の占有が区切られる |
| `--max-dml-affected-rows`（影響行数上限・既定無効） | (a) 分割実行には適用しない ／ (b) 明示指定時はジョブ全体の累計に適用し、累計が上限を超えるチャンクは適用せずに部分完了として止める ／ (c) チャンクごとに適用 ／ (d) 明示指定時は分割実行そのものを拒否する | 既定（未指定）ではどの候補でも差が出ない。運用者が明示指定した場合は (b)。(a) は運用者が安全策として設けた上限を分割実行の修飾だけで迂回できる（制限を緩める側の変更）ため推奨しない。(b) は上限を超える行へ一度も適用しない一方、既存の「超過時は副作用ゼロで `54000`」（`predicate-dml-exec.md` §6）は P2 では守れない（総件数が事前に分からない）ため、`54000` ではなく部分完了のコード（5.1 節）で止める。最初のチャンクで超える場合は 1 件も commit していないので、5.1 節の R1 どおり `54000`（副作用ゼロ）になる。より保守的な (d) との選択はオーナー判断。(c) は 1 チャンク内の件数しか見ず、上限の意味を失う |
| チャンク幅 | (a) 適用行数 ／ (b) バイト数 ／ (c) 時間 | (a) 適用行数を主とし、(b)・(c) の代わりにチャンクあたりの走査予算と writer 保持時間の上限を併用する。既定値・指定可能範囲はオーナー判断 |

## 5. 論点 3: 部分完了の応答・エラーコード・進捗照会・再開・取り消し

### 5.1 部分完了の応答と `wire_code`

中断の原因は、チャンク内の行エラー（式評価エラー・制約違反）、チャンク開始時の writer 待機
上限（`55P03`）、取り消し、接続断、プロセス停止のいずれかである。

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| R1 部分完了専用の新コード | 1 チャンク以上 commit 済みで中断したら、部分完了を表す新しい `ErrorClass`（ラベル例 `PARTIAL_COMPLETION`、SQLSTATE は実装定義の値）で返す。原因のコードと commit 済み件数・`operation_id` は固定書式のメッセージに入れる。commit 済みが 0 件なら原因のコードをそのまま返す（従来の原子的失敗と区別がない） | 「一部 commit 済み・同じ文の再送で再開できる」ことをコードだけで判別できる。既存コードの意味（`54000`＝副作用ゼロ等）を変えない | `ErrorClass` の追加（件数定数・HTTP 射影表の更新）が必要。SQLSTATE 値の選定が要る |
| R2 原因コードをそのまま返す | 中断原因のコード（`22012`・`23505`・`55P03` 等）を返し、部分完了であることはメッセージだけで示す | クラス追加が不要 | クライアントはコードだけでは原子的失敗と区別できず、「何も起きていない」と誤認しうる（fail-open 側） |
| R3 `57014`／`40001` を流用 | キャンセル・ロールバック系の既存 SQLSTATE を使う | PostgreSQL クライアントが知っているコード | `40001` は「ロールバックされた」意味で事実と逆。`57014` は本リポに未実装で、PostgreSQL では副作用なしの中断を意味する |
| R4 成功応答＋警告 | `UPDATE n` を返し、`NoticeResponse` で部分完了を知らせる | 応答が単純 | 警告を読まないクライアントは成功と誤認する（fail-open）。不可 |

**推奨（候補）**: R1。SQLSTATE の具体値は、PostgreSQL の既存クラスと衝突しない実装定義の値から
オーナーが選ぶ（要判断項目）。全チャンク完了時の応答は従来どおり `UPDATE n`／`DELETE n`
（`n` はジョブ全体の累計。再開をまたいだ場合も累計）とする。

### 5.2 HTTP 射影（ERR-4）

| 候補 | HTTP | 評価 |
| ---- | ---- | ---- |
| H1 | `409 Conflict`＋`code` ラベル＋本文に `committed`・`operation_id` | 「ジョブが中間状態にあり、同じ要求の再送で解消する」状態の衝突として表せる。`23505`（409）と同じ帯 |
| H2 | `503 Service Unavailable` | `55P03`（503）と同じ再試行可能の帯だが、行エラーで止まった場合（再送しても同じ行で再び止まる）には合わない |
| H3 | `200 OK`＋`"complete": false` | R4 と同じく fail-open。不可 |

**推奨（候補）**: H1。完了時の本文は既存 D4（`nosql-update-delete-mapping.md`）と同型
（`{"updated":<n>,...}`／`{"deleted":<n>,...}`）とする。

### 5.3 進捗照会・再開・取り消し

| 項目 | 候補 | 推奨（候補） |
| ---- | ---- | ------------ |
| ジョブの識別子 | (a) クライアントが指定した `(table, operation_id)` ／ (b) サーバーが採番するジョブ id | (a)。`operation_id` は既に必須で一意。採番 id を推測・列挙される面を作らない。テナントは認証主体から導出し、キーに含める |
| 進捗照会 | (a) 読み取り専用の専用文（例: `SHOW PARTITIONED DML '<operation_id>' ON <table>`）／ (b) システムビューへの `SELECT` ／ (c) 照会手段なし | (a)。writer を使わずに状態（実行中／中断／取り消し済み／完了）・処理済み件数を返す。(b) は仮想テーブルの基盤が要る |
| 再開 | (a) 同じ文を同じ `operation_id` で再送すると、内容照合ハッシュが一致すればカーソルから再開 ／ (b) 専用の再開文 | (a)。「再送して commit 済みか確かめる」既存の回復手順（`multi-row-dml-operation-id.md` §3 の候補 C の説明）と同じ操作で再開できる。ハッシュ不一致は `22023`、完了済みは `23505`（6 節） |
| 取り消し | (a) 専用文（例: `CANCEL PARTITIONED DML '<operation_id>' ON <table>`）で、実行中なら次のチャンク境界で止め、状態を取り消し済みにする ／ (b) CancelRequest（pg wire）で止める | (a)。CancelRequest は未実装（F9）。(b) は別 Issue で検討する |
| 取り消し後のロールバック | (a) 行わない（commit 済みチャンクは残る）／ (b) 変更前の行内容を保存して戻す | (a)。(b) は変更前イメージの保存が O(対象行) になり、分割の目的に反する |
| 実行中ジョブへの再送 | (a) `55P03` で拒否 ／ (b) 実行中ジョブの終了を待つ | (a)。プロセス内の実行中ジョブ登録簿で `(tenant, table, operation_id)` の二重実行を防ぐ。クライアントがタイムアウト後に再送した場合も安全 |

取り消し済みジョブへの同一内容の再送は再開しない（取り消しを優先する）。この場合のコードは
部分完了コード（5.1 節）に「取り消し済み」を示す固定メッセージを付けるか、別コードにするかは
Issue #1129 で確定する。

## 6. 論点 4: 台帳と再送検出

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| L1 ジョブ単位（完了時に台帳記録） | 進行状態は台帳と別のジョブ表（キー `(tenant, table, operation_id)`、値は内容照合ハッシュ・状態・カーソル・処理済み件数）に持つ。最後のチャンクと同じトランザクションで台帳エントリを記録し、ジョブ表の行を消す | 「台帳エントリの存在 ⇔ 対象とした全行の変更が commit 済み」（F2）を分割実行でも保てる。完了後の再送は既存どおり `23505`／`22023`。完了したジョブは台帳 1 エントリだけが残り、増え方は既存と同じ | 通常の DML が実行中・取り消し済みジョブと同じ `operation_id` を使う場合を検出するため、台帳照合の際にジョブ表も 1 回引く必要がある |
| L2 チャンク単位 | チャンクごとに `(operation_id, チャンク番号)` の台帳エントリを記録する | 各チャンクの commit が台帳で確定する | P2 ではチャンク境界がデータに依存し、再送時にチャンク番号を再現できない。エントリ数がチャンク数に比例して増え、掃除がない（F3）。`multi-row-dml-operation-id.md` が候補 B を退けた理由（部分状態・どこまで commit 済みか判定できない）と同じ問題を持つ |
| L3 開始時に台帳記録 | 開始トランザクションで台帳エントリを記録する | 二重起動を台帳だけで防げる | F2 の同値性が崩れる（エントリがあっても全行は未適用）。既存の再送判定・回復手順の意味が変わる |
| L4 台帳値に「進行中」版を追加 | 台帳値の版バイトに進行中を表す版を足し、完了時に通常の版へ書き換える | ジョブ表を別に持たない | keep-first（上書きしない）の契約を変える。未知の版を `Corrupted` とみなす既存の読み手（F3）と互換がない |

**推奨（候補）**: L1。あわせて次を提案する。

- **ハッシュのドメイン**: 分割実行は原子的実行と意味論が違うため、内容照合ハッシュの操作種別
  タグを分ける（例: `OpTag::UpdateWherePartitioned`／`DeleteWherePartitioned`。既存タグの値は
  変えない）。同じ `operation_id` を原子的実行と分割実行で使い回すと `22023` になる。
  チャンク幅はハッシュに**含めない**（結果に影響しないため、幅を変えて再開できる）。
- **通常 DML との衝突**: 実行中・中断・取り消し済みジョブの `operation_id` を通常の DML が
  使った場合は、ドメインが違うので `22023` で拒否する。
- **保持期間**: 完了時はジョブ表の行を消す（台帳エントリが残る）。取り消し済み・中断のまま
  放置されたジョブは、`operation_id` の再利用を防ぐため状態を残す。掃除は台帳と同じく
  `DROP TABLE` 時とし、期限掃除の要否はオーナー判断（要判断項目）。
- **明示トランザクション内の台帳**: 3.3 節の X1 により分割実行はトランザクション内に入らない
  ため、明示トランザクションの台帳の扱い（`explicit-transaction.md` §1）とは交わらない。

## 7. 論点 5: テーブル世代・キャッシュ失効・索引更新と途中状態の可視性

### 7.1 索引更新

UNIQUE 索引・FK 検査（F6）は、各チャンクで行の書き込みと同じトランザクション内で行う（候補を
置かない。チャンクの commit ごとに行と索引が一致していなければならない）。FK はチャンクごとに
即時検査する。スカラー二次索引・HNSW・疎索引は派生キャッシュで、世代で失効する。

### 7.2 世代の進め方

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| G1 チャンクごと | 影響 1 行以上のチャンクで `bump_table_generation_in_txn` を呼ぶ | 各キャッシュは世代照合だけで失効する（F5）ので、commit 済みの行と読み取り結果が常に一致する | テーブル世代は全テナント共通なので、チャンクごとに全テナントのキャッシュが失効し、`USING PLAN` の世代照合も失敗しうる |
| G2 ジョブ完了時に 1 回 | 途中のチャンクでは世代を進めない | キャッシュの失効が 1 回で済む | 途中のチャンクで commit 済みの行（削除済みの行など）を、古い世代のキャッシュが返し続ける。読み取りの正しさが崩れるため不可 |
| G3 G1 ＋間引き | G1 を保ったまま、チャンク幅の下限やチャンク間の間隔で世代を進める頻度を抑える | 正しさを保ったまま負荷を調整できる | 分割の細かさ（writer を手放す頻度）との兼ね合いになる |

**推奨（候補）**: G1（必要なら G3 の間引きをチャンク幅・間隔の既定値で調整する）。G2 は
キャッシュの正しさを壊すので推奨しない。

### 7.3 途中状態の可視性

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| V1 見えることを許容し文書化する | チャンク commit ごとに他クライアントから途中状態が見える。行単位（行は旧値か新値のどちらか）とチャンク単位の原子性は保つ | Spanner の Partitioned DML と同じ扱い。追加の仕組みが要らない |
| V2 途中状態を隠す | ジョブ完了まで変更を見せない | 影の版管理（MVCC 相当）が必要で、本リポのストレージ（単一 writer・スナップショット読み取り）にはない。不可 |

**推奨（候補）**: V1。`EXPLAIN` の出力と利用者向けの文書で、分割実行であり途中状態が見える
ことを示す（#1129）。

## 8. 論点 6: RLS とテナント間の資源上限

### 8.1 テナント境界

- 各チャンクは既存の述語形 DML と同じ範囲（テナント所有かつ可視。閉区間
  `(tenant, 0)..=(tenant, u64::MAX)`。`predicate-dml-exec.md` §4）だけを走査する。カーソルは
  この閉区間の中だけを進み、他テナントの領域のキー・値を読まない。
- 再開時の認可は、再開したセッションの認証主体から改めて導出する（ジョブ表に RLS の文脈を
  永続化しない）。ジョブ表のキーにテナントを含めるので、別テナントからは同じ
  `(table, operation_id)` のジョブに到達しない。
- 進捗照会・取り消しは自テナントのジョブだけを対象にする。「ジョブが存在しない」「別テナントの
  ジョブ」「`ON <table>` のテーブルが存在しない」「テーブルはあるが要求元から見えない」は、
  すべて同じ応答（同じコード・同じ文言）にする（RLS-9 の応答同一性と同じ考え方）。
- 応答に含める件数は自テナントで commit した件数だけとする。

### 8.2 資源上限

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| Q1 プロセス全体の上限だけ | 同時実行ジョブ数の上限をプロセス全体で持つ | 単純 | 1 テナントが枠を使い切ると他テナントが起動できない。拒否されたこと自体から他テナントの負荷が分かる |
| Q2 テナント単位＋プロセス全体 | テナントごとの同時実行ジョブ数上限を主にし、プロセス全体の上限は余裕のある値にする | テナント間の公平性を保てる | 設定項目が増える |
| Q3 上限なし | — | — | writer をチャンク単位で手放しても、多数のジョブが交互に writer を取れば通常の書き込みが待たされる |

**推奨（候補）**: Q2。加えて次を提案する。

- **writer の手放し方**: チャンクごとに writer gate を取り直す（取得には既存の待機上限が
  効き、超えたら `55P03` で部分完了または 0 件失敗になる）。writer gate は `Mutex`＋`Condvar`
  で到着順を保証しないため、チャンクの commit 後に待機者がいれば譲る（待機者がいるときだけ
  短く間を空ける）。1 チャンクの writer 保持時間には上限を設け、走査予算と合わせて占有時間を
  区切る。
- **起動時の上限超過**: 1 チャンクも commit していない時点での拒否なので副作用ゼロであり、
  `54000` で返す。プロセス全体の上限による拒否も同じコード・同じ文言にし、他テナントの
  ジョブの数や識別子を応答に含めない。ただし、自テナントのジョブが上限未満なのに拒否された
  ことから、プロセス全体が混んでいることは分かる。これは writer 待機の `55P03` と同じ程度の
  残余リスクであり、許容するかどうかを要判断項目に挙げる。
- 既定値（チャンク幅・走査予算・保持時間・同時実行数）はオーナー判断とする。

## 9. 論点 7: クラッシュ時の挙動と crash-test の「部分コミット 0 件」基準との区別

### 9.1 既存の crash-test が確認していること

`make crash-test`・`crash-test-cross-table`・`crash-test-unique-index` は、それぞれ
`crates/engine/examples/crash_tool*.rs` の書き込み処理を `kill -9` で止め、再起動後に次を
確認する（`crash-test-interrupt` はスクリプト自体の中断処理のセルフテスト）。

| ターゲット | 書き込み | 再起動後の確認 |
| ---------- | -------- | -------------- |
| `crash-test`（PERSIST-1） | 1 行ずつ commit | 行 id が欠番なく連続し、内容が一致し、ack 済みの件数以上が残る |
| `crash-test-cross-table`（TABLE-10） | 10 行＋バッチ台帳を 1 トランザクション | 行と台帳が連続し、台帳の件数合計と行の総数が一致し、行数がバッチ幅の倍数（1 トランザクションの部分 commit が 0 件） |
| `crash-test-unique-index`（TABLE-16） | UNIQUE 列への 10 行を 1 文で INSERT | 行数がバッチ幅の倍数で、既存値の再 INSERT が必ず `23505`（索引の欠落がない） |

いずれも「1 トランザクション（1 文）の変更は全部残るか全く残らないか」を確認しており、
UPDATE／DELETE を kill するシナリオはない（F14）。

### 9.2 分割実行のクラッシュ時の挙動

| 候補 | 内容 | 評価 |
| ---- | ---- | ---- |
| C1 クライアントの再送で再開 | 再起動後は何も自動実行しない。永続化された「実行中」状態は、プロセス内の実行中ジョブ登録簿にないことから「中断」とみなす。同じ文の再送でカーソルから再開する | セッションのない実行主体を持たない。S1・L1 と整合する |
| C2 起動時に自動再開 | 再起動時にサーバーが中断ジョブを自動で再開する | RLS の文脈の永続化と、セッションのない実行主体が必要（S3 と同じ欠点）。利用者が知らないうちに書き込みが再開する |

**推奨（候補）**: C1。チャンクの commit に失敗した場合は既存どおり `process::abort()` で止まる
（F7）。各チャンクは「行変更・索引・カーソル・処理済み件数・（最後のチャンクでは）台帳記録と
ジョブ表の削除」を 1 トランザクションで commit するので、再起動後の状態はチャンク境界の
どこかにそろう。

### 9.3 検証基準の区別（#1131 への提案）

- 既存の crash-test 系ターゲットと、その「部分コミット 0 件」基準（1 トランザクション・1 文の
  単位）は**変更しない**。分割実行を既存ターゲットの対象に加えない。
- 分割実行には別の基準を設ける。
  1. **チャンク原子性**: 1 チャンクの変更は全部残るか全く残らない（チャンク単位での「部分
     コミット 0 件」）。
  2. **前方一致**: 適用済みの行は、永続化されたカーソル以下の一致行と正確に一致する（カーソルより
     後ろの行は未適用）。処理済み件数とも一致する。
  3. **ちょうど 1 回**: 再開後に全一致行へ 1 回だけ適用される。`SET` がリテラルだけの現状では
     値から二重適用を観測できないため、`DELETE` のシナリオと処理済み件数の照合で確認する。
  4. **台帳**: 完了前は台帳エントリがなく、完了後はちょうど 1 エントリある。
- 新しい `crash_tool` と `scripts/crash_test_*.sh`・Makefile ターゲットを追加する形が候補だが、
  `make ci` に入れるかは実行時間を見て #1131 で決める。

## 10. 論点 8: NoSQL 表層とのパリティ

| 候補 | 内容 | 利点 | 欠点 |
| ---- | ---- | ---- | ---- |
| N1 既存 op の修飾 | `update`／`delete` op に `"mode": "partitioned"`（例示）を足す。`filter` 指定時だけ受理し、`where`（単一行）との組合せは `42601` | SQL の S1（文の修飾）と対称。同じ実行器・同じ内容照合ハッシュのドメインを使える | op ごとの判定順序（`nosql-update-delete-mapping.md` D5）に分岐が増える |
| N2 専用 op | `partitioned_update`／`partitioned_delete` op を新設 | op の許可リストで経路が分かれる | `filter` の検証・写像を二重に持ちやすい |
| N3 NoSQL では提供しない | SQL 表層だけ | 実装量が少ない | NOSQL-12 のパリティから外れる |

**推奨（候補）**: N1。進捗照会・取り消しは NoSQL にも用意する（op の追加。名前は #1130 で
確定）。次の点を SQL 表層とそろえる。

- 実行器・上限・部分完了の意味論・内容照合ハッシュのドメインは SQL 表層と同じ（同じ
  `operation_id` で SQL と NoSQL を跨いで再送すると、内容が同じなら再開・`23505`、違えば
  `22023`）。
- 述語は既存の述語形 DML の `filter` と同じく `eq`／`prefix` のみ（F13）。
- HTTP 射影は 5.2 節の H1。長時間の HTTP 要求はクライアント・中継のタイムアウトに当たりうるが、
  再送で再開できる（5.3 節）ことを利用者向けの文書に書く。
- NoSQL 表層にはトランザクションがない（`explicit-transaction.md`）ため、3.3 節の拒否は該当しない。

## 11. 推奨（候補）のまとめ

| 論点 | 推奨（候補） |
| ---- | ------------ |
| 対象文 | 述語形 `UPDATE`／`DELETE` のみ（`RETURNING`・単一行形・UPSERT・`TRUNCATE` は対象外） |
| 構文 | 同期実行の文修飾（S1）。明示・暗黙トランザクション内では拒否（`25001` の流用） |
| 対象集合 | キー順カーソルでチャンクごとに再評価（P2）。カーソルは行変更と同じトランザクションで保存 |
| 冪等性 | カーソルの原子的保存で 1 行 1 回を保証。`SET` の右辺の形に依存しない |
| 上限 | `MAX_SCANNED_ROWS` はチャンクごと。`--max-dml-affected-rows` は明示指定時にジョブ累計へ適用し、超える手前で部分完了として止める |
| 部分完了 | 新しい部分完了コード（R1・SQLSTATE 値はオーナー判断）。HTTP は `409`（H1） |
| 照会・再開・取り消し | `(table, operation_id)` で識別。専用の照会文・取り消し文。再開は同じ文の再送 |
| 台帳 | ジョブ単位。完了時に台帳記録（L1）。分割実行用にハッシュのドメインを分ける |
| 世代・可視性 | 影響のあるチャンクごとに世代を進める（G1）。途中状態は見える（V1） |
| RLS・資源 | 既存と同じ走査範囲。テナント単位＋全体の同時実行数上限（Q2）。チャンクごとに writer を手放す |
| クラッシュ | 自動再開しない。再送で再開（C1）。既存 crash-test の基準とは別の基準を新設 |
| NoSQL | 既存 op の修飾（N1）。照会・取り消しの op を追加 |
