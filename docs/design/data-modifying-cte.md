# データ変更 CTE（`WITH x AS (INSERT/UPDATE/DELETE ...)`）の設計記録

ポインタ: SQL-63（`docs/spec/04-behavior/sql-surface.md`）・SQL-29 (b)・SQL-62・RLS-10 (b)・
RECOVER-1。親 Issue #1874 配下の 4 Issue（#1875 構文 → #1876 書き込み経路での実行 →
Issue #1877 1 文内の可視性・原子性 → #1878 RLS・権限境界テスト）の設計記録を本ファイルに集約する。

## Issue #1875: 構文受理と列解決（実行なし）

CTE 本文に単一表の `INSERT ... VALUES`・`UPDATE`・`DELETE`（各 `RETURNING` 任意）を書ける構文を
受理し、`RETURNING` が外側へ公開する列（名前と並び）を確定する。**書き込みは一切発生させない**。
検証をすべて通過した文も固定文言の `0A000`（`data-modifying CTE is not supported yet`）で止める。
公開 API（`Statement` の variant）は変えない。実行結線は #1876。

### 構成

| 箇所 | 役割 |
| ---- | ---- |
| `sql/allowlist.rs` `parse_data_modifying_cte_body` | 本文先頭が DML なら既存の DML 許可パーサーで解析する（第 2 のパーサーなし） |
| `sql/cte.rs` `CteBody` / `DataModifyingCteBody` | 検証済みの DML 型をそのまま保持（#1876 の実行器が再構築なしで受け取る） |
| `sql/cte.rs` `validate_data_modifying_cte` | 対象表の確認と `RETURNING` 公開列の確定（列名リストの改名を含む） |
| `sql/allowlist.rs` `WITH` 分岐 | 定義順に検証し、主クエリの列スコープを既存検査へ通し、最後に `0A000` |
| `sql/statement_splitter.rs` | データ変更 CTE を含む `WITH` を `Write` に分類（fail-closed） |

### 拒否コード

| 入力 | コード |
| ---- | ------ |
| 本文の構文誤り、副文の `USING OPERATION_ID`・`PARTITIONED`、本文内の `;` | `42601` |
| 主クエリが DML（`WITH ... INSERT ...`） | `42601`（従来どおり） |
| 対象表なし | `42P01` |
| `RETURNING` に存在しない列 | `42703` |
| 主クエリが `RETURNING` に無い列を参照 | `42703`（既存 CTE と同じ） |
| 列名リストが `RETURNING` の列数より長い | `42P10` |
| 定義数・連鎖の上限超過（データ変更 CTE も数える） | `54000` |
| 検証を通過した文・`RETURNING` なしの参照・`INSERT ... SELECT`・`UPDATE ... FROM`・`DELETE ... USING`・ビュー／CTE が対象・SELECT 本文 CTE からの参照・列情報を返せない lookup | `0A000` |

### 不変条件

- `resolve_relation` はデータ変更 CTE の名前に一致したとき、表・ビューへ展開せず固定 `0A000` を返す
  （同名の実表を RLS の暗黙適用を迂回して読む経路を作らない）
- `CteDef` はテナント・`PolicyContext` を保持しない（RLS-10 (b)）。エラーはテナント間で同一
- `operation_id` の必須化は文単位の判定で、副文ごとには呼ばない（副文は `LedgerMode::Optional` で解析）

### 後続への引き継ぎ

- 実行・`RETURNING` 行の具体化・型付き列メタデータ・Describe（#1876）、可視性・原子性（#1877）、境界テスト（#1878）
- `INSERT ... SELECT`・`UPDATE ... FROM`・`DELETE ... USING` 本文、ビューや一時表が対象の本文、
  SELECT 本文 CTE からの参照、主クエリが DML の形は未対応
- 副文の `INSERT` の行数上限（`max_insert_rows`）は検証段では適用されない。実行結線時に必ず適用する
- `WITH RECURSIVE` 内のデータ変更 CTE の扱いは再帰 CTE の実装後に確認する

## Issue #1876（書き込み経路での実行）

ポインタ: SQL-63 (1)〜(6)・RECOVER-1・RECOVER-11・RLS-9・RLS-10 (b)。親 #1874、後続 #1877（文内の可視性・
同一行の多重変更・失敗時動作）・#1878（RLS・権限の境界テスト）。

### 経路

| 入口 | 役割 |
| ---- | ---- |
| `sql::allowlist::validate_session_with_tokens` | 最上位の文だけが呼ぶ。`parse_with_clause` の結果でデータ変更 CTE を検出し、実行計画 `ValidatedDataModifyingCte` を返す（第 2 の検出器を作らない）。読み取り入口（`validate_sql_tokens`・cursor・COPY・CREATE VIEW・CTAS・EXPLAIN・サブクエリ内側）は従来どおり検証後に固定 `0A000` |
| `ParsedSql::DataModifyingCte` | `ParsedSql::Statement`（読み取り専用）に載せない。wire 側が非書き込みと誤判定して commit 後の失敗を包み損ねないため |
| `core/dm_cte_exec.rs` | 事前照合 → 副文を定義順に実行 → 台帳記録 → 主クエリの外側処理。副文は単独 DML と同じ `execute_*_returning_form` を通す |
| `view_buffered::plan_outer_parts` | 評価後射影形ビューと同じ外側処理（Describe と Execute が同じ入口） |

### 実行する形（ゲート）

検証段（書き込みトランザクションを開く前）で判定し、それ以外は固定 `0A000`（表は変わらない）。

| 形 | 扱い |
| ---- | ---- |
| データ変更 CTE が 1 つで、主クエリの FROM がその CTE（`RETURNING` あり） | 実行 |
| データ変更 CTE が 2 つ以上 | #1876 時点は `0A000`。Issue #1877 で実行する形になった（下の「Issue #1877」節） |
| 主クエリの FROM が実表・ビュー・SELECT 本文 CTE | #1876 時点は `0A000`。Issue #1877 で実行する形になった（同上） |
| `RETURNING` なしの副文を参照 | `0A000` |
| 一時表が対象 | `0A000`（`temp_route` が振り分け対象外として拒否。一時コアへ流さない） |

### トランザクション

- autocommit は `execute_subquery_dml_autocommit` と同じ文単位の暗黙トランザクションで実行する。副文ごとの
  autocommit では原子的にならず、`WriteTarget::InTxn` を直接使うと遅延 `FOREIGN KEY` 検査が抜けるため、
  `commit_implicit` を通す。明示・暗黙トランザクションは共有 write txn 上で実行し、書いた全表へ `mark_written` する
- 失敗（副文の制約違反・主クエリのエラー・行数上限超過）は txn の abort で全体が破棄される

### 台帳（文単位 1 エントリ）

- 文末の `USING OPERATION_ID '<id>'` を主クエリから切り離して受理する（副文内の指定は従来どおり `42601`）。
  `--require-operation-id` 構成での省略・`NULL` は検証段で `23502`
- 文ハッシュは `OpTag::DataModifyingCte`（= 29）で、送られた文のトークン列だけが材料（結果行の値は含めない）。
  再送は最初の副文を実行する前の事前照合で `23505`、別内容は `22023`
- 副文は `operation_id` を持たないため、副文の実行中だけ台帳モードを「省略可」へ切り替える
  （`SubstatementLedgerScope`。`Ledgered` のままだと副文が `23502` になる）。副文は台帳に触れない
- 台帳・世代の単位は「定義順で最初のデータ変更 CTE の対象表」に決定的に固定する。同じ `operation_id` を同表へ
  直接 DML で再送した場合は別ドメインのハッシュで `22023` になる

### 対象外（後続）

- 文開始時点の可視性、同一行を複数の副文が変更する場合の順序、複数のデータ変更 CTE、
  主クエリが実表・ビュー・SELECT 本文 CTE を読む形（#1877。実装済み。下の「Issue #1877」節）
- RLS・権限の境界テスト（#1878）。DML 単位の権限検査（SQL-40 相当）は現状実装がなく、本 Issue では副文が
  単独 DML と同じ経路を通ることだけを保証する
- 主クエリが DML の形、`INSERT ... SELECT`／`UPDATE ... FROM`／`DELETE ... USING` 本文、ビュー・一時表が対象の本文、
  `WITH RECURSIVE` 内のデータ変更、拡張クエリの `$n`、NoSQL 表層（従来どおり拒否）

## Issue #1877（1 文内の可視性・失敗時の動作）

ポインタ: SQL-63 (1)(2)(4)・RECOVER-1・RECOVER-11・RLS-10 (b)。親 #1874、前段 #1875（構文）・#1876（書き込み経路）、
後続 #1878（RLS・権限の境界テスト）。意味は PostgreSQL 17 に揃える。

### 意味

| 項目 | 契約 |
| ---- | ---- |
| 可視性 | 全副文と主クエリは文の開始時点の状態を読む。互いの変更は `RETURNING` を通したときだけ見える |
| 同じ行を複数の副文が変更 | `WITH` に書いた順に実行する。後の副文は、先の副文が挿入・更新・削除した行に触れない（本 DB は順序を決定的に固定する） |
| 原子性 | 副文または主クエリのどこかでエラーなら文全体を取り消す。autocommit は暗黙トランザクションを破棄し、明示トランザクションは `Failed` へ遷移する |
| 行数の上限 | `--max-affected-rows` などは副文ごとに判定する。超過は `54000` で、他の副文の書き込みも取り消される |

### 実行の段（エラーの優先順位もこの順）

1. 外側の事前計画（束縛エラー）と実行形のゲート。いずれも書き込み前
2. 台帳の事前照合
3. 段 A: 全副文の `WHERE` サブクエリを定数の述語へ解決する（共有 write txn の現在の状態＝文の開始時点）。
   解決結果はフォーム関数へ渡し、フォーム関数の内側で再び解決されない。台帳ハッシュは解決前の文から出す
4. 段 B: 主クエリが実表・ビュー・SELECT 本文 CTE を読む形は、ここで実体化する（`execute_read_statement_with_limits`）。
   共有 write txn を読み取り源にするため、明示トランザクションの先行文の未 commit の書き込みは見え、本文の副文の
   書き込みは見えない。結果行の上限超過（`54000`）は副文を 1 つも実行する前に確定する
5. 段 C: 副文を定義順にすべて実行する。参照されない副文・`RETURNING` なしの副文も実行する。単独 DML と同じ
   フォーム関数を通す（第 2 の書き込み経路を作らない）
6. 台帳記録 → 主クエリの結果（副文を読む形は `RETURNING` 行に外側処理を適用、実表を読む形は段 B の結果）

redb の読み取り txn を文の開始時に別途開く方式は採らない。明示トランザクションでは文の開始時点の状態に
同じトランザクションの未 commit の書き込みが含まれる必要があり、新しい read txn には見えないため。
既存の前例（`INSERT ... SELECT`・述語形 DML のサブクエリ）と同じく、読み取りはすべて最初の書き込みより前に
済ませる。

### 文内変更集合（`tenant/statement_writes.rs`）

書き込み前に済ませられない読み取りは、後の副文が対象行を選ぶ候補の列挙だけである。ここを次で補正する。

- 副文の実行区間だけ張る RAII スコープ（スレッドローカル）が、先の副文が書いた `(表, id)` を保持する
- 記録: 行の挿入（`insert_unique_row`）・更新（単一行・述語形）・削除（単一行・述語形）の書き込み点。スコープが
  無いときは何もせず、通常の DML の挙動はビット同一
- 除外: 述語形の候補列挙（`enumerate_dml_candidates_with`）と単一行の `id` 指定の更新・削除で、記録済みの行を
  「無い」ものとして扱う。結果は影響 0 行で `RETURNING` にも出ない。除外した行は `max_affected_rows` に数えない
  （走査行数には数える）
- 正しさ: 行の現在の状態が開始時点と違うのは、先の副文が触れた行だけで、そうした行は仕様上どの後続副文も変更
  しない。したがって「現在の状態から記録済みの行を除いたもの」は「開始時点の状態から先の副文が触れた行を
  除いたもの」と一致する。先の副文が挿入した行は記録済みなので除外され、削除された行はもう存在しない
- 一意性・`FOREIGN KEY` の検査は現在の状態に対して行う（既存の挙動・PostgreSQL と同じ）

決定的に定めた事項:

| 場合 | 結果 |
| ---- | ---- |
| 先の副文で削除した id を、後の INSERT 副文が再び使う | 削除は反映済みなので成功 |
| 2 つの INSERT 副文が同じ id を使う | `23505` で文全体を取り消す |
| 先の副文で更新・削除した行を、後の副文が UPDATE／DELETE する | 後の副文は 0 行・`RETURNING` に出ない |
| 先の副文で挿入した行を、後の副文が UPDATE／DELETE する | 対象にならず、挿入した行は残る |

### 実行形のゲート（Issue #1877 後）

| 形 | 扱い |
| ---- | ---- |
| 副文 1 つ以上。主クエリが副文（`RETURNING` あり）を FROM に読む | 実行（全副文を定義順に実行） |
| 副文 1 つ以上。主クエリが副文を読まず実表・ビュー・SELECT 本文 CTE を読む（単一リレーション） | 実行（主クエリは段 B で文の開始時点の状態を読む） |
| 参照されない副文（`RETURNING` の有無を問わない） | 実行 |
| `RETURNING` なしの副文を参照 | `0A000`（PostgreSQL と同じ） |
| JOIN の主クエリで副文を含む | `0A000`（維持） |
| 副文が 2 つ以上で、対象表が `FOREIGN KEY` の参照アクション（`CASCADE`／`SET NULL`／`SET DEFAULT`）の参照先 | `0A000`（新設。後述） |
| `ON CONFLICT` 付き INSERT 副文が他の副文と同じ表を対象にする | `0A000`（新設。衝突判定が先の副文の変更を見てしまい、可視性を保証できない） |
| 一時表が対象、または主クエリが一時表を読む | `0A000`（`temp_route`） |
| 最上位以外・`WITH RECURSIVE`・副文ごとの `USING OPERATION_ID`／`PARTITIONED` | 既存の拒否を維持 |

参照アクションのゲートの理由: 参照アクションが書く子行（`constraint.rs` の連鎖）は文内変更集合へ記録していない。
記録しないまま複数副文を実行すると、後の副文が連鎖で変更された子行を再び変更でき、順序が定まらない。誤った順序の
まま出荷しないため（fail-closed）、書き込み前に固定文言の `0A000` で拒否する。副文が 1 つの文は従来どおり実行する
（順序の問題が無い）。判定は `referencing_foreign_keys_in_txn`（対象表を参照先とする FK の参照アクション）で、
書き込みトランザクションの中・最初の書き込みより前に行う。

### 台帳・テナント境界

- 台帳は文単位で 1 エントリのまま。台帳・世代の単位は定義順で最初の副文の対象表。再送は何も実行せず `23505`
- 副文の台帳モード切替（`SubstatementLedgerScope`）は段 A の事前解決にも張る。`precheck_subquery_dml_ledger` が
  `self.ledger_mode` ではなく `dml_ledger_mode()` を見るようにし、`--require-operation-id` の構成で `WHERE` に
  サブクエリを持つ副文が `23502` になる不具合を直した
- 副文・主クエリ・事前解決するサブクエリはすべて書き込むセッション自身の `PolicyContext` で既存の経路を通す。
  文内変更集合は自テナントの行だけを記録し、除外の判定もテナントの名前空間の中で閉じる。エラー文言は固定で、
  行の値・他テナントの存在を含めない（RLS-10 (b)。境界テストは #1878 で実施済み）

### 対象外（追跡候補）

- JOIN の主クエリで副文と実表を組み合わせる形
- 衝突の判定まで文開始時点の意味に揃えた ON CONFLICT 副文と、同じ表を対象にする他の副文との組み合わせ
- 参照アクションが関わる表に対する複数副文（子行の変更も文内変更集合へ記録すれば解除できる）
- 主クエリが DML の形、`INSERT ... SELECT`／`UPDATE ... FROM`／`DELETE ... USING` の本文、
  `WITH RECURSIVE` の中のデータ変更（#1876 から引き継ぎ）

## Issue #1878 RLS・権限の境界テスト

ポインタ: RLS-10・SQL-63。関連: SQL-40（未実装）・SQL-23・RECOVER-1・RECOVER-11・TABLE-27。engine 本体は変更しない。
`crates/engine/tests/rls10_data_modifying_cte_paths.rs` を新設し、単独 DML のマトリクス
（`rls10_write_constraint_paths.rs`）と同じ流儀で、データ変更 CTE を閲覧テナント 3 つ × 可視性 2 モード ×
実行経路 2 つ（autocommit／明示トランザクション）× 形で検査する。

### 検査軸

| 軸 | 内容 |
| -- | ---- |
| T0 | 各モードで陽性対照（行を返す・制約違反・`0A000`）が発生する |
| T1 | 返却 id・`wire_code` を真実値と照合。副文の本文を単独 DML として同じモードで実行した結果（返却 id・`wire_code`・自テナントの事後状態）と一致 |
| T2 | baseline（閲覧テナントの行のみ）と flooded（他 2 テナントの行を衝突させて追加）で応答と自テナントの事後状態が一致。他テナントにだけ値がある場合はどこにも無い場合と同じ応答 |
| T3 | flooded の他テナントの行が全表で事前・事後に一致（構造同値＋FNV フィンガープリント） |
| T5 | 影響行数の上限を該当件数ちょうど（成功）・1 少なく（`54000`）にし、副文ごとに判定されること、主クエリの結果行数上限も他テナントの行で動かないこと |
| T6 | 捏造した違反（行の書き換え・削除・トークン混入）を検査器が検出する |
| T7 | autocommit と明示トランザクションで応答・事後状態が一致（エラー時は `Failed` 遷移・`COMMIT` は `25P02`） |

### 「権限」の解釈

engine にあるのは DDL 実行権限（`SessionState::ddl_allowed`）だけで、オブジェクト単位の権限（SQL-40）は未実装。
そのため次の 3 軸で検証した。

- P1: DDL 権限の有無で、データ変更 CTE の応答・自テナントの事後状態・他テナントの行が変わらない（DDL 権限は RLS を広げない）
- P2: `CREATE VIEW／TABLE／MATERIALIZED VIEW ... AS WITH <データ変更>` と、CTE 本文が DDL・`TRUNCATE` の形は、DDL 権限の
  有無を問わず成功せず、書き込みゼロ・応答は他テナントの行に左右されない
- P3: 可視性モードが書き込み対象の軸になる。Public のみのモードでは自テナントの Private 行は UPDATE／DELETE の対象外、
  衝突先が見えない UPSERT は `42501`、INSERT 副文は制約検査より前に `XX000`（単独 DML と同じ）

### 実測で確定した事項

- 主クエリが `docs` のような共有可視な表を読む形は、他テナントの Public 行が読み取りで可視（RLS-10 の読み取り規則）なため
  応答の完全一致ではなく「他テナントの Private トークンが出ない」で検査する。段 A のサブクエリは他テナントの追加行を
  Private にして応答の完全一致を保つ
- 他テナントの SCHEMA 修飾の対象は存在しない SCHEMA と同じエラー形で、所有テナントの行は変わらない
- 台帳キーはテナントごと（他テナントが使った `operation_id` を使っても成功し、同じテナントの再送は `23505`）
- Public のみモードの INSERT 副文は常に `XX000` で、制約違反の `wire_code` は Public＋Private モードで検査する
- 本テストの範囲で engine の欠陥は見つからなかった

### 対象外（追跡候補）

- SQL-40（オブジェクト・列単位の権限を副文ごとに検査すること）: 実装時に本マトリクスへセルを追加する
- wire-server 経由・NoSQL 表層の越境、レイテンシの統計的な区別不能性（専有環境での計測の担当）
