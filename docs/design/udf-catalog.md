# UDF カタログのスキーマと保存形式（Issue #1919）

親 Issue #1918（UDF の永続化）の土台。ビヘイビア ID は SQL-66（関連: SQL-9・SQL-67 (3)・
TABLE-27・RLS-12・TASK-309）のポインタ表記のみで参照し、spec 本文は転記しない。

## 範囲

- #1919: redb のテーブル定義、定義 blob の版付き保存形式、crate 内部の保存・読み出し API
  （`crates/engine/src/catalog/function.rs`）。
- #1920: `CREATE FUNCTION`／`DROP FUNCTION` からの書き込み（下記「書き込み経路」）。
- #1921: セッション開始時のロードと他セッションの変更の反映（下記「ロード経路」）。
- #1922: 件数上限の起動時設定と DDL 権限との整合（下記「上限の設定と権限」）。
- #1917: `DROP FUNCTION [IF EXISTS] ... [CASCADE | RESTRICT]` と `CREATE OR REPLACE FUNCTION`（下記）。
- 範囲外: 多重定義の解決規則。

## テーブル

| 表 | キー | 値 |
| -- | ---- | -- |
| `functions` | `(scope, function_key, arg_signature)` | 定義 blob |
| `function_id_counter` | 固定キー `next_id` | `u64`（1 始まり・再利用しない） |

どちらも最初の書き込みまで作らない（遅延作成）。読み取りは表の不在を 0 件と扱うため、UDF を
使わない DB や本変更前の DB のファイル構成・既存カタログの値は変わらない。

## キー設計

- `scope`: 可視範囲の所有者。本 Issue では検証済みの `tenant_id` のみ受理する。キーの先頭に置くため、
  他テナントの定義は構造上引けない（RLS-12 の境界）。
- `function_key`: relation キー形（`public` は裸の名前、SCHEMA 配下は `#<schema_id>.<name>`）を
  ASCII 小文字へ正規化したもの。
- `arg_signature`: 多重定義を別キーにするための引数型の並び。各引数を typmod・配列の最大長と次元を
  落とした型トークンへ写して `;` で連結する（型注釈なしは `?`、引数 0 個は空文字列）。decode 時に値から
  再計算して一致を検査する。

## 定義 blob v1

リトルエンディアン。文字列は `u32` 長 + UTF-8。

```text
u8 version(=1) / u64 id / u8 owner(予約=0) / u8 language / u8 volatility / u8 flags
/ u8 parallel / cost(u8 有無 [+ f64]) / rows(u8 有無 [+ f64])
/ u32 引数数 { name(u8 有無 [+ str]) / type(u8 有無 [+ str tag + str param]) }
/ return type(同上) / str 本体の原文
```

- 版の運用: 未知の版は拒否する（`CorruptSchema`）。形式を変える場合は新しい版を足し、v1 の decode を
  残す。ゴールデンバイト列のテストで v1 を固定している。
- 型は `ColumnType::catalog_fields` の `(tag, param)` 1 対で持つ。ENUM は本 Issue では encode・decode
  とも拒否する。受理に広げても `(tag, param)` のバイト表現は変わらないため、版を上げずに解禁できる。
- 上限: 引数 100（格納形式上の上限）・本体 64 KiB・スコープあたり 64 件（`ViewLimitExceeded`）。長さ・件数は
  確保の前に検査する。

## fail-closed

未知の言語／揮発性／parallel タグ、未定義の flag ビット、owner 予約領域の非零、id=0、切断、末尾の余り、
上限超過、不正 UTF-8・識別子・型、キーと値のシグネチャ不一致はすべて固定文言の `CorruptSchema`。
blob の断片・tenant_id・本体の原文はエラー文言へ出さない。

## 書き込み経路（Issue #1920）

`CREATE FUNCTION`／`DROP FUNCTION` をカタログへ結線した（実行本体は `sql/udf_ddl.rs`、呼び出し元は
`core.rs`）。

- **判定順（CREATE）**: 構文（`AS` 以降のトークン列を `lexer::render_tokens` で描画し `body_source` にする。
  CREATE VIEW の `body_sql` と同じ規約。名前解決後のトークンのため SCHEMA 配下は `#<id>.f` 形のまま。
  描画不能・上限超過は拒否）→ `prepare_function_definition`（予約名・識別子・引数・閉じた本体。レジストリ
  不変）→ セッションに同名があれば `42723` → `Storage::create_function`（単一 write txn・1 回の commit。
  同名の定義があれば `42723`・件数上限 `54000`）→ commit 成功後にレジストリへ登録。カタログで失敗した
  場合セッションは変わらない。
- **DROP**: `DROP FUNCTION [IF EXISTS] <名前> [(<型>, ...)] [CASCADE | RESTRICT]`（複数名は `0A000`）。
  カタログ（DDL 権限ありのときだけ）とセッションのレジストリの両方から消し、どちらでも消えなかった場合
  だけ `42883`（他テナントの定義も同じ。存在情報を出さない）。`IF EXISTS` なら代わりに `skipped` の成功
  （他テナントの定義・不在は同じ応答。コマンドタグは `DROP FUNCTION`。NoticeResponse は他の `IF EXISTS` と
  同じく未送出）。権限の無いセッションがカタログ由来の定義を消そうとすると `IF EXISTS` でも `42501`。
  型の並びは引数の数と、型注釈のある引数の型で照合する（型注釈なしの引数は任意の型に一致）。
- **依存（Issue #1917）**: 関数に依存できる永続オブジェクトは TRIGGER だけ（ビュー・索引・CHECK は作成時に
  組み込み以外の関数呼び出しを拒否する）。`RESTRICT`（既定）は依存トリガがあれば `2BP01`、`CASCADE` は
  関数の削除と同じ write txn で、同じテナントの依存トリガだけを消す（影響した表の世代も進める）。
- **OR REPLACE（Issue #1917）**: 同名が無ければ新規作成。あれば引数の数・型注釈・引数名・戻り値型が同じ
  場合だけ、**同じ内部 ID のまま**本体を置換する（単一 write txn・1 回の commit。commit 後にレジストリを
  上書きし、他セッションは世代で読み直す）。引数名・戻り値型（`RETURNS` の有無を含む）の変更は `42P13`、
  引数の数・型が違う同名の再定義（多重定義）は未対応のため `42723`、組み込み・予約名は `42723`。権限の無い
  セッションの置換は保存先の振り分けより前に `42501`（Issue #1922）。型付き・`RETURNS` つきの置換も同じ規則で永続化する
  （Issue #2798）。
- **循環の拒否（Issue #1917）**: 置換は `f -> g -> f` の呼び出しの循環を作れるため、新しい本体が置換対象へ
  推移的に到達するなら `0A000` で拒否する（インライン展開の無限再帰を作らない）。`CREATE` は追記専用で
  循環しない。複数セッションの競合で循環が永続化されても、ロードは呼び出し先が先に登録できない定義を
  読み飛ばす（既存の「恒久的にロード不能」の扱い）ため展開されない。
- **42725**: 名前だけの DROP が複数の候補に当たったときの SQLSTATE（`ambiguous_function`）。現状は作成時に
  同名の多重定義を拒否するため通常は起きない防御で、カタログの単体テストで固定する。
- **権限**: `session.ddl_allowed()` のときだけカタログへ書く。権限が無いセッションの `CREATE`／`DROP FUNCTION` は
  拒否される（`42501`。保存先の振り分けより前に検査する。下記「上限の設定と権限」）。
- **多重定義**: 同名の定義がカタログに 1 件でもあれば、シグネチャが違っても `42723`。`UdfRegistry` は名前
  単位でしか持てず、書けても読めない状態を作らないため。名前だけの DROP が常に一意に解決できる。
- **明示トランザクション**: DDL 権限ありのセッションの `CREATE`／`DROP FUNCTION` は `0A000`（ROLLBACK で
  取り消せない書き込みを txn 内で行わない）。権限なしのセッションは `42501`（権限検査が先。#1922）。
- **DROP SCHEMA との連動**: `RESTRICT` は配下に関数があれば `2BP01`。`CASCADE` は同じ write txn で配下の
  関数行（自テナント・自 SCHEMA の接頭辞）も消す。残すと内部キーを書けない利用者が DROP できない孤児になる。
- **crash 耐性**: 新しい crash-test ジョブは足さない。CREATE／DROP はいずれも単一 write txn の 1 回の
  `commit_boundary::commit` で、CREATE VIEW・SEQUENCE と同じ保証になるため、再オープンを検証する
  in-process テスト（`tests/sql_t40_up/sql66_udf_catalog_write.rs`）で足りる。
- **public の共有**: 見送り（テナント単位を維持）。全テナント共有は予約 scope（空文字列）で後から足せ、
  blob 形式は変わらない。spec 側の確認事項。
- **スコープ外の扱い**: ENUM 型は解禁せず、カタログが拒否した場合は `0A000`。
- **型付き引数・RETURNS（Issue #2798。SQL-66・TASK-309）**: 型注釈つきの引数と `RETURNS` も永続化する。
  検証は非 DDL セッションと同じ prepare（`42P13`・`0A000`・`42723`）を先に通し、通った定義だけを書く。
  - 写像: UDF シグネチャの型（`CastType`）は `result_column_type` 経由の `(tag, param)` で保存する。blob の
    符号化は v1 のままで、版は上げない（型フィールドは v1 が元から持つため新しいバイト表現が要らない）。
  - numeric の正規化: 構文段は `numeric(p,s)` を修飾子なしへ正規化するため、保存値は `numeric(38,16)` に
    なり、ロード側が `Numeric(None)` へ戻す。`DROP FUNCTION f(numeric)` は識別トークン（typmod を落とした形）で
    照合するため一致する。
  - `DROP FUNCTION f(<型>)` のセッション内定義の照合もカタログ側と同じ規則（型注釈のある引数は識別
    トークンで比べる）にする。不一致は不在と同じ扱い（`42883`／`IF EXISTS` は `skipped`）で、存在情報を出さない。

## ロード経路（Issue #1921）

実装: `crates/engine/src/sql/udf_load.rs`。`EngineCore::load_session_udfs`（開始時）と
`refresh_session_udfs`（Query／Parse の前）が薄いラッパー。

- 対象: 認証済みテナントの scope だけ。DDL 権限の有無を問わずロードする（呼び出しに DDL 権限は要らない）。
- 再パース: `body_source` を `tokenize_rendered` で字句解析し、`CREATE FUNCTION` と同じ式文法で再パースして、
  作成時と同じ検証（`prepare_function_definition`。予約名・閉じた式・上限）を通す。
- 登録順: `id` 昇順で試し、失敗した定義は次のパスへ回す（呼び出し先を DROP して作り直すと id が逆転するため）。
  進捗が無くなれば終了し、パス数は `MAX_FUNCTIONS` が上限。
- 出所: レジストリはカタログ由来の名前を覚える。権限の無いセッションがカタログ由来の関数を `DROP FUNCTION`
  すると `42501`（呼べる関数に `42883` は事実と食い違うため）。#1922 以降は権限なしの `CREATE`／`DROP` が
  一律 `42501` のため、この出所は置換・衝突の判定とロード時の入れ替えに使う。
- 型付き行（Issue #2798）: 型付き引数・`RETURNS` の行は、保存値が書き込み経路の正規形に往復一致する
  場合だけ復元する（`varchar(n)`・`numeric(p,s)`〔`38,16` 以外〕・`bpchar`・`vector`・ENUM は skip）。
  旧形式の扱い: 型なしの v1 行は従来どおりロードし、未知の版はテナント全体のロードが `XX000`。新しいバイナリが
  書いた型付き行を旧バイナリが読んでも、その行を個別に skip するだけでロード全体は失敗しない。
- 失敗の扱い（2 層）:
  - カタログ全体が読めない（blob 破損・I/O）: ハンドシェイクは `AuthenticationOk` の後に FATAL `XX000`
    （固定文言）を返して切断する。refresh ではカタログ由来を全部消し、次回再試行する。
  - 1 件の定義が登録できない（再パース失敗・予約名との衝突・呼び出し先の消失・レジストリで表せない形
    〔`language` が Declarative 以外・書き込み経路の正規形に往復しない型・型注釈の混在・型なし引数つきの
    戻り値型〕）: その定義だけ登録しない（呼ぶと `42883`）。行は
    カタログに残り、DDL セッションが `DROP FUNCTION` で消せる。skip したことを知る手段は限られる。
- テナント束縛（P0）: レジストリがロード時の scope を記録し、別テナントの ctx での呼び出しは何もロードせず
  カタログ由来を全部消す。
- 世代: `Storage` がテナント単位の世代をメモリ上に持つ（永続化しない。redb は単一プロセスが占有し、再起動後は
  全セッションが開始時にロードするため）。`CREATE`／`DROP FUNCTION`・`DROP SCHEMA ... CASCADE` の commit 成功後に
  進める。読み取り側は世代を先に読んでから一覧するため、競合しても次の確認で必ずリロードされる。
  `BEGIN` 時のセッション複製が `ROLLBACK` で古い世代へ戻っても、次のメッセージで再びリロードされるだけで害はない。
- 適用範囲: ロードを結線するのは pg wire のハンドシェイクだけ。HTTP（NoSQL）表層はリクエストごとに
  `SessionState::default()` を作るため変えない。

## 後続への申し送り

- 共有 `public` の扱い: 上記のとおりテナント単位を維持。共有する場合は spec 側の確認が要る。
- ENUM 型の引数・戻り値の解禁（形式は不変）。
- `sql::udf_call::MAX_UDF_PARAMS`（32）は構文段で先に効き、格納上限 100 の内側に収まる。100 と `54023` への
  引き上げは #1917／#1922。
- #1921（ロード）: 実装済み（「ロード経路」）。準備済み文（Parse 済み）が他セッションの DROP の後に
  陳腐化する件は未対応（refresh は Query／Parse の時点だけ）。
- `MAX_SESSION_UDFS`（64）と `MAX_FUNCTIONS`（64）は等しく、カタログが満杯だと WASM 等のセッション内の登録を
  入れる余地が無い。#1922 の CLI 設定はこの 2 つのハード上限を超えない範囲（下げる方向のみ）に限り、
  両者は同じ値で動かす。
- #1917: 実装済み（「書き込み経路」）。残り: 多重定義（引数の型の並びが違う同名関数）の保持・呼び出し時の
  解決規則・呼び出し時の `42725`（型付き引数・`RETURNS` の永続化は #2798 で実装済み）。複数名の
  `DROP FUNCTION f, g`・`IF EXISTS` の NoticeResponse も未対応。
- #2798: 型付き引数・`RETURNS` の永続化・ロードは実装済み。残り: ENUM 型の解禁、numeric 引数の呼び出し時の値変換
  （現状 `0A000`）、`LANGUAGE sql`／`plpgsql` の UDF の永続化。
- 引数上限（100 個・`54023`）は #1917 または別 Issue。#1922 では扱っていない。

## 上限の設定と権限（Issue #1922）

- フラグ `--max-functions <1-64>` は 1 本で、カタログ経路（`MAX_FUNCTIONS`）の書き込み判定に値を渡す。
  値は全テナントで共通。
- **下げる方向のみ**: 読み取り側（一覧・削除対象の列挙・ロードのパス数）はハード上限超過を
  `CorruptSchema` として fail-closed に扱うため、上げる設定は正常な DB を破損扱いにする。範囲は
  `engine::function_limits::validate_max_functions` に一元化し、`FunctionLimits::new` と
  `create_function_with_limit` で飽和させる。
- **ロードには適用しない**: ハード上限で判定し、上限を下げて再起動しても既存の関数は読める・呼べる
  （SQL-46 (5)）。
- 判定順は変えない（名前・予約名 → 重複 `42723` → 件数 `54000` → 引数数 → 本体）。上限に達していても
  同名の再定義は `42723`。
- **権限**: DDL 権限の無いセッションの `CREATE FUNCTION`（`OR REPLACE`・型付き引数・RETURNS を含む）と
  `DROP FUNCTION`（`IF EXISTS` を含む）は、カタログ経路・セッション限定経路のどちらにも触れず `42501`
  （fail-closed）。検査は保存先の振り分け・本体の検証・重複判定のいずれよりも前で、明示トランザクション内でも
  `0A000` より先に効く（`sql::ddl::require_ddl_permission`）。`IF EXISTS` でも `42501` にして、対象の有無を
  権限の無いセッションに区別させない。ロード済み（カタログ由来）の関数の呼び出しは権限によらず可能。
- **契約の変更**: SQL で作る UDF は、DDL 権限のあるセッションがテナントのカタログへ書く永続定義だけになった
  （旧: 権限なしセッションのセッション限定の登録。型付き引数・RETURNS 付きも #2798 で永続化される）。永続定義は
  同じテナントの別セッションからロード・refresh で見え、他テナントからは不在と同じ `42883`。判定順は権限
  `42501` → 重複 `42723` → 件数 `54000`（件数はテナントのカタログ件数）。`DROP FUNCTION` はカタログから消し、
  レジストリにあるカタログ外の定義（WASM UDF など）も消す。明示トランザクション内の `CREATE`／`DROP FUNCTION`
  は永続化する形が `0A000`。
  `CREATE OR REPLACE FUNCTION`（#1917）も、同名が無く新規作成になる場合は同じ上限で判定する。
  既存定義の置換は件数を増やさないため設定上限を判定しない（上限を下げて再起動した DB でも既存関数の置換は
  通る）。
- **永続定義の依存**: 永続定義（`CREATE`／`OR REPLACE`）が、セッション限定の関数（SQL では作れず、公開 API の
  `define_function` で登録したカタログ由来でない宣言的 UDF・WASM UDF）へ直接・推移的に依存する場合は `0A000`（別接続・再起動後に呼び出し先が無くロードで読み飛ばされる
  ため。永続化できない形の既存拒否と同じコード）。拒否時はカタログもレジストリも変わらない。
  セッション限定の定義がカタログ関数を呼ぶのは許可。
- 結合テストは `crates/engine/tests/sql_t40_up/sql66_udf_limits.rs`、CLI の外形は
  `crates/wire-server/tests/wire_cli/wire_function_limits_cli.rs`。
