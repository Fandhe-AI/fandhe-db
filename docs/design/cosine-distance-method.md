# ADR: コサイン距離の実装方式（正規化帰着かノルム併用か）

- ステータス: Proposed（オーナー確認待ち。承認は得ていない）
- 対応: Issue #1986（親 #1985）。後続: #1987（コサインカーネル）・#2240（ゼロノルムの NaN と並び順）・#1988（L1）・#1996／#1999（HNSW の opclass 別処理）
- 関連ビヘイビア: SQL-33、TASK-237／238。判断記録は `docs/spec/04-behavior/records/pgvector-distance-operators-decision-2026-10-10.md`・`docs/spec/04-behavior/records/pg-parity-owner-decisions-2026-10-10.md`。本文は転記しない（[spec-confidentiality](../../.claude/rules/spec-confidentiality.md)）
- 関連コード: `crates/engine/src/isa.rs`（`dot`）、`crates/engine/src/kernel.rs`、`crates/engine/src/hnsw.rs`、`crates/engine/src/gpu_batch/`
- 計測入口: `crates/engine/benches/cosine_method_bench.rs`・`crates/engine/benches/harness/cosine_method.rs`（`make bench-cosine-method`）
- 本 ADR は docs と計測ベンチのみの変更で、production のカーネル・永続形式・依存を変更しない

## 1. 背景

- 現行のコードは「呼び出し側が L2 正規化済みのベクトルを渡せば、内積の降順がコサイン類似度の降順と一致する」前提で作られている。エンジンは格納時に正規化しない。前提の所在は `hnsw.rs` の冒頭コメント、`kernel.rs` のスコア規約、[hotpath-implementation-survey.md](hotpath-implementation-survey.md) の「既採用: 正規化契約」の行である
- SQL-33 の改訂（上記の判断記録）で、`<=>` は「内積の降順」から pgvector と同じ「コサイン距離 `1 - cos` の昇順」へ変わった。ゼロノルムの扱いは NaN で確定している（#2240）
- 本 ADR が決めるのは、距離をどう計算するかという実装方式だけである。ゼロノルムを NaN にして並べる規則（#2240）、L1（#1988）、HNSW の opclass 別処理（#1996／#1999）は扱わない

## 2. 必須条件

次の 3 つを満たさない方式は採用しない（いずれも SQL-33 のポインタ。本文は転記しない）。

1. 正規化していない入力でも、距離の値が pgvector と一致する
2. `SELECT` が入力どおりの値を返す（格納値を置き換えない）
3. 同じ列に対して `<->`・`<#>`・`<+>` が正しい値を返す（1 列に複数の opclass の索引を持てる。#2910）

## 3. 候補

| 記号 | 方式 |
| ---- | ---- |
| A | 正規化済みを前提に `1 - dot(q, x)` を返す（現行契約の延長） |
| B | 保存時に正規化し、格納値を正規化値に置き換える |
| B′ | 原値と正規化値の両方を持つ（B の欠点を避ける変形） |
| C1 | 検索時に 1 パスで `dot`・`‖x‖²`・`‖q‖²` を同時に累積し、ノルムで割る |
| C2 | 行ごとの `‖x‖²` を arena 常駐の派生値として持ち、検索時は `dot` と事前計算値で割る。`row_codec` と catalog の永続形式は変えない |
| C2′ | 格納値は変えず、HNSW の cosine opclass で常駐するコピーだけを構築時に正規化して内積グラフで探索し、最終スコアは f32 の arena から採用式で再計算する。記録のみで、採否は #1996／#1999 が決める |

## 4. 比較

数値は 2026-11-03 の実測（x86_64・AVX2+FMA・論理 10 コア・共有環境）。時間値は参考値で、判定の根拠にしない（第 8 節）。計測は 2000 行・次元 128／768／1536。

### 4.1 精度と必須条件

| 方式 | 必須条件 1（pgvector と値が一致） | 実測（pgvector 0.8.7 との最大絶対差。未正規化 fixture） |
| ---- | ------------------------------- | ------------------------------------------------------ |
| A | 満たさない | 約 4.4e4（反例は次の段落）。Top-10 の一致は 2/10 |
| B／B′ | 正規化値で計算するため条件 1 は満たすが、B は条件 2・3 を満たさない | 範囲の外（B′ は原値を残すので 2・3 を満たす） |
| C1／C2 | 満たす | 約 3.8e-8（Top-10 は集合・順序とも一致） |

- 反例: 行 `[2, 0]`・クエリ `[1, 0]` のとき、pgvector は 0、方式 A は -1 になる（ベンチの `counterexample` と同じ式）
- 正規化済み fixture では A と B′ も差が約 7e-8 以下で、A が成立するのは入力がすでに正規化されている場合に限る
- B′ の誤差は、未正規化 fixture で pgvector との最大絶対差が 1.6e-7 前後（エミュレーションとの比較）。丸めが 2 回（正規化と内積）乗るため、C1／C2 より大きい
- ゼロノルム行は、A と B′ では距離が 1 になり NaN にならない。C1／C2 は NaN になる（pgvector と一致。fixture の 2 行で確認）

### 4.2 メモリ・書き込み・検索コスト

| 方式 | 追加メモリ（1 行あたり） | 書き込みコスト（ns/行、次元 128／768／1536） | 検索コスト（ns/行、min。次元 128／768／1536） |
| ---- | ----------------------- | ------------------------------------------- | -------------------------------------------- |
| A | 0 | 0 | 5.2／43／99（`isa::current().dot`） |
| B′ | 512／3072／6144 B（+100%） | 99／634／1307（正規化と複製） | 6.8／44／156 |
| C1 | 0 | 0 | 54／285／564（第 4.3 節の注意あり） |
| C2 | 4 B（0.78%／0.13%／0.065%） | 12.5／74／179（ノルム² の計算） | 6.5／43／99（`isa` の dot + 事前計算値）。8 レーンの試作 dot では 12.9／73／150 |

- 書き込みコストは、構築・挿入のたびに 1 行あたり 1 回発生する。[ingest-stage-profile.md](ingest-stage-profile.md) の行あたりコストとの比は本 ADR では算出していない（未検証）
- C2 のメモリ増は 10 万行・次元 768 で約 400 KB。行数の上界は `MAX_ARENA_ROWS` で抑えられる
- ベンチは Scattered fixture（未正規化）で、各方式を 9 ラウンド交互に回した。ベースライン構成で 5 プロセス、`target-cpu=native` 構成で 5 プロセスを実行し、どちらも傾向は同じだった（C2 の `isa` dot は次元 768 以上で A と 5% 以内、次元 128 では約 1.3 ns/行 増。C1 の試作は dot の約 5.5〜10 倍）

### 4.3 C1 の計測上の注意

- C1 の試作は safe Rust の 8 レーン配列（`as_chunks`）で、3 本のアキュムレータを同時に更新する。計測ではスカラー逐次のエミュレーションとほぼ同じ速度で、自動ベクトル化が効いていない。`target-cpu=native` でも変わらなかった
- そのため C1 の検索コストは「実装が悪いと遅くなる」ことを示す参考値で、方式そのものの上限ではない。C1 を production に入れる場合は `isa.rs` と同様に `target_feature` ごとのカーネルを書く必要があり、これは C2 には不要な追加コストである
- 原因（ベクトル化されなかった理由）の調査はしていない（未検証）

### 4.4 その他の軸

| 軸 | C1 | C2 |
| -- | -- | -- |
| ゼロノルムの検出 | クエリのたびに行ごとに検出 | arena 構築時に分かる。HNSW の cosine 索引から安価に除外できる |
| 行ごとの O(d) の追加計算 | 毎回（`‖x‖²` を再計算） | なし（事前計算値を使う） |
| キャッシュ整合 | 不要 | arena の世代キャッシュ（[sql-arena-generation-cache.md](sql-arena-generation-cache.md)）と一緒に再構築されるため、追加の仕組みは不要 |
| 永続形式への影響 | なし | なし（派生値のみ） |
| arena を経由しない経路 | そのまま使える | 使えない。同じ式を C1 で計算する |
| GPU バッチ | 融合計算を WGSL に持ち込む必要がある | ノルムバッファを追加で渡す形になる |

## 5. 「一致」の定義と許容差

- pgvector は積和の順序がコンパイラとハードウェアに依存し、ビット一致は定義できない
- 実測では、実 pgvector（0.8.7）の値は f64 累積の厳密値に近く（最大差 2.4e-8〜1.97e-7）、f32 の逐次累積のエミュレーションからは 8.1e-8〜5.6e-7 離れた。C1 は厳密値との差が 3e-8（遠い行）〜2.8e-7（ほぼ重複の行）、pgvector との差が 3.8e-8〜1.86e-7 だった
- 提案する許容差: 距離の絶対差が 1e-6 以下であること。固定 fixture では、許容差内の同点を除いて Top-k の順序が一致すること。値は実測最大（5.6e-7）に余裕を持たせた提案で、規範化するかどうかは spec 側の課題である
- ほぼ重複の行（距離 1e-6 程度）は、全方式で Top-10 が pgvector と一致しない（集合の重なりは 0〜5/10）。距離の差が f32 の累積誤差と同程度になるためで、方式の優劣ではなく許容差内の同点として扱う
- C2 が `‖x‖²` を C1 と同じ累積順の f32 でキャッシュすれば、C1 と C2 はビット一致する。ベンチは全 fixture・全次元で検証し、不一致なら実測値を出さず非 0 で終了する。C2 の検証にはこの照合を使える

## 6. pgvector と同じ値にする式

手順は次のとおりで、#1987 の要件とする。出典は pgvector 0.8.x の `src/vector.c`（版は [hotpath-implementation-survey.md](hotpath-implementation-survey.md) の出典欄と同じ系統）。コードは転記しない。

1. `dot`・`‖a‖²`・`‖b‖²` を f32 で累積する
2. `s = (f64)dot / sqrt((f64)‖a‖² * (f64)‖b‖²)` を計算する
3. `s` を `[-1, 1]` にクランプする（NaN はそのまま通る）
4. `d = 1 - s` を float8 で返す

- 累積を f32 にする理由: f64 で累積すると、巨大値で `‖a‖²` が f32 の範囲を超えたときの inf／NaN の挙動が pgvector と変わるため
- ゼロノルムは `‖a‖² * ‖b‖² = 0` になり、`0 / 0` で NaN になる（#2240 と整合）
- クエリの非有限値を拒否する既存契約（`KernelError::NonFiniteQuery`）は、行側の NaN とは別経路で維持する
- `precision.rs::cosine_similarity`（f64 累積。precision ゲート用）は別の用途で、カーネルからは再利用しない

## 7. 候補ごとの判定

| 方式 | 判定 | 理由 |
| ---- | ---- | ---- |
| A | 不採用 | 必須条件 1 を満たさない（第 4.1 節の反例と実測） |
| B | 不採用 | 条件 2・3 を満たさない |
| B′ | 不採用 | 条件は満たすが、ベクトル領域が +100%（arena 常駐と永続化の両方）で、書き込みのたびに正規化コストがかかり、誤差も C1／C2 より大きい |
| C1 | 準採用（C2 を使えない経路用） | 値は pgvector と一致し、メモリ・書き込みの変更が不要。行ごとの追加計算と、ベクトル化のために専用カーネルが要る点が欠点 |
| C2 | **推奨** | 値は pgvector と一致し、追加メモリは 4 B/行、永続形式は不変、ゼロノルムを構築時に検出できる。C1 とビット一致するため検証も容易 |
| C2′ | 保留 | HNSW 側の判断（#1996／#1999）。f16／SQ8 常駐との相互作用を論点として残す |

## 8. 判定の根拠

- 共有 QEMU 環境の時間値は、[benchmark-judgement-policy.md](benchmark-judgement-policy.md) §5・§6 により採否の根拠にできない。判定は構造的な理由（必須条件の充足・追加メモリ・永続形式への影響・ゼロノルムの事前検出・行ごとの追加計算の有無・キャッシュ整合）で行った
- 実測は参考値として添える。C2 の検索コストが次元 768 以上で A とほぼ同じであることは、構造的な理由と矛盾しない

## 9. 採用方式

**C2（arena 常駐の行ノルム²・永続形式は不変）を推奨する。** クエリのノルム² は検索ごとに 1 回だけ計算する。arena を経由しない経路は同じ式を C1 で計算する。この推奨は Proposed で、オーナーの確認を得ていない。

## 10. 後続 Issue への要件

- #1987: 第 6 節の式でカーネルを実装する。`hnsw.rs` の冒頭コメントと `kernel.rs` の doc comment を、新しい契約に合わせて更新する。ノルム² のキャッシュは arena の可視行の派生値として持ち、他テナントの行の情報を provider へ渡さない（`kernel.rs::SearchInput` の既存契約を維持する）
- GPU バッチ: ノルムバッファを渡す形と融合計算のどちらを採るかを決める。WGSL はこの Issue では変更しない
- #1996／#1999: C2′ の採否と、HNSW の cosine opclass の fixture（[hnsw-search.md](hnsw-search.md) の正規化前提）の扱い
- #2240: ゼロノルムが NaN になる行の並び順
- 許容差（第 5 節）を spec 側で規範化するかどうかは、spec リポ側の課題としてオーナーへ報告する

## 11. 再現手順

1. `make bench-cosine-method`。手動実行専用で、`GITHUB_ACTIONS` 下では拒否される。ベンチは C1 と C2 のビット一致を検証し、不一致なら非 0 で終了する
2. 共有環境の時間値の採取は、プロセスを 5 回以上起動して min と median を比べる
3. 実 pgvector との照合: `BENCH_COSINE_METHOD_EMIT_SQL=1` で fixture（次元 128・各 200 行・4 種）を SQL として stdout、期待値を stderr に出す。一時コンテナ（`pgvector/pgvector:pg17`、pgvector 0.8.7・PostgreSQL 17.11）へ流し、`extra_float_digits = 3` で `<=>` の結果を取って各方式の値と比べた。照合は 2026-11-03 に実施し、コンテナは停止・削除した。差分集計は使い捨てスクリプトで行い、リポジトリには含めない
