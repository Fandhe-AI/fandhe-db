# ts_headline 関数の契約と資源上限の起動時設定（CLI）

## ステータス・対象

- ステータス: 採用（Issue #2125・SEARCH-14 のポインタのみ。spec 本文は転記しない）
- 対象: SQL 組み込み関数 `ts_headline(doc, query[, options])`、フラグ `--max-ts-headline-bytes`／`--max-ts-headline-fragments`
- 先行: 一致範囲の算出は Issue #2124（`sparse::match_span`）。上限の運搬は [sparsevec-limits-cli.md](sparsevec-limits-cli.md)（Issue #2027）と同型
- 後続: NoSQL の `search` の `highlight` 公開と、SQL との一致・RLS／列の権限の網羅的な検証は #2126。検索語パーサ（フレーズ・除外・前方一致・`or`）は #2113 以降（[fulltext-query-syntax.md](fulltext-query-syntax.md)）

## 背景

疎検索・ハイブリッド検索の結果について、一致した箇所を強調した抜粋を返す手段がなかった。LLM のコンテキストへ渡すスニペットとして使えるよう、PostgreSQL の `ts_headline` と同じ名前・オプション・既定値の関数を SQL 表層へ追加した。Issue タイトルにある「escape オプション」は Issue 本文・親 #2123 の方針（`ts_headline` と同じくエスケープしない）により設けない。

## 関数の契約

- 形: `ts_headline(<本文 TEXT>, <検索語 TEXT>)` と `ts_headline(<本文>, <検索語>, <オプション TEXT>)`。結果は `TEXT`。いずれかの引数が NULL なら NULL（STRICT）。設定名を取る形（`regconfig`）と `tsquery` 型は持たない
- 組み込み名として予約される（`CREATE FUNCTION ts_headline` は `42723`）。検索設定に依存する STABLE 関数として扱い、式索引・生成列には置けない（`42P17`）
- 検索語は索引と同じトークナイザで分割した語の集合（任意語）として解釈する。`or`・`-`・`"`・`*` は検索語パーサが入るまで通常の語や区切りとして扱う（現行の疎検索と同じ）

### オプション

PostgreSQL の公開ドキュメントと同じ 8 つ。名前の大小文字は区別せず、同じキーが複数あれば後勝ち。

| 名前 | 既定値 | 意味 |
| ---- | ------ | ---- |
| `StartSel` | `<b>` | 一致語の直前に挿入する文字列 |
| `StopSel` | `</b>` | 一致語の直後に挿入する文字列 |
| `MaxWords` | 35 | 断片あたりの最大語数 |
| `MinWords` | 15 | 断片あたりの最小語数 |
| `ShortWord` | 3 | この長さ以下の語は断片の端にしない |
| `HighlightAll` | false | 真なら本文全体を出力（語数の整合性は検査しない） |
| `MaxFragments` | 0 | 0 は単一断片方式。正なら断片方式 |
| `FragmentDelimiter` | ` ... ` | 断片の区切り |

- 文法は `key = value` をカンマか空白で区切って並べる形。値は引用符なし・`'…'`・`E'…'`・`"…"` の 4 通り（`''`・`""` は引用符 1 文字。バックスラッシュは `\\` の 2 連だけが 1 文字になる）。閉じ引用符の直後は空白かカンマだけを許す
- 整数は前後の空白、符号、10 進、桁間の `_`、`0x`／`0o`／`0b` の接頭辞を受理する。範囲は 32 ビット符号付き整数
- `HighlightAll` は `1`・`on`・`true`・`t`・`y`・`yes`（大小無視）だけが真で、それ以外はエラーにせず偽とする（PostgreSQL と同じ。出力の一致を優先する）
- 区切り文字列（`StartSel`・`StopSel`・`FragmentDelimiter`）は 32,767 バイトまで

### エスケープしない方針

`StartSel`／`StopSel`／`FragmentDelimiter` と本文はそのまま出力し、HTML などのエスケープは**しない**（PostgreSQL と同じ）。結果を HTML として表示する場合は、利用者側（表示する側）で適切にエスケープする責務がある。

### ASCII 制御文字

本文中の制御文字（U+0000〜U+001F・U+007F。TAB・LF・CR を含む）は区切り単位として扱い、語数には数えず、出力にはそのまま写す（置換もエスケープもしない）。オプション文字列中では C の `isspace` の 6 文字（空白・TAB・LF・VT・FF・CR）が区切りで、それ以外の制御文字はキーや値の一部になる。キーに入れば未知のオプションとして `22023` になる。値に入れば区切り文字列としてそのまま使う（端末向けの強調シーケンスなどの用途がある）。エラー文言は固定の英語で、入力を含めないため、制御文字がエラーやログへ入り込むことはない。

## PostgreSQL との一致の基準

- 比較対象は PostgreSQL 17 の `ts_headline('simple', 本文, to_tsquery('simple', 'w1 | w2 | …'), オプション)`。`w1…` は検索語を本 DB のトークナイザで分割した語を `|` で結んだもの
- 一致を保証するコーパスは「ASCII の英字・空白・基本的な句読点（`, . ; : ! ?`）」。結合テスト `search14_ts_headline.rs` の期待値は PostgreSQL 17 の出力を固定した文字列で、生成に使った SQL の形を各期待値の直上に残してある（CI は PostgreSQL に依存しない）。実装時には同じ形の乱数入力 13,000 件を PostgreSQL 17 の実機と比較して出力が全件一致することも確認した
- 次の 4 つは PostgreSQL の既定パーサが別種のトークンとして扱い、本 DB の分割規則と食い違うため一致を主張しない: 数字、ハイフン・アンダースコア、URL・メールアドレス、HTML タグ。アクセント付きラテン文字や全角英数字を語とみなす扱いも同様
- CJK と数字の出力は PostgreSQL と同一であるとは主張しない（PostgreSQL の既定パーサにはバイグラムのモデルがない）。決定的な固定期待値で回帰を固定する
- 選択処理は PostgreSQL 17 の `ts_headline` の公開挙動に合わせて再実装したもので、ソースの移植ではない

## 単位モデル

分割規則は索引・クエリと共通の `walk_tokens` を唯一の真実源とする。バイグラムとユニグラムが重なるため、そのままは単位列にならない。次の手順で、重ならず本文を隙間なく覆う単位列を作る。

1. ASCII 単語トークンと CJK の 1 文字トークンだけを採る（バイグラムは捨てる）
2. 単位の間の隙間（空白・句読点・ASCII 以外の非 CJK 文字・制御文字の連続）を 1 つの区切り単位にする
3. 各単位は、統合済みの一致範囲（`match_spans`）と交われば「一致」とする

語数・`ShortWord` の長さは「単位」「文字数（Unicode スカラー値）」で数える。CJK は 1 文字が 1 語になる。PostgreSQL は `ShortWord` をバイト長で比較するが、ASCII ではバイト数と文字数が等しいので一致する範囲は変わらない。既定の `ShortWord=3` では、一致しない CJK 1 文字は常に「短い語」とみなされ、断片の端にならない。

一致を囲む粒度は、同じ統合済み一致範囲に属し連続する単位を 1 組にする。ASCII は 1 単位なので語ごとに囲み PostgreSQL と同じになる。CJK の `東京都` は `<b>東京都</b>` になる。接するだけの一致範囲は併合されないので別々に囲む。一致範囲・断片の境界・区切りの挿入位置はすべて文字境界に揃う。

## 既知の差

| 事象 | 本 DB | PostgreSQL 17 |
| ---- | ----- | ------------- |
| 整数として解釈できない値（`abc`・`1.5`） | `22023` | `22P02` |
| 32 ビット整数の範囲外の値 | `22023` | `22003` |
| エラー文言 | 固定の英語。キー名・値・本文を含めない | 入力を含む |
| 本文が 1 MiB 超 | `54000` | 上限なし |
| 生の一致数が 65,536 件超 | `54000` | 上限なし |
| 出力が上限超過 | `54000`（切り詰めない） | 上限なし |
| `MaxFragments` が上限超過 | `54000` | 上限なし |
| 選択処理の歩数が予算超過 | `54000` | 上限なし |
| 検索語が `MAX_QUERY_BYTES`・`MAX_QUERY_TERMS` 超 | `22000` | — |
| 同じ語を複数回含む検索語 | 語の集合として 1 回に畳む | 項目ごとに数える |

## 資源上限（fail-closed）

- 入力: 本文 1 MiB・検索語 16 KiB・一致 65,536 件（`MatchSpanLimits` の既定）。超過は切り詰めずエラー
- 出力: 追記の前に毎回、長さを checked 演算で求めて上限と比べ、超えるなら確保せずに `54000` で止める。切り詰めない
- 仕事量: PostgreSQL 由来の選択処理は、`MaxWords` が巨大だと一致ごとに本文末まで走査し、最悪で（一致数 × 単位数）になる。選択処理のすべての内側ループが 1 歩ずつ消費する歩数予算（`MAX_HEADLINE_STEPS` = 2^26）を設け、使い切ったら `54000`。決定的な数え方で、最悪入力（1 MiB 弱・一致 6 万件・`MaxWords=2147483647`・`MinWords=2147483646`）でも概ね 1 秒未満で打ち切る
- 確保は `try_reserve` で行い、失敗したら `54000`。長さは checked／saturating 演算で扱う

### CLI

| フラグ | 範囲 | 既定（= ハード上限） | 意味 |
| ------ | ---- | -------------------- | ---- |
| `--max-ts-headline-bytes <N>` | `1`〜`4194304` | 4 MiB（行の `TEXT` 列値 1 個分の上限と同値） | 出力のバイト長の上限 |
| `--max-ts-headline-fragments <N>` | `1`〜`1024` | 1024 | `MaxFragments` オプションに許す最大値 |

- 設定できるのは**下げる方向だけ**。範囲外・非数値・値欠落・2 回目以降の重複指定は起動エラー（fail-closed）。解決は bind・ユーザーストア読込より前。環境変数やセッション・SQL・テナントから変える経路は作らない（全テナントに同じ値が効く）
- 値の運搬は `engine::headline_limits::HeadlineLimits`（`Copy`・フィールド非公開・ハード上限で飽和）を `EngineCore::with_headline_limits` で起動時に 1 回注入する。範囲検証は engine の `validate_max_output_bytes`／`validate_max_fragments` に一本化し、wire-server は CLI 文字列を厳密パースして渡すだけ
- 上限は**束縛時に関数ノードへ焼き込む**（`BuiltinFn::TsHeadline2`／`TsHeadline3` のペイロード）。評価時に thread-local を読むと、スコープ外で評価される経路でハード上限へ黙って戻る fail-open になるため。束縛区間のスコープは `sparsevec_limits_scope()` を張る全箇所で一緒に張る（戻り値のガードに束ねてある）。スコープの外で束縛された場合はハード上限になる（常に有界）
