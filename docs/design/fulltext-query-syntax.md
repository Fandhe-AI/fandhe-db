## 1. 背景・目的

- 現状の疎検索は、クエリを `tokenize()` で bag-of-terms にして BM25 の和で順位付けする。フレーズ・除外・前方一致・OR の構文はない
- 構文を `websearch_to_tsquery` 互換にすることは公開 Issue #2111 で確定している。一方、字句規則・優先順位・エスケープ・CJK のフレーズの定義・
  統計との関係・上限とエラー契約は未決で、決めずに #2113〜#2116 を進めると実装ごとに解釈がずれる
- 本書は後続 4 Issue が参照する詳細設計を固定する。根拠は、公開 Issue の記述、PostgreSQL・SQLite・MySQL・Elasticsearch の公開ドキュメント、
  本 ADR 独自の決定（D1〜D10）に限る。spec の期待欄は列挙し直さない

## 4. 決定事項

### D1 字句規則（トークナイズより前に生の文字列へ適用）

- `-` は、入力の先頭または空白の直後にあり、直後が語の文字（ASCII 単語文字か CJK）または `"` のときだけ除外演算子とする。
  `a-b` や `-` 単独は従来どおり区切り文字
- `*` は、語の文字の直後にあり、直後が空白・終端・`"` のときだけ前方一致とする。`*` 単独や語の途中の `*` は区切り文字
- `or` は、大文字小文字を区別しない単独の語で、項と項の間にあるときだけ演算子とする。先頭・末尾・連続する `or` は捨てる
- `"` はフレーズの開始と終了を表す。閉じていない `"` は終端までをフレーズとする
- エスケープ文字は持たない。`\` は従来どおり区切り文字。`or` や `-` を語として検索したいときは引用符で囲む（`"or"` はフレーズ内の語）
- 括弧・ネストはない。パーサは非再帰の 1 パスで入力長に線形とする（#2113 の線形時間の根拠）
- 上記に当てはまらない入力は通常のテキストとして既存 tokenizer へ渡す。構文不正を理由にしたエラーは出さない（D7 の上限検証を通過した入力はどの入力でも Ok を返す。上限超過は D7 のとおり拒否する）

### D2 意味モデルと優先順位

- 優先順位は「除外・前方一致（単項）＞ 並び（暗黙）＞ `or`」。トップレベルを `or` で区切ったグループの和とする
- グループ内のフレーズと除外は硬いフィルタ、通常語と前方一致は任意（スコアのみに寄与）
- 演算子を含まない並びは積に絞らない（公開 Issue #2111 に記載された PG との意図的な差）。通常語どうしの `a or b` は `a b` と同じ結果になる
- 一致条件はグループごとに判定してから和集合にする。各グループは「そのグループ内の正の語（通常語・前方一致・フレーズ）への一致が 1 つ以上あり、かつそのグループの全フィルタ（フレーズ・除外）を満たす」ときだけ一致とする。文書はいずれかのグループが一致すれば一致
- 一致しなかったグループのスコアは加算しない。文書のスコアは、一致したグループのスコアの和とする（`a -b or c` で a と b を含み c を含まない文書は、グループ 1 が除外で不一致、グループ 2 も不一致なので 0 件。グループ 1 の a のスコアは使わない）
- 正の語を持たないグループ（除外のみ）は常に不一致。除外語だけの検索語は 0 件

### D3 境界の組み合わせ

- フレーズ内の `*`・`-`・`or` は演算子にせず、語または区切り文字として扱う
- `-word*` は前方一致の展開語すべてを除外する。展開語数の上限の対象に含める
- 空のフレーズ `""` と、トークンが 1 つも出ないフレーズは無視する
- `-` の対象からトークンが出ないとき（ストップワード 1 文字、記号のみ）は無視する

### D4 CJK の位置とフレーズの定義

- 位置モデル: トークン化の単位（ASCII 単語 1 つ、または CJK 1 文字）ごとに位置を 1 つ進める。ユニグラムとバイグラムは開始文字の位置を共有する。区切り文字は位置を消費しない
- CJK 連続 n 文字（n ≥ 2）のフレーズは、バイグラム b1..b(n-1) が位置 p, p+1, …, p+n-2 に連続して現れることで一致とする。1 文字のフレーズはユニグラム一致
- フレーズ内のストップワード（`"東京の店"`）は、ユニグラムが除去されてもそれを含むバイグラム（`京の`・`の店`）が残るので一致できる。
  ASCII と CJK の混在、およびストップワード 1 文字が単独の単位になる場合は、その位置を任意の 1 単位に一致する穴として扱う（PG がフレーズ内のストップワードを距離で数えるのと同じ考え方）
- 必須トークン規則（Issue #2114 の実装。`sparse/phrase.rs`）: ASCII 単語はその語、長さ 2 以上の CJK の連続はバイグラムだけ（並び中のユニグラムは使わない）、バイグラムに含まれない CJK 1 文字はユニグラム、単独で抑止されたストップワード文字は穴（位置を消費し任意の 1 単位に一致）。先頭と末尾の穴は落とし、最初の必須トークンからの相対位置に正規化する。`"cafe の 東京"` は `cafe@0, 東京@2`
- 区切り文字をまたぐ場合（`東京・都`）はバイグラムが生成されないので `"東京都"` に一致しない。既知の制約
- 空白を含む CJK（`"東京 都"`）も同じ tokenizer の結果で判定する（SEARCH-11 ポインタとの整合）。区切りは位置を消費しないため、この規則では `東京@0, 都@2` となり、文書 `東京都`（位置 2 に `都` のユニグラムがある）と `東京・都` に一致する。実装でこの帰結を固定した
- 除外語が CJK の複数文字なら上記のフレーズ一致による除外とする。トークンを 1 つでも含む文書を除外すると、`-東京` が `東` や `京` を含む文書をすべて落とすため避ける
- CJK に付けた前方一致は何もしない（`*` を外す）。ユニグラム＋バイグラムで部分文字列一致がすでに成り立つため。展開語数にも数えない

| 入力 | 解釈 |
| ---- | ---- |
| `"tokyo tower"` | ASCII 語 2 つが隣接位置に連続 |
| `"東京都"` | バイグラム `東京`・`京都` が位置 p, p+1 に連続 |
| `"東"` | ユニグラム `東` の一致 |
| `"東京の店"` | バイグラム `東京`・`京の`・`の店` が連続（ユニグラム `の` の除去の影響を受けない） |
| `"東京 都"` | tokenizer の結果（空白で分かれるため `東京` と `都`）で判定 |
| `"cafe 東京"` | ASCII 1 単位＋CJK バイグラムの位置連続で判定 |

### D5 BM25 統計との関係

- N・df・avgdl は RLS 暗黙適用後の可視集合（`search_within` の `visible_ids`）だけで計算する（RLS-8 ポインタ）。除外とフレーズのフィルタは統計の計算後に候補へ適用し、統計を変えない（Lucene の MUST_NOT と同じ）。スコアが演算子の有無で変わらないようにするため
- 除外語はスコアに寄与しない
- フレーズのスコアは構成トークンを個別の語として数えた BM25 の和とする（案 A）。フレーズ頻度を擬似語として扱う案 B（Lucene の方式）は可視集合でのフレーズ df の計算コストがかかるため不採用とし、将来の候補として記録する
- 前方一致の展開語は、それぞれの idf による BM25 の和とする（「広く返す」設計に合わせる）。ES の prefix が定数スコアにするのとの差は §3 のとおり

### D6 前方一致の展開

- 展開には順序付き語彙の範囲走査を使う。**決定（#2115）**: `HashMap` の `TermDictionary` は変えず、先頭が ASCII 単語文字の語だけを昇順に持つ補助索引 `prefix_vocab`（`Vec<(Box<str>, TermId)>`）を足した。CJK の前方一致はパーサが通常語へ落とす（D4）ため対象外。索引と同寿命なので世代キャッシュ（[sparse-index-cache.md](sparse-index-cache.md)）のキー・無効化経路は変えない。語幹の範囲の和集合を 1 回だけ走査して可視 df を判定する（語幹の数に比例して走査が増えない）
- 展開語数は、可視集合で df > 0 の語だけで数える。語彙はテナントをまたいで共有されるため、全体語彙で数えると上限超過の有無から他テナントの語の存在を推測できる（RLS のサイドチャネル）
- 走査コストは語彙サイズの上限（`MAX_CORPUS_TOKENS` 等）で有界
- 時間差のサイドチャネルは既知の制約として記録する

### D7 上限とエラー契約

- フレーズの必須トークン数には、データに依存しない定数 `MAX_PHRASE_REQUIRED_TOKENS`（暫定 64。Issue #2114）を置く。超過は切り詰めず `PhraseError::PatternTooLong` で拒否する（同じ語の繰り返しで位置の照合が `必須トークン数 × MAX_CORPUS_TOKENS` まで膨らむのを防ぐ）。`54000` への写像は #2115 で実装した（CLI 化はしない。[text-query-limits-cli.md](text-query-limits-cli.md) の D7）
- 上限は 2 種類: (a) 1 つの検索語の項の数、(b) 前方一致の展開後の語の数。どちらも既定値と CLI フラグを持つ。既定値を「上限なし」にしない
- フラグ名は既存の `*_limits_opt.rs` の `--max-…` 形式に揃える（#2115 で `--max-text-query-terms`・`--max-text-query-prefix-expansions` に確定。既定値・範囲は [text-query-limits-cli.md](text-query-limits-cli.md)）
- 新設する上限（(a)(b)）の超過は `54000` で拒否する。一部の語だけで黙って検索しない
- 既存の `MAX_QUERY_BYTES`・`MAX_QUERY_TERMS`（入口の `validate_query_bounds`）の超過は、現状の `map_hybrid_error` どおり `invalid_input`（22000）のまま変えない。既存の呼び出し元の契約と、演算子を含まない入力の後方互換（D8）を保つため。22000 を 54000 へ移すかは本書では決めず、#2115・#2116 の未決事項とする
- `MAX_QUERY_BYTES`・`MAX_QUERY_TERMS` はパーサの入口でも引き継ぐ（#2113）
- 検査順: 入口の既存上限（バイト長 → 項数）を最初に検査し、超過なら 22000 を返して終わる。通過した入力だけが構文解析へ進み、新設の上限（(a) → (b)）を検査する。両方を超える入力は常に 22000 になり、どの上限に当たったかで応答コードが揺れない

### D8 後方互換

- 「演算子を含まない入力」は、D1 の規則で演算子が 1 つも認識されず、かつ D1 で捨てられる `or`（先頭・末尾・連続する `or`）も含まない入力、すなわち大文字小文字を区別しない単独の語 `or` を 1 つも含まない入力と定義する。この入力は従来と同一の語列・同一の順位になる
- 単独の語 `or` を含む入力は、演算子として認識されるか捨てられるかを問わず後方互換の対象外とする（従来の tokenizer が生成していた語 `or` は残らない）。`or` を語として検索するには引用符で囲む（D1）
- 演算子を意図していなくても結果が変わる入力: 先頭の `-5`、空白の後の `-x`、単独の語 `or`（`or`・`or a`・`a or` のように捨てられる位置を含む）、語末の `*`、閉じていない `"`
- #2111 の「同一結果」の基準は上の定義の範囲で検証する

### D9 USING PLAN の経路

- `expanded_query_text` は LLM 出力の `search_terms` を疎側の検索語へ連結する。ここに構文を適用すると、出力中の `-` や `"` で意味が変わり、プロンプトインジェクションでフィルタを操作できる
- 既定ではこの経路に構文を適用せず、すべて通常語（リテラル）として扱う。EXPLAIN の `search_terms` への反映は #2116 へ申し送る

### D10 近接演算子

- `NEAR(n)`・`<N>` は演算子にせず、通常の語（`near`・数字）として扱う（#2111 に記載）

## 5. 入力例と解釈

| 入力 | 解釈 |
| ---- | ---- |
| `a b` | 任意語 a・b（従来と同一） |
| `"a b" c` | フレーズ a b が必須、c は任意 |
| `"a b" or "c d"` | 「フレーズ a b」または「フレーズ c d」 |
| `a -b or c` | グループ 1: a 任意かつ b を含まない／グループ 2: c |
| `-a` | 除外語のみなので 0 件 |
| `-"a b"` | フレーズ a b を含む文書を除外（他に正の語が要る） |
| `foo*` | foo で始まる語の展開（各語の BM25 の和） |
| `-foo*` | foo で始まる展開語のいずれかを含む文書を除外 |
| `東京*` | `*` を外して `東京` と同じ（展開しない） |
| `-東京` | フレーズ `東京` の除外（バイグラム一致） |
| `"東京の店"` | D4 のバイグラム連続一致 |
| `a "unterminated` | a は任意語、`unterminated` は終端までのフレーズ |
| `or a or` | 先頭・末尾の `or` は捨て、`a` のみ |
| `a-b` | `-` は区切り文字。語 a・b の任意語 |
| `NEAR(a b)` | 通常語 near・a・b |

## 6. 後方互換

D8 のとおり。演算子を含まない入力の結果は従来と一致し、意図せず演算子と解釈される入力と、D1 で捨てられる予約語 `or` を含む入力は D8 に列挙した範囲に限られる。

## 7. セキュリティ・テナント境界

- 構文木は engine 内の構造体だけで扱い、SQL・プラン文字列を組み立てない
- 統計・除外・フレーズ・展開数の計数は可視集合だけで行い、不可視行の存在を除外の評価や 54000 の判定へ反映しない（時間差は既知の制約）
- 非再帰で線形のパーサ、既定値付きの上限、超過時の 54000 により fail-closed とする
- USING PLAN の LLM 出力にはフィルタ操作を許さない（D9）
- 例示には架空の語だけを使う
