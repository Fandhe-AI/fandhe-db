# ADR: ストリーミングレプリケーションの方式

- ステータス: Proposed（設計記録。第 9 節のオーナー判断事項は未承認。承認を得たとは書かない）
- 対応: Issue #2172（親 #2171。後続は #2173・#2174・#2175・#2176・#2177・#2245。運用 doc は #2179、障害注入は #2178）
- 関連ビヘイビア: RECOVER-2・RECOVER-13・RECOVER-14・RECOVER-15（小項目は `RECOVER-15 (n)` で参照）・RECOVER-17、WIRE-9・WIRE-18、TASK-258。ポインタ: `docs/spec/04-behavior/recovery.md`・`docs/spec/04-behavior/wire-protocol.md`。本文は転記しない（[spec-confidentiality](../../.claude/rules/spec-confidentiality.md)）。契約は spec を正とし、本書は「どう実装するか」だけを書く

## 1. 背景・目的

- 現状はレプリケーション機能が無い。Phase 9（#2148）の段階 4 として、ストリーミングレプリケーションを入れる
- 方式は物理（変更ログの適用）で、既定は非同期とする。同期モード（#2245）と読み取りレプリカ（#2175）はオプションとする
- 昇格は運用者が CLI で行う操作として範囲に含める。自動フェイルオーバーは対象外（`RECOVER-15 (4)`）
- 本 ADR は後続 sub-issue の前提を 1 か所に固める。受入基準は ADR がマージされること

## 2. 方式の選択

| 案 | 内容 | 採否 |
| -- | ---- | ---- |
| 物理（変更ログの適用） | プライマリの commit 単位の変更ログをレプリカへ送り、同じ順序で適用する | **採用** |
| 論理（SQL・行の再送） | SQL 文または行変更を再実行する | 不採用。非決定的な関数・採番・トリガの再実行で結果が分岐しうる。operation_id 台帳（RECOVER-2）も同じ commit 点で再現しにくい |
| redb ファイルの定期コピー | ファイルを一定間隔で複製する | 不採用。ストリーミングにならず、整合した時点の切り出しも難しい。再同期（第 8 節）の素材としては使う |

- 物理を採る理由は 2 つ。(1) 台帳を含めて同じ commit 点を再現できる。(2) #2165 の変更ログ基盤を共有でき、バックアップ・復元（RECOVER-13・RECOVER-14）と土台が揃う
- 非同期を既定とする。レプリカの切断・遅延でプライマリの書き込みを止めない（`RECOVER-15 (8)`）
- 同期モードと読み取りレプリカは、既定では無効のオプションにする。レプリケーション自体も opt-in で、既定では無効にする

## 3. 変更ログ（#2165）への要求事項

レプリケーションが変更ログに求める性質を列挙する。各項目は「#2165 で確定」とし、本書では形式を決めない。

| 要求 | 理由 |
| ---- | ---- |
| commit ごとに単調増加する番号（commit 番号） | 適用順・欠番検出・再開位置に使う |
| トランザクション単位で原子的な記録 | 部分トランザクションをレプリカに見せない |
| operation_id 台帳の書き込みを含める | 昇格後の再送判定を複製済みの台帳で行う（`RECOVER-15 (5)`） |
| 記録ごとの整合検査値 | 破損・改ざんを適用前に検出する（第 6 節） |
| 保持範囲の下限・上限の問い合わせ | 保持外の位置の要求を検出する（第 8 節） |
| 再開カーソル | 切断後に続きから送る |

- `storage_generation`（`GENERATION_TABLE`）は commit ごとに +1 されるストレージ全体のカウンタで、RLS prefilter キャッシュの失効検出に使われている。commit 番号に流用できるかは #2165 への問いとし、本 ADR では判断しない
- 一時表はセッションローカルで永続化しないため、複製の対象外とする
- #2165 が先にマージされた場合は、着手時にその ADR を読み、本節を「整合確認の結果」に書き換える

## 4. トポロジと接続（#2173）

| 案 | 内容 | 評価 |
| -- | ---- | ---- |
| 案 A | 既存の pg wire listener 上で、StartupMessage のレプリケーション用パラメータとサブプロトコル（CopyBoth 相当）を使う | **推奨**。PostgreSQL と同等で、[wire-copy-protocol.md](wire-copy-protocol.md) の資産を再利用でき、ポートが増えない |
| 案 B | 専用ポート（例 `--replication-bind`）で独自フレームを使う | listener・TLS・bind 検査を別に持つ必要があり、保守が増える |

どちらの案でも、設計に次を含める。

- 送信位置は、レプリカの ack で進める。ack は 3 段階（受信・永続化・適用）とし、同期モードの確認段階（第 8 節）と対応させる
- バックプレッシャを持つ。未確認の送信量が上限に達したら送信を止める
- レプリケーション接続数の上限と、未確認送信量の上限を CLI で設定できる。新しい `*_opt.rs` に閉じた語彙で置き、`connection_limits_opt.rs` の流儀に倣う
- レプリカの切断・遅延で、非同期のプライマリの書き込みを止めない（`RECOVER-15 (8)`）
- 受信した長さフィールドは、上限を検証してからアロケーションに使う

## 5. 認証・TLS（#2177）

### 資格情報

- レプリケーション専用の資格情報を、テナントのロールカタログとは別の運用者用ストアに置く
- `--users` は #2238 以降ブートストラップ専用なので、別フラグで指定する。例 `--replication-users <path>`（名前は #2177 で確定）
- テナントのロールではレプリケーション接続ができない構造にする（`RECOVER-15 (3)`）
- 認証方式は `auth_method_opt.rs` と同じく、サーバー全体で 1 つに固定する。SCRAM-SHA-256 を推奨する。レプリカ側は SCRAM のクライアントを実装する必要がある（[tls-scram-design.md](tls-scram-design.md)）
- 未認証のレプリケーション接続は拒否する

### TLS

- 非ループバックでは TLS を必須にする（WIRE-9）。`bind_guard.rs` と `tls_opt.rs` の流儀を、レプリケーションの接続にも拡張する
- **TLS クライアントが無い**。`crates/wire-server/src/tls/` にあるのはサーバー側のハンドシェイクで、レプリカはプライマリへ接続するクライアントになるため不足する

| 案 | 内容 | 評価 |
| -- | ---- | ---- |
| (a) 自作 | 既存の primitive（x25519・hkdf・key_schedule・aes_gcm・record_protection・ed25519・x509・certificate_verify・transcript・finished）を再利用して TLS 1.3 クライアントを作る。サーバー証明書は、葉証明書の SHA-256 指紋のピン留め、または CA ファイルで検証する | **推奨**。新規依存なし。外部プロトコルライブラリに依存しない方針と一貫する |
| (b) 依存追加 | `rustls` 等を導入する | オーナー承認が要る（第 9 節） |

- サーバー証明書の検証を省く設定は持たない
- 証明書・鍵・資格情報はログに出さず、マスクする（`tls_opt.rs` と同じ方針）

## 6. 適用ループ（#2174）

- commit 番号の順に、トランザクション単位で原子的に適用する
- 適用位置は、適用と同じ redb トランザクションの中で永続化する。再開を冪等にするため
- 順序違反・欠番・整合検査値の不一致を見つけたら、適用を停止する（fail-closed）。飛ばして続けない
- 適用後に、`storage_generation` などキャッシュ失効の契機を進める。RLS prefilter と HNSW などの世代キャッシュの整合を保つ
- 台帳も複製される（RECOVER-2・`RECOVER-15 (5)`）

## 7. 読み取りレプリカ（#2175）

- wire-server にレプリカモードの CLI を設ける
- 書き込み文・DDL・COPY FROM は `25006` で拒否する。NoSQL（HTTP）表層の書き込みも拒否し、HTTP への写像を揃える
- 読み取りは、適用済み commit 番号の時点のスナップショットで行う
- RLS と権限は、プライマリと同じ契約のまま変えない。レプリカは全テナントのデータを持つため、運用者の管理下に置く
- 遅延（適用済みの commit 番号・時刻）は、運用者の CLI とログでだけ観測できるようにし、テナントのセッションには出さない（`RECOVER-15 (8)`）

## 8. 同期モード・保持・再同期・昇格

### 同期モード（#2245）

- 確認の段階を CLI で選べるようにする: `remote_write`・`on`・`remote_apply`。既定は `on`
- 確認を受けるまで成功を返さない。待機の上限は既定で無い
- 上限を設けて超えた場合の扱い（書き込みを拒否するか、非同期へ縮退するか）は、運用者が CLI で選ぶ。既定値はオーナー判断事項（第 9 節）で、推奨は fail-closed（拒否）
- コミット完了と台帳記録の順序は、`commit_boundary.rs` の成功境界（RECOVER-5）との関係で #2245 が整理する

### 保持と再同期（#2176）

- 未送信の変更ログを、容量の上限まで保持する。既定値と CLI は #2176 で決める
- 上限を超えたレプリカ、または保持範囲の外の位置を要求したレプリカは、適用を停止し、再同期が必要な状態を報告する。欠落を飛ばして適用を続けない
- 再同期は、フルバックアップ（RECOVER-13・#2149）からレプリカを作り直し、その commit 番号から受信へ切り替える

### 昇格

- 運用者 CLI の操作とする。自動フェイルオーバーは対象外
- 昇格前に、受信・永続化済みで利用可能な変更ログの適用を完了し、最終適用位置（適用済み commit 番号）を確定する。受信位置ではなく最終適用位置を基準にする（受信済みでも未適用の commit は昇格後のデータに含まれないため）
- 喪失の範囲（非同期の場合）は、確定した最終適用位置より後として運用者へ報告する。ただし旧プライマリの最終位置が不明なときは、喪失範囲の上端も不明であると明記して報告する（上端を受信位置などで推定して確定表示しない）
- 昇格後の再送判定は、複製済みの台帳で行う
- 復元世代（RECOVER-17・#2446）との関係はポインタで触れるに留め、詳細は #2446 で扱う

## 9. 承認事項・オーナー判断事項

| 項目 | 内容 | 状態 |
| ---- | ---- | ---- |
| 依存の追加 | 推奨の (a) では新規依存なし。本 ADR では依存を追加しない。(b) を採る場合のみ、dependency-policy の 4 項目（クレート名と `=x.y.z`・ライセンス・メンテ状況・推移的依存）を揃えてユーザー承認を得る | 追加なし |
| 同期待機の上限超過時の既定 | 拒否（推奨）か非同期への縮退か | 未承認 |
| TLS クライアントの方式 | (a) 自作か (b) 依存か。あわせて証明書の検証方式（ピン留めか CA か） | 未承認 |
| レプリケーション用資格情報ストアの形 | ファイルの形式・フラグ名 | 未承認 |
| 接続方式 | 案 A（既存 listener）か案 B（専用ポート） | 未承認 |

## 11. OWASP Top 10 観点

| 観点 | 対応 |
| ---- | ---- |
| A01 アクセス制御 | 資格情報をテナントロールと分ける。レプリカでも RLS と権限は同じ契約。遅延と commit 番号をテナントのセッションに出さない |
| A02 暗号化 | 非ループバックでは TLS 必須。サーバー証明書を検証し、検証を省く設定は持たない |
| A03 インジェクション | サブプロトコルは固定のバイナリ形式。SQL 文字列を組み立てない |
| A04 不安全な設計 | 順序違反・欠番・検査値不一致で停止（fail-closed）。長さは上限検証後にアロケーション。接続数・未確認送信量に上限（DoS 対策） |
| A05 設定ミス | 既定では無効（opt-in）。証明書・鍵・資格情報をログに出さない |
| A06 脆弱な依存 | 推奨案は新規依存なし。追加時はユーザー承認と `=x.y.z` 固定が前提 |
| A07 認証の不備 | 未認証を拒否。SCRAM を推奨。認証方式はサーバー全体で 1 つ |
| A08 整合性 | 記録ごとの整合検査値。適用位置を適用と同じトランザクションで永続化 |
| A09 ログ・監視 | 遅延と再同期の要否は運用者のログ・CLI へ。テナントの情報を含めない |

## 12. 対象外

- 自動フェイルオーバー
- 論理レプリケーション（publication / subscription）
- カスケードレプリケーション
- 複数プライマリ
