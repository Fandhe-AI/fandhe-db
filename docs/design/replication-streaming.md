## 実装判断（Issue #2173）

本節は送信側 endpoint の実装で選んだ形式・フラグ・上限の記録で、契約の本文は private spec の RECOVER-15・WIRE-9
（上記ポインタ）を正とする。実装は engine の `storage::change_log::stream`、wire-server の `replication_opt`・`replication`。

**配置と接続**

- テナント向けの pg wire リスナーとは別の TCP リスナー（`--replication-bind`）。テナントのセッションは一切受け付けず、
  レプリケーションの接続もテナントのポートでは扱わない。1 接続 = 1 レプリカ
- TLS と認証の強制の詳細は #2177 の担当。本 Issue は fail-closed を既定とし、**ループバックだけ**を bind でき、
  非ループバックは起動拒否にする（`bind_guard` の平文と同じ扱い）。#2177 が TLS を配線したら緩める

**認証と許可リスト**

- 注意: ループバックの port-forward やプロキシで外へ出すと、資格情報とレコードが平文で流れる。TLS（#2177）が入るまで外へ出さない
- 専用ロール: `--replication-roles <file>` の `name:phc` 行（Argon2id。`--users` と同じ推奨パラメータのみ。
  ロール名は `[A-Za-z0-9._-]` の 1〜64 文字）。テナントのユーザーストアとは別の名前空間で、テナントのロールは
  このリスナーで認証できず、レプリケーションのロールもテナントのポートでは使えない。資格情報ファイルの形式は `--users`
  （`name:tenant:phc`）と非互換で、互いのファイルでは起動できない（起動時に拒否される）
- 照合は既存の `verify_phc`（同時 KDF 数の上限を共有）。未知のロール・不正なロール名は既知ロールと同じコストのダミー照合を行い、
  失敗は経路によらず固定遅延（`AUTH_FAILURE_DELAY`）の後に同じコードで返す
- 許可リスト: `--replication-allow <ip|cidr>`（繰り返し可・1 件以上が必須・全許可の `/0` は拒否）。accept 直後に送信元で判定し、
  許可外には何も読まず何も返さず閉じる。空のリストは何も許可しない

**プロトコル**（フレーム = 型 1B + 本体長 4B BE + 本体。詳細は `replication` モジュールの doc）

- Hello（版数・ロール・パスワード）→ Identity（DB 識別子・timeline・最新 LSN）→ Start（照合する識別子 + 適用済みの最後の LSN）→
  Ok → Record（LSN + `change_log` 表の値そのまま）と Heartbeat、受信側から Ack（受け取り済みの最後の LSN）。エラーは固定コード 1 バイト
- レコードは D3 の自己完結形式（チェックサム付き）のままで、受信側が検証する。長さは確保前に上限検証し（Hello 1091B、Start 32B、
  Ack 8B、Record は `MAX_RECORD_BYTES`）、型・長さ・値（ack の単調増加と送信済み以下）の違反は固定コードを返して切断する
- 同期モードで ack を待つ commit と ack の種類の追加は #2245。本実装の ack は「受け取り済みの最後の LSN」の 1 種類で、
  種類を足すときは新しいフレーム型で足す（版数は Hello で交渉済みの 1）

**送信位置と保持**

- 送信位置はレプリカの ack で管理する。接続中のレプリカごとに確認応答済みの位置を engine の保持位置として登録し
  （`pin_change_log_for_replica`）、刈り込み（`--change-log-retain-records`）は最小の保持位置より後を消さない。接続が切れると登録は外れる
- 開始位置の存在確認は、保持位置の登録の後に行う。保守 commit は登録簿のロックを commit まで保持するため、確認した範囲が直後に消えない。
  ロックの順序は常に「書き込みゲート → 登録簿」で、保守 commit はゲートを得てから登録簿を取る（ゲート待ちの間に ack の更新・登録・解除を塞がない。
  それらはゲートを取らず登録簿のロックだけで済むので、逆転によるデッドロックはない）。Start では、登録の直後に取り直した最新 LSN で遅れを再判定し、
  超えていれば `RESYNC_REQUIRED` で登録を外す。Ok の書き込みは短い期限（5 秒）にする
- 開始位置が `change_log` 表に無い（刈り込み済み）なら `RESYNC_REQUIRED`、プライマリの最新より先なら `AHEAD`、識別子の不一致は `FOREIGN` で拒否する。
  アーカイブのセグメントからの読み出しは後続（#2176 ではフルバックアップからの再構築のみ実装）。再同期は `replica-resync`（#2176）
- 保持を引き延ばせないよう、2 つの条件で切断し保持位置を外す（監視スレッドが送信ループと独立に判定する）:
  最も古い未確認レコードが送信を始めてから `--replication-ack-timeout-secs` を超えた（上限未満でも、書き込みが塞がっていても）、
  確認応答済みの位置からプライマリの最新までの遅れが `--replication-max-lag-records`（既定 100000）を超えた
  （最新 LSN は監視が約 100ms ごとに read トランザクションで自分で読む。送信ループが窓の満杯や書き込みの閉塞で読まない間も判定でき、
  読み取りに失敗したら保持位置を残さないよう切断する）。後者は
  `RESYNC_REQUIRED` を返す。切断されたレプリカが再接続しても、開始位置が刈り込み済み、または遅れの上限を超えるなら
  `RESYNC_REQUIRED` で拒否される（期待どおりの挙動。再同期は `replica-resync`。#2176）

**バックプレッシャと接続数**

- 送信済みで未確認の量が `--replication-max-unacked-bytes`（既定 64 MiB）に達したら送信を止める（フロー制御。未確認が空なら 1 件は必ず送る）。
  ack の待機上限は上の監視が判定し、そのレプリカだけにエラーコードを送って切る（コードを書く間も塞がるときは `shutdown` で解く）。
  書き込みタイムアウトにも同じ時間を使う。1 バッチの読み出しは `max-unacked` とは別に 16 MiB で打ち切る。窓に入らなかったレコードは 1 件だけ持ち越して再利用し（毎ループの再読み出しと検証をしない。大きさは 1 件のレコードの上限以内）、窓が空くまで待つ。
  ack のプロトコル違反（後退・送信済みの超過・型・長さ）は、ack 読み取りが理由を立て、送信ループ（書き込みはここだけ）が `BAD_REQUEST` を書いてから切る。書き込みが塞がる場合は監視が 1 秒の待機で諦めて切る
- 送信キューをプライマリ側に持たない（読み出しは都度 `change_log` 表から取る）ので、メモリは 1 バッチ分に有界。engine は読み取りトランザクション
  しか取らず、書き込みゲートに触れない。レプリカの切断・遅延・停止が commit を止めることはない（非同期）
- `--replication-max-connections`（既定 8、1〜256）は認証済みの枠。超過は認証の後に `BUSY` を返して閉じる。認証前の接続は別枠（16）で、
  Hello と Start の待機は各 5 秒。認証に失敗し続ける送信元は、5 回を超えると指数的に伸びる（最大 60 秒）バックオフの間、読まずに閉じる
  （送信元の表は 1024 件で有界）
- 不正値・重複指定・前提の欠落（`--change-log` なし、bind なしの従属フラグ、ロール・許可リストの欠落）は DB を開く前に起動拒否。エラー文は固定の英語で値・パスを含まない

## 実装判断（Issue #2174）

本節は受信側（レプリカ）の適用ループの実装判断の記録で、契約の本文は private spec の RECOVER-15（上記ポインタ）を正とする。
実装は engine の `storage::change_log::replica_apply`、wire-server の `replica_opt`・`replica`（`wire-server replica` サブコマンド）。

**適用位置と原子性**

- 適用位置は `storage_generation`。変更ログの 1 レコードは 1 commit で、本体に世代表の更新を含むため、レコードの適用・
  `change_log` 表への追記・世代の更新が同一の redb トランザクションで確定する。別の位置表は持たない。再開位置は常に DB の世代から取り直す。
  各レコードの適用後に「世代 == そのレコードの LSN」を検査し、満たさなければバッチ全体を abort して停止する
- 受信を溜めた複数レコードを 1 つの書き込みトランザクションで適用する（既定は 256 件・16 MiB）。バッチ内に不整合があれば全体を abort し、
  何も適用しない。durability は `Immediate` の保守 commit で、commit が済んでから ack を送る。クラッシュ後は適用済み LSN から再送されるので二重適用は起きない
- 順序違反（欠番・`prev_lsn` 不一致・フレームの LSN とヘッダの不一致）・DB 識別子／timeline／版数の不一致・チェックサム不正・適用不能なレコードは適用せず停止する。
  適用済みの LSN の再送は、`change_log` 表の同じ LSN の行とバイト一致なら読み飛ばし、不一致は分岐として停止する

**レプリカの DB の開き方**

- ベースのコピーを**変更ログを有効にしないまま**開く（`Storage::open` のみ）。ベースは変更ログを一度有効にした DB なので、通常の書き込みは
  既存の `54000`（`DisabledOnEnabledDb`）で拒否される。適用だけが専用の書き込み入口を通る（読み取りレプリカの `25006` への写像は #2175）
- 帰結: レプリカ自身の `change_log` 表は適用のたびに伸びる。アーカイブ・刈り込み・再配信（カスケード）は対象外

**停止の分類と終了コード**

| 分類 | 例 | 動作 |
| ---- | -- | ---- |
| 適用停止（終了コード 10） | 順序違反・チェックサム不正・識別子／版数の不一致・適用不能・分岐 | 再接続して飛ばして進めない |
| 要報告（終了コード 11） | プライマリの `FOREIGN`・`RESYNC_REQUIRED`・`AHEAD`・認証失敗・Identity の不一致 | 適用を止めて報告のみ（再同期は `replica-resync`。`RESYNC_REQUIRED` は標準エラーの文言で区別。#2176） |
| 一時障害 | 切断・タイムアウト・ハートビート途絶・プライマリの `BUSY`／`INTERNAL` | 上限つき指数バックオフ（抖動つき）で再接続 |

- 停止状態の永続フラグは作らない。再起動時は世代から再開し、整合性違反は再検出される。引数の不備は終了コード 2

**接続と入力検証**

- 接続先は**ループバックのみ**（TLS と認証の強制は #2177。それまで非ループバックは起動拒否）。資格情報は `--credentials <file>`
  （`role:password` の 1 行。group／other から読める権限なら拒否）で渡し、CLI 引数・ログ・エラー文に出さない
- Identity を受けたらローカルの識別子と照合し、不一致なら Start を送らず報告して停止する。受信フレームも untrusted: 本体長は確保前に上限検証し、
  受信データの経路で `unwrap`／`expect`／添字アクセスを使わない。進捗（適用済み LSN・プライマリの最新 LSN）は運用者向けの標準エラーだけに出す

**既知の制約と後続**

- TLS と認証（#2177）、同期モードの確認段階（#2245）、障害注入試験（#2178）、運用 doc（#2179）は未対応
- 関数・UDF カタログなどプロセス内キャッシュの無効化は #2175 で扱った（下記「実装判断（Issue #2175）」の既知の制約）

## 実装判断（Issue #2175）

読み取りレプリカモード（RECOVER-15 ポインタ。契約の本文は private spec を正とし、ここには実装上の判断だけを書く）。

**起動方式**

- `wire-server --users <f> --db <base> --replica-primary <ip:port> --replica-credentials <file>` で、通常のテナント向けリスナー
  （SQL・NoSQL）と #2174 の適用ループを同じプロセス・同じ `EngineCore` で動かす（redb は 1 プロセスが排他的に開くため別プロセスにしない）。
  `--replica-max-backoff-secs`・`--replica-batch-records`・`--replica-batch-bytes` は任意。値の検証は `replica_opt::parse` に一本化した
- `--change-log`・`--replication-*`・`--backup-socket` との併用、ベースでない DB は DB を開く前後に起動拒否する（変更ログを有効にすると
  適用が拒否され履歴も分岐する。カスケードとレプリカからのバックアップは対象外）。ログイン名の同期と `--users` のブートストラップは
  DB へ書くため行わない（プライマリで作られ複製される）。`--users` は認証の構成に引き続き必須
- 適用ループが停止（整合性違反・プライマリの拒否）したらプロセスごと終了する（終了コードは `replica` サブコマンドと同じ 10・11）。
  古いデータを黙って配り続けない fail-closed の判断

**書き込みの拒否（`25006`）の 3 層**

1. トランザクション層: `Storage` の read-replica フラグが立っていると、`SessionTransaction` はどの起点でも READ ONLY で始まる。
   暗黙トランザクションも writer を取らず読み取りスナップショットだけを開く。既存の READ ONLY の機構（許可リスト方式の判定・
   `ensure_writer` の `25006`・COPY FROM の事前拒否）をそのまま再利用する。`BEGIN READ WRITE`・`SET TRANSACTION READ WRITE`・
   `SET SESSION CHARACTERISTICS ... READ WRITE` は `25006`。修飾子なしの `BEGIN` は READ ONLY として始まる
2. autocommit の分類層: `execute_parsed_in_session_inner` の先頭で、許可リスト（`read_only_permits`）に無い文を台帳・採番・
   カタログ・writer に触れる前に `25006` で拒否する。`COPY FROM` は権限検査の後・CopyInResponse の前に拒否する
3. ストレージの choke point: `Storage::wrap_gated` が read-replica フラグを見て書き込みトランザクションの生成を拒否する（安全網。
   `54000` 相当で、ログ行は出さない）。適用専用の `begin_replica_apply_txn` は通らないため適用は動く

**読み取りの意味と遅延**

- 読み取りは redb の読み取りトランザクションで行い、適用はバッチ単位の 1 書き込みトランザクションで確定する。読み手には常に
  commit 境界の状態だけが見える。読み取りは writer gate を取らないので適用を止めない。RLS・権限は通常の経路を通る
- 遅延（適用済みの commit 番号・時刻）は標準エラーだけで観測できる。テナントのセッションには、LSN を返す関数・SHOW・
  ParameterStatus を足していない（commit 番号の進みから他テナントの書き込み量を推測させないため）。`25006` の文言は固定で、
  LSN・世代を含まない。`SHOW restore_generation` は全テナント共通の値で commit 番号ではないため許容する

**既知の制約**

- プロセス内キャッシュ: 表・索引カタログの世代をキーにしたキャッシュは、適用が同じ世代の表を書き換えるため自然に失効する。
  世代をキーにしないもの（HNSW opt-in の増分グラフ、関数・UDF のプロセス内レジストリ）は網羅の確認が済んでいない。HNSW opt-in との
  併用は未検証として扱う（後続で検討する）
- 書き込み専用の Rust API 入口（`execute_bound_*_in_session` など）は、分類層ではなく安全網で拒否される（`25006` ではなく `54000`）。
  SQL・NoSQL の表層は分類層・トランザクション層で `25006` になる
- 昇格（フェイルオーバー）、PostgreSQL 互換の観測口（`pg_is_in_recovery()` など）は対象外

## 実装判断（Issue #2176）

再同期（ベースバックアップからの再構築）。ポインタ: RECOVER-15・RECOVER-13・RECOVER-17・TASK-258。

- **サブコマンド `replica-resync` を新設**: `--socket`（稼働中のプライマリのバックアップソケット）・`--out`（新しいレプリカ DB。
  新規パスに限り、上書きしない）・`--primary`・`--credentials`。古いレプリカ DB には触れない（運用者が退避または削除する）。
  既存の `replica` へのフラグ追加にはしない（既存 DB の置き換えになるため）。既存のバックアップファイルからの再同期は対象外
- **`restore` を通さない・復元の世代番号は進めない**: `restore` は公開前に復元の世代番号を進めるが、その表は変更ログの記録対象外で
  レプリカがプライマリに追いつけない。進めるとプライマリと永久にずれ、アプリに「復元された」と誤って知らせる。再同期は
  プライマリのフルバックアップをそのまま使うので世代は進まない
- **手順（fail-closed）**: 一時名へフルバックアップ → 整合検査（矛盾・検査不能は公開しない）→ ベースの連続性検査 →
  プライマリへの確認接続（Identity をベースと照合し、Start(切り替え点) が Ok なら Ack せず閉じる）→ `hard_link` で公開
  （公開先が検査したファイルと同じ inode かを確かめ、違えば取り消す）。どの失敗でも最終名には何も出さず、一時名は消す
- **切り替え点の検査**: engine の `replica_base_point_of`（読み取り専用で開く）が、メタ情報の存在と「最後の LSN（変更ログ表の末尾、
  空ならアーカイブ水位、無ければ初回有効化時の世代）= `storage_generation`」を確かめ、`{db_id, timeline, end_lsn}` を返す。
  同じ検査を適用ループの開始時にも実行する（`Storage::check_replica_base`。`replica` と読み取りレプリカの両方）。
  不一致は `ReplicaApplyError::BaseDiscontinuous` で終了コード 10
- **「再同期が必要」の報告**: 終了コード 11 は変えず、`RESYNC_REQUIRED` のときだけ固有の英語文を標準エラーへ出す
  （ハンドシェイクとストリーム中の両方）。専用の終了コードは採らなかった（#2174・#2175 の契約の変更を避ける）
- **終了コード（`replica-resync`）**: 0 成功、1 実行時の失敗、2 引数・パスの拒否、3 公開済みだが後始末を確かめられない、
  4・5 整合検査の矛盾・検査不能、10 ベースが連続しない、11 プライマリの拒否（`RESYNC_REQUIRED` は文言で区別）
- **既知の窓**: 確認接続の後、レプリカを起動するまでは保持位置を登録しないため、その間に刈り込まれうる。その場合は起動した
  レプリカが再び `RESYNC_REQUIRED` で止まる（飛ばして進めないので安全）。直後に起動し、保持を十分に取る
- **範囲外**: アーカイブのセグメントから刈り込み済みの区間を送る経路、ベース取得中からの保持位置の登録、再同期の自動実行、
  専用の終了コード、保持の容量（バイト）指定
