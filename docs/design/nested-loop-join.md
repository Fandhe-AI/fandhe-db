# 非等価 JOIN のネステッドループ結合（実行方式・比較回数上限・SQLSTATE）

## ステータス・対象

- ステータス: 採用（設計記録。実装は #1837〜#1839（すべて実装済み）。#1837 は INNER、#1838 は LEFT／RIGHT の未一致追跡（D10）とキー無し FULL の `0A000`（D11）を実装済み）。比較回数上限の値は #1837 の release ビルド実測で桁を確認済み（下記「実測」節）
- ポインタ: SQL-60（spec 本文は転記しない）
- 対象: 等価結合キーを持たない ON（`a.x < b.y`・`BETWEEN`・`OR` を含む形）の実行方式、比較回数・メモリ・時間の上限、外部結合の未一致行の追跡方式、SQLSTATE
- 親: #1835。先行: #1829（ON 単側述語）・#1830（ON 残余）・#1831（CROSS JOIN）・#1834（WHERE の等価昇格）・#1551（[join-limits-cli.md](join-limits-cli.md)）・#1798（[statement-interrupt.md](statement-interrupt.md)）
- 後続: #1837（INNER の実行器）・#1838（LEFT／RIGHT／FULL）・#1839（ON パースと実行器選択の配線）。時間上限は #1950・#1951・#1954

## 背景

等価キーの無い ON は、#1839 より前は束縛段（`sql/join/plan.rs`）で `42601` になっていた。これをネステッドループ結合（NLJ）で実行する。入力上限（各側 100,000 行）どうしの直積は最悪 10^10 回の比較になり、出力上限（100,000 行）では抑えられない（大半のペアが述語で落ちる場合、出力が小さくても比較は膨らむ）。そのため出力上限とは別軸の「比較回数上限」が要る。

## 決定

| # | 決定 |
| - | ---- |
| D1 実行器の選択 | 段ごとに選ぶ（left-deep の連鎖内で混在可）。等価キーあり → 既存のハッシュ結合＋ON 残余。キーなし・ON 残余なし（CROSS・カンマ・共通列 0 個の NATURAL）→ 既存の直積経路（`左 × 右 ≤ 出力上限` の確保前判定）。キーなし・ON 残余あり → NLJ。「キー無し ON は `42601`」は #1839 でこの条件に限って解除した（解除済み）。述語は既存の `ResNode` と `residual::eval_all` で評価する |
| D2 ループ構造 | 外側ブロック化は採用しない。両側とも `Vec<ResultRow>` として実体化済みで（入力上限と `JoinBudget` で有界）、ブロック化の利点（I/O 削減）が無い。外側は蓄積タプル（`on_acc` を 1 回ずつ評価して通過したもの）、内側は新 relation の行のうち `on_new` を通過したものの索引列（1 回だけ作る）。二重ループで `on_mixed` を評価する。ハッシュ表は作らない。帯域結合等の最適化は対象外 |
| D3 比較回数の定義 | 比較 1 回 = `on_mixed` を評価するペア 1 組。単側述語（`on_acc`・`on_new`）の評価は入力上限・出力上限で有界なので数えない。`on_mixed` が空の段は比較 0 回で、出力件数（通過 acc × 通過 new）を出力上限で確保前に判定する（CROSS と同じ扱い） |
| D4 比較回数上限の値 | ハード上限 `MAX_JOIN_COMPARISONS` = 10,000,000（出力上限 100,000 の 100 倍）。既定値はハード上限と同値。1 比較あたり数十〜数百 ns の評価で 1 文あたり数秒以内に収まる桁であり、入力上限どうしの直積 10^10 を 3 桁下回る |
| D5 予算の単位 | 文全体で 1 つの比較予算。3 表以上の連鎖で NLJ 段が複数あっても合計で上限を超えない（`JoinBudget` と同じ考え方）。累計は `checked_add` で行い、オーバーフローも超過扱い |
| D6 判定位置 | NLJ 段ごとに、`on_mixed` の評価を始める前に「通過 acc 数 × 通過 new 数」（`checked_mul`）を残り予算と照合し、超過なら評価もペア確保もせずに `54000`。ループ内の累計カウンタは安全網として残す。判定は可視行（RLS・WHERE プッシュダウン適用後）の件数だけで行い、`LIMIT`／`OFFSET` の値に依存させない。結果は実体化前にエラーになるため部分結果は返らない |
| D7 既存上限との関係 | 4 本目の独立した軸として追加し、既存 3 軸は変えない。入力上限（各側 100,000。不変）、出力上限（一致ペア＋NULL 補完行 ≤ 100,000。NLJ でも段ごとに同じ判定）、最終段の早期停止 `final_stop`（#1797。不変）。ハッシュ経路の候補数上限（出力上限と同値）は据え置く |
| D8 メモリ | 新しいメモリ上限は設けない。NLJ が確保するもの（内側の索引列・`matched_*`・ペア列・評価用スクラッチ）はすべて確保前に既存の `JoinBudget`（`MAX_ARENA_TOTAL_BYTES`）へ計上する。ハッシュ表が無いぶん、同じ入力でハッシュ経路より確保量は増えない |
| D9 タイムアウト・中断 | 時間の上限値は本 ADR で新設しない（並行する第 2 の仕組みを作らない。statement-interrupt.md の方針）。NLJ は内側ループで `interrupt::check()` を呼ぶ（`CHECK_STRIDE` で償却）。切断検出・将来の statement_timeout（#1950／#1951）はいずれも `57014` で止まる。実行時間は D4 の比較回数上限で間接的に有界化する |
| D10 外部結合の未一致追跡 | 既存の `preserve_acc`／`preserve_new` と `matched_acc`／`matched_new`（bool 配列）をそのまま使う。LEFT は外側タプルごとの一致フラグを持ち、未一致はループ後に NULL 補完行として出す。RIGHT は新 relation の全行分の一致フラグを持ち（`on_new` で落ちた行も未一致扱い）、ループ後に未一致行を NULL 補完で出す。NULL 補完行も出力上限の対象 |
| D11 FULL JOIN | 等価キーの無い FULL JOIN（NLJ が選ばれる形）は PostgreSQL 17 と同じく `0A000` で拒否する。判定はデータ非依存で束縛段（走査前）に行う。等価キーあり＋残余の FULL は既存のハッシュ経路で従来どおり受理する。`ON TRUE` のような定数のみの ON の扱いなど境界は #1838 で PostgreSQL 17 の結合方式選択に照らして確認し、未確認の間は `0A000`（fail-closed）に倒す |
| D12 決定的順序 | 最終タプル列は既存の安定ソートで並べ替えるため、ループ順は結果順に影響しない（`scripts/check_sort_determinism.sh` ゲートの対象のまま） |
| D13 将来の CLI | フラグ名は `--max-join-comparisons <1-10000000>`。join-limits-cli.md の D1〜D8 と同型（下げる方向だけ・2 回目の指定は fail-closed・環境変数なし・`SET` なし・範囲検証は engine 側）。値は `engine::join_limits` にハード上限定数を置き、内部の `sql::join::JoinLimits` に `max_comparisons` を足す想定。CLI 配線自体は #1836〜#1839 の対象外 |

## SQLSTATE

| 事象 | SQLSTATE | 判定位置 |
| ---- | -------- | -------- |
| 比較回数上限の超過（オーバーフロー含む） | `54000` | NLJ 段の評価前（D6）＋ループ内の安全網 |
| 出力上限（ペア＋NULL 補完）・入力上限・共有バイト予算・暗黙の結果行数上限 | `54000`（従来どおり） | 従来どおり |
| 等価キーの無い FULL JOIN | `0A000` | 束縛段（走査前） |
| 切断・将来の statement_timeout による中断 | `57014` | `interrupt::check()` |
| 未対応の構文（ON の未受理の形・LATERAL 等） | `42601`（従来どおり） | 構文段・束縛段 |
| ON 残余の型不一致 | `42804`（従来どおり） | 束縛段 |

エラー文は英語の固定文言（例: `JOIN comparison count exceeds the limit`）とし、他テナントの行・件数・存在情報を含めない（含めるとしても上限値のみ）。新しい `wire_code` クラスは追加しない。

## テナント境界

比較対象・件数判定とも RLS 適用済みの可視行だけで行う。他テナントの行は比較にも NULL 補完判定にも現れず、上限超過の有無は自テナントの可視データだけで決まる。NLJ の導入でテナント境界を緩める経路は作らない。

## セキュリティ考慮（OWASP Top 10）

- アクセス制御: 上記のとおり可視行のみ
- インジェクション: ON 述語は束縛済みの `ResNode` として評価し、SQL 文字列を組み立てない
- 不安全な設計（DoS）: 比較回数上限を評価前に fail-closed で判定し、演算は `checked_*`。メモリは確保前に `JoinBudget` へ計上し、内側ループに中断点を置く
- 設定・情報漏えい: エラー文は固定文言。既定値はハード上限と同値で、将来の CLI は下げる方向だけ
- 整合性: 両側を 1 つのスナップショットで評価する既存の契約を変えない

## 実装の割り当て

- #1837: INNER の NLJ（D2〜D9・D12）。release ビルドの実測で D4 の桁を確認する
- #1838: LEFT／RIGHT／FULL（D10・D11）。実装済み。判定位置は束縛の最後（WHERE の外部結合簡約の後）で、両側の保存が残るキー無し FULL だけ `0A000`。簡約で片側以下になった段は #1839 で NLJ へ流すようになった（それまでは `42601`）。実行器（`nlj.rs`）にも多重防御の `0A000` を置く。列解決・型エラーは `0A000` より先に出る。`ON TRUE` など定数のみの ON は構文段で受け付けておらず束縛段へ届かないため対象外（従来どおり拒否）
- #1839: 実行器選択の配線（D1）・`OR` を含む ON・3 表以上での混在。実装済み。ON は構文段で `AND`／`OR`／括弧の論理木（`JoinWhereExpr`）のまま保持し、`on_split` が最上位 `AND` の conjunct 単位に分類する（`OR` を含む conjunct は結合キーにならず残余専用）。束縛段のキー無し非 FULL の `42601` を削除し、`keyless_full_on` の判定を「両側保存が残るキー無し段だけ `0A000`、他は NLJ／ハッシュ経路へ流す」に改めた。葉数（8）・括弧深さの上限は ON にも適用する（超過は `54000`）。`BETWEEN` は WHERE と同じく対象外（`42601`。`>= AND <=` の形は動く）

## 対象外

- 比較回数上限の CLI 化（D13）
- ハッシュ経路の候補数上限を比較回数軸へ統一すること
- 帯域結合・ソートマージ等の最適化、外側ブロック化
- DML の結合（`UPDATE ... FROM`／`DELETE ... USING`）での NLJ
- `EXPLAIN` の JOIN 対応、LATERAL・派生テーブル
- statement_timeout 本体（#1950／#1951／#1954）
- PostgreSQL 17 実機との照合（各実装 Issue で実施）

## 実測（#1837・D4 の確認）

- 条件: release ビルド、Intel Core i7-13700K、整数列 2 relation（各 3,163 行）、常に偽になる 2 個の比較（`x < y AND x > y`。1 比較あたり最初の述語の評価が主）、比較 10,004,569 回（上限 10,000,000 とほぼ同数）
- 結果: 5 回実行で 346〜359 ms（中央値 約 350 ms）。1 比較あたり約 35 ns
- 判断: 上限まで比較しても 1 文あたり 1 秒未満で、D4 の「数秒以内」の想定内。`MAX_JOIN_COMPARISONS` = 10,000,000 は改訂しない。計測用のテストは `nlj_comparison_throughput_probe`（時間はアサートせず出力のみ）
